## Prompt 原文

請你以「Claude Code 工作流架構顧問」的角度，全面審查這台電腦目前的 Claude Code 環境設定與使用流程。
這是本專案唯一一次使用 Fable 5 的機會。這個 session 結束後，本環境將由能力較弱的模型（如 Sonnet、Opus 4.8、Haiku）長期運作。你的終極任務只有一個：【將你的高階判斷力與架構思維，外化為可長期沿用的制度與實體檔案，全面升級本機的開發 Harness（工作流防閉環迭代機制），讓後續的弱模型能在此框架下穩定自主產出。】
請注意：本 session 的核心是「立制度與防錯機制」，不要拿去執行日常開發任務。請先進行診斷，不要直接修改任何專案檔案。

### 🔍 審查與診斷範圍

1. Claude Code 的全域設定與專案設定
2. Skills / MCP server 的配置與使用方式
3. Hooks、commands、agents、subagents 或自動化流程
4. system prompt、project instructions、CLAUDE.md 等指令文件
5. 檔案讀寫、任務拆解、驗證、回顧、測試與交付流程

### ⚙️ 作業規則（請嚴格遵守執行節奏）

1. 靜態診斷與提問：開場請先自主全面檢查環境。最多向我提出 5 個以內的關鍵釐清問題，隨後便進入全自主作業，不再停下來等待回覆。
2. 骨架先行 ＋ 隨做隨寫：由於此任務極度消耗 Context，請先將本任務列出的所有交付檔案「建立骨架目錄與結構定義說明」，確保 session 若意外中斷，大框架依然完整。隨後依據價值排序逐一填實內容，完成一項立刻落檔（Write to disk），不可堆積在 Buffer 中。
3. 備份與指引原則：修改既有檔案前必須建立 `.bak` 副本。新規則一律獨立成檔，CLAUDE.md 僅作為高效的「路由中心」指向各別說明檔。
4. 弱模型面向：你的讀者是 Sonnet 與 Opus。請提供「具體、具備明確判準（Rubric）、有輸入輸出範例」的規則。禁止使用「保持高品質」等自由心證的抽象詞彙。所有設計必須在 Sonnet 等級就能流暢執行。
5. 全力運作：請開啟最高 Effort 模式

### 📋 交付清單（按價值與執行優先級排序）

#### A. Harness 漏水診斷書

精準指出當前工作流中「最浪費 Token、最容易導致模型失焦、最常引發工具/MCP/Skills 調用錯誤」的前三個痛點，並給出物理級的阻斷方案。這份先寫，供後面所有產出引用。

#### B. 重寫 CLAUDE.md

重新梳理專案主入口文件。遵循「弱模型需要明確、強模型需要留白」的原則。收斂重複規則，移除過時資訊，將長內容抽離至獨立檔案，CLAUDE.md 只留核心架構與檔案路由。

#### C. 模型調度與動態升降級守則（獨立檔案）

針對弱模型的指揮官系統（Agent/Subagent）建立調度合約：
- 指揮官不下場：主對話模型（如 Opus 4.8）只做決策與架構引導，大批量讀檔、搜尋、Repo 掃描一律指派 Subagent（如 Sonnet），主對話只接收精簡結論。
- 派工三件套：任何 Subagent 的指派必須包含「明確目標與背景、嚴格的驗收條件、標準回報格式（成果路徑與關鍵行號，禁止噴出大段代碼）」。
- 異常升降級路徑：小模型（Haiku）工具或語法錯誤 1 次直接升級至 Sonnet；中階模型（Sonnet）同一子任務連錯 2 次，必須帶上完整失敗軌跡升級至 Opus 4.8；當高階模型解出固定模式後，降回便宜模型批次套用。同一件事最多重試兩輪。
- 隔離驗證：負責實作的 Agent 不得自我驗證。驗收必須指派「Fresh-Context Subagent」，透過 read-back 重新讀檔、實跑測試測資、或引入多樣本評審（Multi-agent debate）選優。

#### D. 判斷力外化矩陣（獨立檔案）

將你（Fable 5）獨有的高階直覺，量化為弱模型可肉眼比對的檢核表（Checklist）。每條判準必須附帶一個【完美正例】與【典型反例】。至少涵蓋：
- 什麼樣的信號代表「方向完全錯了，應該立刻停下換路徑」，而非在錯誤的代碼上原地重試？
- 滿足何種量化條件，才算任務「真正完成」可交付？ 
- 何時該觸發熔斷機制，停止自主作業並向 User 提問？

#### E. 標準化派工 Prompt 模板（獨立檔案）

提供給未來主模型直接套用的委派模板（含 Context 引入語法、驗收條件框架、回報格式填空）。針對常見任務型態各提供一份：搜尋研究、功能實作、代碼重構、代碼審查。

#### F. 知識迭代與反思協議（獨立檔案）

定義未來的弱模型如何安全地自我更新這套 Harness 檔案。哪些規則文件模型可自行優化更新（如：踩坑後的教訓紀錄），哪些動之前必須先徵得 User 同意？踩坑紀錄的寫入格式為何？累積到多長時必須自動觸發精簡與概念抽象化？

#### G. 給未來 Session 的交接信（獨立檔案）

三件我沒問、但你身為 Fable 5 認為對這個開發環境與工作流最關鍵的事。並指出這套制度在弱模型長期運作下，最可能出現的「退化/腐化方式」以及如何預防。

### 🏁 收尾與合規驗證（強制執行）

1. 對抗審查：文件落檔後，立刻開啟一個 fresh-context subagent 扮演「挑剔的審查員」，全面掃描這套 harness 檔案，揪出規則衝突、路徑錯誤、或是弱模型會誤讀的模糊語句，修正至完美為止。
2. 唯讀驗證：使用工具重新 read-back 讀取所有落地檔案，確保沒有截斷、內容完整。
3. 執行摘要：在主對話中提供一頁總結：你具體建立/修改了哪些檔案、核心架構邏輯、以及我明天開始與弱模型協作時，該如何啟動這套 Harness。
4. 熔斷控 Token：若發現 Context Window 即將耗盡，請立刻停下手上的產出，先完成收尾前三步，把未完成項目寫進「給未來 session 的信」交接。

### ⚖️ 誠實條款

請在診斷書中明確標記這套 Harness 的能力極限。利用拆解與隔離驗證可以逼近高階品質，但遇到「模糊的商業美感、品味決策」時弱模型注定失敗。請寫明當弱模型遇到這類極限時的具體應對標準。不確定的事就查，查不到就標註，不要編造。
