# AI Hero — 兩家公司補強再審視

## 結論

上一輪方向大致正確，但優先順序應改為：**先證明 AI 公司能正確完成一句話交辦，再增加知識、員工方法與自動化程度。** 工具測試通過，不代表 AI 會理解要求、正確派工、查對 Wiki、遵守授權或完成驗收。

本頁保存 2026-09-09 對話中的再審視結果，不是已實作清單。後續唯一計畫為 [[AI-一人公司/兩家一人公司 — AI Hero 補強計畫]]；測試公司的既有架構見 [[QA/一人軟體測試公司 — 架構與工作流程]]。研究材料不構成操作授權。

## 研究範圍與限制

- 上一輪研究盤點網站 sitemap 的 188 個不重複網址，讀取 25 項 Skills 的用途，深入查閱規劃、派工、評測、研究、交接、教學與架構的相關內容；其餘做目錄／摘要篩選。
- 不是所有正文逐字審核；付費課程與完整影片未完整觀看。網站數量是當時快照，不是永遠固定的數字。
- 本次存檔依據上一輪研究與回覆，沒有再次抓取全站，也沒有執行上游 Skills、安裝套件或重現網站所列問題。
- 2024–2026 不同時期教材共存；採用實際 SDK 程式碼前須重新核對官方 API。作者對自己方法的介紹，不等於已驗證適用本公司。
- 來源入口：[網站目錄](https://www.aihero.dev/sitemap.xml)、[Skills](https://www.aihero.dev/skills)、[公開內容說明](https://www.aihero.dev/llms.txt)。

## 上一輪建議的修正

| 原方向 | 判斷 | 修正後做法 |
|---|---|---|
| 主模型規劃，適合的小任務交 Luna | 保留 | 記錄包含返工的成本與時間，不以委派次數衡量成功 |
| 先試作再擴大 | 保留並釐清 | 探索樣品回答未知問題；完整小案驗證真正端到端交付；代表性試作不能只挑最簡單的題目 |
| 拆小任務 | 保留 | 每個任務具輸入、交付物、驗收與依賴，避免只拆成水平零件 |
| 不增加規格與任務文件 | 修正過度絕對的說法 | 小任務省略，跨對話或多步驟工作保留最少必要決策與依賴；不重複保存案件或發布狀態 |
| 增加交接文件 | 有條件 | 換人、換對話、換工具或中斷才需要；指向既有原檔，不複製第二份真相 |
| 加強品質檢查 | 細化 | 「有沒有做到要求」與「成果好不好」分開判斷，不能互相抵銷 |

上述限制與 [to-spec](https://www.aihero.dev/skills-to-spec)、[to-tickets](https://www.aihero.dev/skills-to-tickets)、[handoff](https://www.aihero.dev/skills-handoff) 的適用情境相符；具體落點仍由公司既有契約決定。

## 七項主要補強

### 1. 公司行為評測

建立固定交辦題目，驗證真實模型與工具執行，而非只測腳本。程式可判定的用程式；語氣、清楚程度由人抽查；AI 評分只輔助且需校準。來源：[Three Types of Evals](https://www.aihero.dev/three-types-of-evals)。

| 內容公司 | 測試公司 |
|---|---|
| 指定素材與單一平台，不能擅自增加平台 | 指定需求，案例須有可追溯預期結果 |
| 來源矛盾，不自行編造答案 | 需求缺漏，不猜測規格 |
| 未授權發布，只交草稿 | 無執行證據，不回報 Pass |
| 中途修改要求，最終版本符合新要求 | 注入已知缺陷，正確找到且留下證據 |
| 中斷續做，不重複產出或發布 | 重跑不重複建立問題，原失敗保留 |

初次可各選 6–10 題，每題重跑 3 次，固定環境及模型設定比較前後；這是建議規模，尚未執行。有限測試零錯誤不代表永遠零風險。

### 2. 需求與品質分開驗收

需求符合度逐项對照本次交付；專業品質檢查事實、語氣、案例有效性與可维护性。小案由主模型分兩輪；高風險才追加獨立 reviewer。實測證據另列，不能用評語代替命令結果。來源：[Code Review](https://www.aihero.dev/skills-code-review)。

內容公司現有 quality-gate 已區分範圍與品質；補強重點是可追溯驗收與行為驗證，不再建一套重複閘門。

### 3. Wiki 搜尋品質

現有測試公司搜尋以關鍵字匹配；讀得到不等於找得對。建立同義問法、無答案、過期資料、互相矛盾及引用不支持結論等題目。先測基準，再改善範圍、別名、排序、段落擷取；有量測需要才考慮向量搜尋。SHA-256 只證明檔案內容身分，不能證明正確或新鮮。來源：[改善 LLM 應用的方法](https://www.aihero.dev/how-to-improve-your-llm-powered-app)。

### 4. 執行證據與 Dashboard

AGENTS.md 與員工卡存在不等於已執行。工作台應顯示目標、實際進度、阻塞、成果、驗收與更新時間。能力可用、已連接、已實測分開呈現；未確認就顯示未知。中斷後先核對已完成動作，再決定續做；限制重試，避免重複副作用。

這是根據兩家公司現況提出的設計建議，不是 AI Hero 提供的現成產品。先用既有執行平台與本機工具，不新增常駐後端。離線 Dashboard 顯示最近建置的快照，不能假稱即時監控。

### 5. 內容公司研究流程

長文章／長影片先從讀者問題出發，查原始來源，形成大綱，再寫作與核對。不同角度不必每次都派不同 agent。短貼文保留快路線。STORM 論文指出來源偏差與過度聯想仍是限制；不把研究實驗數字當成本公司的效果。來源：[AI Hero 介紹](https://www.aihero.dev/storm-generate-high-quality-articles-based-on-real-research)、[STORM 原始論文](https://arxiv.org/abs/2402.14207)。

### 6. 帶使用者完成第一件事

開公司目錄 → 檢查工具與知識 → 明示缺口 → 開正確 Dashboard → 一句範例交辦 → 交付成果 → 告訴使用者下次怎麼說。安裝可中斷續做，不照搬 Bash wizard 的秘密或設定處理。來源：[Wizard](https://www.aihero.dev/skills-wizard)、[Wait What](https://www.aihero.dev/skills-wait-what)。

研究時发现測試公司 SETUP.md、Vault結構與使用說明.md、實作計畫.md 仍有無 commit／remote 的歷史敘述，Wiki 舊架構頁及索引也有狀態漂移。須分清「當時紀錄」與「目前安裝指南」，依實作時 Git 證據更新；不直接把全部歷史改成現在狀態。

### 7. 依失敗原因改善

區分需求不清、派工不當、資料錯舊、工具失敗、產出錯誤與驗收漏判。先在既有紀錄記原因；反覆出現的問題才提煉方法並重跑評測。不是每次失敗都增加 prompt 或換大模型。

## 不直接採用的做法

- 不整包裝 25 個 Skills，不另建與既有角色重複的入口。
- [Ask Matt](https://www.aihero.dev/skills-ask-matt) 是推薦 Skill 的路由，不是自動執行公司任務的引擎。
- [Research](https://www.aihero.dev/skills-research) 頁面自述遞迴派工與停止條件問題；本次未重現。借鏡時要限制範圍／輪次，不授權子代理再派工。
- 不照搬自動 commit、發布、外部安裝或帳號設定。Hooks 是輔助，不把文字規則或單一字串攔截當成完整安全邊界。
- 不因教材範例而改用 TypeScript、Vercel SDK 或建立新後端。先保留目前 Python／Node 與平台能力。
- 不要求私密推理過程；交付簡短判斷依據、來源與驗收證據即可。

## 建議架構與順序

```text
一句話交辦
  → 主模型確認目標、既有資料與授權
  → 選擇直接做／既有流程／先探索
  → 必要時派明確小任務
  → 工具檢查＋需求驗收＋品質驗收
  → 原始成果與既有正式紀錄
  → Dashboard 顯示結果、限制與必要決策
```

先修文件與建立基準，再跑兩家公司完整小案，接著改善搜尋／研究，最後按結果擴大自動化。使用者不當派工員；需要他處理的是實質決策與授權，不是內部角色選擇。
