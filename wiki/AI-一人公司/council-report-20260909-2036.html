YONGLI COUNCIL · 2026-09-09

保留完整能力藍圖，先驗證自用旅遊管家

先補可行性判準、訂單真實狀態、改動影響與離線使用，再擴大角色及連接。

2026-09-09｜5 位獨立顧問 + 5 位新上下文匿名互評者。兩個可用子代理名額；兩階段均按 2+2+1 執行，每 wave 完成才開始下一 wave。未指定模型或 profile，子代理未使用工具、未寫檔或再委派。沒有缺席；未偏離 5+5 邏輯。主席對中立問題作等義摘要，顧問未看到其他顧問回答，互評者看到完整匿名 A–E、未看到映射。這是設計壓力測試，不是旅程實測、專業資格認定或最新外部服務稽核。

顧問團一致同意

方向可行，但目前是能力藍圖，尚不足以直接當成完整公司的建置規格。最該補的是「可行性的判準、預訂真實狀態、途中可用性與投入是否值得」，不是更多員工。 保留一句話交辦、主模型決策與驗收、按需委派、單一旅程紀錄、來源時間和離線交付。角色方法不等於活躍 Agent；原規劃已說明不用同時啟動 16 人，不能把角色數量本身視為缺陷。

顧問團吵起來的地方

找好處的看重經驗累積與局部重排，其餘顧問較在意先證明第一趟可用。主席採用「先驗第一趟，再用第二趟驗重用效益」：保留長期方向，但不先承諾能省時或提供可靠的旅途中服務。 另外，自用與付費規劃服務不應混成同一首版。建議先以自用驗證；商業版還缺目標客群、服務內容、修改次數、回應時段、定價／成本、客訴與合作供應商責任，這些是後續營運設計，不是新增幾位 AI 員工便會成立。

互評抓到的盲點

1. **沒有比較基準。** 須比較現有人工方式與公司方式的研究時間、人工修正量、重要錯誤、查詢／模型成本；只完成一趟不等於值得建置。 2. **第二趟是否更省力未被驗證。** 偏好與方法可重用，舊價格、班次及營業狀態仍應重查；累積資料也可能增加維護負擔。 3. **缺少一頁成果範例。** 原規劃已列交付清單，問題是沒有可實際閱讀的例子，讓人辨認已確認、尚未訂、自己要做什麼。 4. **未把未知轉成行動。** 記了來源時間，不代表已定義資料過期、來源衝突或工具失敗時該重查、保留草案或阻擋交付。

建議

**保留完整能力藍圖，改以「能核對、能改動、途中能用的自用旅遊管家」作為第一版，通過小案驗證後才擴大。** 以下是主席綜合審查提出的補強，不是已完成的功能或全體顧問逐項共識： | 範圍 | 尚未想清楚的地方 | 更好的作法與責任 | |---|---|---| | 需求與同行者 | 一句話可能同時包含互相衝突的喜好；尚未定義誰能替同行者決定 | 旅客顧問區分每人的硬條件／偏好、代表決策者與待解衝突；沒有解就說明取捨，不暗自平均 | | 時間與行程 | 只有緩衝原則，沒有具體判準 | 設計師與交通規劃師記當地日期、時區、跨日、最晚入住／入場、交通與休息時間；檢查重疊及不可行轉乘 | | 計畫與訂單 | 「排進行程」容易被誤認為已訂妥 | 預訂協調員分開記建議、已查價、使用者選定、供應商確認；已付款與已確認也是不同事。確認需附訂單來源，取消與退款分別追蹤 | | 知識與來源 | 查詢時間不等於有效期限 | 研究員按資料種類及事件定重查條件；過期報價不能標可買、衝突要保留。不把所有資料套同一過期天數 | | 局部重排 | 改一站可能牽動末班車、入住與取消費，未定義影響如何傳遞 | PM 記行程依賴，鎖定已確認安排；重排顯示改動、受影響訂單與新增成本，再檢查整段硬條件 | | 旅途中協助 | 本機桌面系統如何在手機使用？沒網路怎麼辦？ | 第一版交付可在手機離線開啟的行程、地址、必要訂單與聯絡入口；需要 AI 改行程時明示網路與宿主需求，不假稱全天候救援 | | 工具與連接 | 名稱清單未交代工具故障、配額或權限不足的去向 | Architect 為每個連接列讀／寫範圍、實測時間、成本上限及失敗退路；讀不到就接收使用者提供的文件或標未確認 | | 私人資料 | 不放公開 Git 並不能限制模型、日誌、分享手冊或備份拿到什麼 | Architect 與總管制定最小收集、遮罩、分享版本、保留期限與備份恢復規則；一般行程輸出不自動包含完整證件資料 | | 驗收 | 同一模型研究後再確認，可能沿用同一個錯誤假設 | 覆核員對照原始来源，用程式驗時間／金額，用獨立情境驗缺資料與失敗，最後請真人只靠交付物完成查找 | 執行時維持五項核心責任即可：**總管（含 PM）、研究、行程設計、品質覆核、交付**。16 個角色保留作方法庫；交通、住宿、同行需求等按案啟用，Architect 只在建置或連接變更時介入。這是責任分組，不是固定要求啟動五個代理。 流程應增加交付前的明確分支： 需求 → 可行性檢查 → 研究／排行程 → 核對來源與訂單 → 檢查 → 行程包。 關鍵資料不足就保留「待確認」；硬條件不成立就提出替代方案。途中變動則先核對現況，再判斷影響、局部重排、重新檢查並產生新版本；改計畫不等於自動改訂單。

先做的那一件事

**完成一份「兩天一夜示範旅程驗收包」。** 用一組明確需求，交付一頁行程、費用、未預訂項目與離線手冊；在隔離副本注入景點關閉、錯過末班車與一筆過期報價，核對系統會否保留已確認安排、標示未知並提出可行替代。測試訂單使用清楚標示的合成資料，不必為驗證而購買。 試作前由主模型寫明驗收門檻：硬條件零違反、未確認資訊明示、訂單狀態不誤報；由主模型核對證據，真人驗證成果能否獨立使用。失敗先定位需求、資料或安排問題，再修正重驗。讓未參與設計的人只看成果，說出下一步去哪裡、如何前往、哪些尚未確認；同時記錄人工修正與時間。這是下一個建議動作，本輪沒有開始執行，也沒有修改 Wiki 規劃。

五份獨立回答

A · 路人甲
目前不應照全案建置，先證明一個人能靠它完成一趟旅行。對外行人而言，「16 角色、JSON、Dashboard」都沒回答：我要先提供什麼、最後拿到什麼、哪些事仍須自己做。 最需要補三處：第一，把「規劃服務」說清楚，是給自己用，還是替付費客人安排；兩者責任與資料需求不同。第二，區分「推薦住宿」「確認有房」「完成預訂」，避免使用者把行程上的項目當成已訂妥。第三，說明途中沒網路、班次取消或手機沒電時，如何找到可用資訊與求助對象。 先用一趟兩天一夜旅程做真人理解測試：讓沒參與設計的人，只看交付物就能說出下一步、未確認事項與備案。通過後再擴充角色。
B · 找好處的
這份規劃被低估的價值，是能把每次旅行的研究與修正累積成下一次可用的資產。旅程 JSON、來源時間與旅後經驗若接得起來，一人服務就能逐步減少重複查找，把時間投入旅客真正需要取捨的地方。 最大上檔在「局部重排」：交通延誤、景點關閉或同行者體力改變時，保留已確認訂單，只重算受影響區段。這項能力也能支撐較有差異的規劃服務。 建議按此方向建置，先用一趟真實旅程跑通 JSON→Dashboard→離線手冊，再測一次臨時改期與真人理解。這會同時驗證資料能否重用、旅途中能否操作，以及哪些角色值得獨立；16 個角色可先作為能力清單。
C · 找碴的
目前不應照完整方案建置。16 個角色把尚未證明可用的流程先複雜化，交接成本可能高於研究本身；列出角色與原則，也無法證明有人會抓到跨日交通、入住截止與取消期限之間的衝突。 最致命的缺口是「可行性」沒有可執行的驗收標準：資料缺漏、來源矛盾或資訊過期時，系統究竟阻擋、降級還是猜測？JSON 單一資料源也不能防止訂單與計畫不同步，必須分清提案、已確認預訂與途中實際狀態。 先用一趟含住宿、轉乘及改期的真實旅程驗證最小流程，實測斷網查閱、重複操作、局部重排與真人理解；私人資料權限及備份恢復也須先定義。通過前，暫緩通知整合與多角色自動協作。
D · 催你動的
可以落地，但現在不應照 16 角色完整建置。先用一趟真實、尚未下訂的兩天一夜旅行，驗證「需求能否變成可走、可核對的行程」。角色數量與 Dashboard 都不能證明這件事。 最快驗證：只做需求表、旅程 JSON、離線手冊，由主模型完成一次規劃，再注入「景點臨時關閉＋末班車趕不上」，檢查能否局部重排、守住預算與硬條件，並保留既有訂單。最後請真人只看手冊，說出下一步去哪、怎麼去、失敗時怎麼辦。 第一個具體動作：今天選定這趟旅行，填入日期、出發地、人數、預算上限與不可妥協條件。通過上述測試才加角色與介面；未通過就修資料契約和流程。
E · 問方向的
真正要驗證的不是「16 個角色能否組成旅遊公司」，而是「這套系統能否讓一個人更快做出可執行、途中看得懂的旅行決策」。自用與對客規劃服務的驗收差異很大，首版應先選自用，避免把尚未證實有效的流程包成服務。 目前問題問早了：角色與資料架構完整，不代表能解決旅行中的取捨。先拿一趟真實旅程，驗證預算與時間是否可行、重大假設是否清楚、交通失接後能否局部重排，以及離線手冊能否讓真人獨立使用。這四項未過，不值得完整建置。 建議保留主模型統籌與單一旅程資料，暫緩固定 16 角色；只為實測暴露的瓶頸增加角色與工具。成功標準應是可用的旅行結果與減少的人工負擔。

五份匿名互評

找碴的
最強 C：把「原則齊全」與「可執行驗收」分開，抓到缺資料如何處置及訂單同步的致命風險。盲點最大 B：先肯定資料重用與局部重排價值，卻未證明重用資訊仍有效、重排後仍可履約。五份全漏：人工規劃基準與投入上限；若完成同一趟旅行反而更耗時、更貴，即使測試全過，也可能是爛交易。
問方向的
最強 C：把「原則齊全」與「實際可用」分開，指出資料矛盾時的處置及訂單狀態同步，直接影響能否出發。 盲點最大 B：先假定資料累積與局部重排有價值，卻未確認維護成本是否低於人工重查。 共同漏項：沒有先問目前規劃旅行最痛、最耗時的是什麼，也缺少與現行人工方法比較的基準。單趟可用只能證明能完成，不能證明值得建置。
找好處的
最強 B：看見旅程資料與修正紀錄的累積價值，並以局部重排驗證差異化能力，最接近可擴大的服務。 盲點最大 D：驗證單趟能走，卻未驗證第二趟能否更省力；容易做成一次性的行程文件。 五份全漏：設計「第二趟重用測試」，量測研究時間、人工修正量，以及哪些偏好與規劃規則可安全沿用，才能證明這套系統值得持續投資。
路人甲
最強 D：直接說明第一步、測試情境與通過條件，外行人最容易照做。 盲點最大 B：強調資料重用與重排價值，卻沒講清楚「排進行程」不等於「已確認可用或已訂妥」，容易造成誤解。 五份全漏：缺少一頁實際交付物範例，以及逐項標示「誰查證、誰決定、誰下訂、何時需要使用者介入」。外行人仍不知道自己究竟要負責多少工作。
催你動的
最強 D：有今天可做的第一步，也有故障注入與真人測試，最快能分辨方案是否可用。 盲點最大 A：偏重交付物能否看懂，沒直接驗證交通、預算及硬條件是否真的可行；看懂不代表走得通。 五份全漏：誰在何時判定通過、失敗後修哪一項，以及相較人工規劃是否省時。先訂驗收門檻：硬條件零違反、未確認資訊明示、真人能獨立找出下一步，並記錄規劃與修正耗時。
