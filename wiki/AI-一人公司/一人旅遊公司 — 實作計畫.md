## 1. 目標、架構與技術選擇

交付一套獨立、可攜的自用旅遊公司：使用者在能讀取公司目錄的 AI 說目標，AI 按需安排 16 個角色方法，完成可核對的行程、費用、預訂準備與手機離線包。遇到變更時核對現況、分析影響、局部重排再驗收。

執行只保留五項核心責任：總管（含 PM）、研究、設計、覆核、交付；不是固定啟動五個代理。旅程 JSON 管當前資料，原始來源／確認文件提供證據，變更紀錄留歷史；Dashboard 與手冊由正式資料產生。

沿用 Markdown、JSON、Python stdlib、Node 及無前端框架的靜態 HTML/CSS/JavaScript。先提供本機工具與 AI 方法，不建立常駐後端、雲端資料庫、付款流程、排程服務或新的模型 API 框架。細部資料格式在 P1 建立，不沿用測試公司的 case.json 業務結構。

## 3. 主模型與 Luna 工作規則

由目前主模型判斷是否值得委派，負責規劃、關鍵決策與最終驗收。對範圍明確、上下文有限且可客觀驗證的實作，優先委派實際可用的 Luna；不熟悉或大量重複工作先做代表性試作，通過後分批擴大相似工作。簡單修改直接完成；高耦合或尚未釐清的部分由主模型先處理。若反覆退回且沒有改善，縮小任務或由主模型接手。

- 每包指定唯一檔案所有權、必要輸入、輸出、驗收命令與停止條件；不得只說「把某功能做完」。
- 同一工作區只允許一個寫入者；子代理寫入期間主模型不改檔。平行只做獨立只讀工作，最多兩個 children，children 不再委派。
- 小型寫入包可用 luna_worker；只讀 profile 只在主模型當段也是只讀時使用。沒有能力就主模型完成，不假報派工。
- 主模型讀回結果並重跑相關檢查；子代理 PASS 不直接當最終通過。
- 同一問題兩次退回無改善時，縮小或接手，不無限重试。
- 規則、狀態、隱私、跨檔整合與最終驗收預設由主模型負責。

## P1：資料契約、狀態與最小驗證器

**Owner：主模型定契約與核心；穩定後才考慮把單一驗證小包交 Luna。**

檔案：T/SCHEMA.md、T/範本/旅程.json、T/scripts/validate_trip.py、T/tests/test_validate_trip.py、T/tests/fixtures/。禁止修改來源公司的 schema。

工作：

1. 定 schema_version、穩定 id、revision、每人硬條件／偏好、決策代表、行程依賴、來源、訂單、支付、實際狀態與驗收紀錄。
2. 行程時間須有當地日期與明確 UTC offset，跨日換算到同一時間軸驗證；另保存時區標籤。缺 offset 或含糊日期不能判可行。若沒有可用時區資料，不推測 DST，自動驗證範圍明示，要求來源提供適用 offset。
3. 金額使用幣別與最小貨幣單位整數，明定幣別小數位；換匯採十進位、記匯率來源與時間。估算總額與已付／待付是不同視角，不能相加重算訂金。
4. 訂單與支付狀態分開；確認、取消與退款需各自憑證。樣本標 synthetic，正式驗收拒絕把 synthetic 當 live。工具只核對結構與證據完整性，不判斷供應商文件是否真實。
5. 來源狀態、重查觸發、依賴缺項／循環、過期或衝突資料、硬條件未知處理。程式能驗的條件與需要人工／來源覆核的條件分列，不以空檢查清單判 Pass。
6. 所有證據及輸出路徑限制在指定根內，拒絕 traversal、absolute path、symlink/junction 越界；UTF-8、非空檔、hash 及版本一致性。

CLI 設計：`validate_trip.py <trip.json> [--require-ready]`。exit 0 表示該模式可確定條件通過；exit 1 表示格式／證據／硬錯誤；exit 2 表示必要條件未知或待確認。普通模式允許合法草案但輸出 ready=false；嚴格模式不得把未知當可出發。輸出 JSON 包含 errors、pending、ready 與驗證範圍。

```bash
py -3 -B -X utf8 -m unittest discover -s tests -p 'test_validate_trip.py' -v
py -3 -B -X utf8 scripts/validate_trip.py tests/fixtures/ready-trip.json --require-ready
py -3 -B -X utf8 scripts/validate_trip.py tests/fixtures/pending-trip.json --require-ready
py -3 -B -X utf8 scripts/validate_trip.py tests/fixtures/invalid-trip.json --require-ready
```

預期：tests exit 0；三個 fixture 分別 exit 0／2／1。用 subprocess 斷言命令本身 exit，不用後續顯示命令掩蓋失敗。測跨日、時間重疊、缺offset、依賴循環、訂金、幣別、狀態混淆、過期來源及越界／空證據。

**停止／回復：** 任一錯誤 fixture 被判 ready 即先修 P1；只恢复本輪相關檔案，保留失敗 log。主模型驗收契約與原始輸出後才進 P2。

## P7：AI 行為、真人與第二趟驗收

**Owner：主模型最終驗收；必要只讀審查按當前能力使用，無強制昂貴 validator。**

檔案：T/evaluations/README.md、scenarios.json、check.py、test_check.py、fixtures/、runs.local/；T/驗收紀錄.md、HUB.md；W 本計畫與索引。

採用通用證據檢查器前檢視 Q/check.py 完整契約，保留其不把結構 PASS 當真實模型效果的邊界；不直接照搬測試公司考題。每次記模型、宿主、可用工具、規則／來源版本、原始對話、產物 hash、需求／品質／授權、限制、時間及成本（未知填 null）。

### 受控行為題：共 12 次新上下文候選執行

正常旅程 2 次、中斷續做 2 次，其餘各 1 次：硬條件衝突、過期／矛盾來源、付款但未確認、取消未退款、景點關閉／末班車失接、版本衝突、工具不可用、私人分享資料。全部使用隔離合成材料，不買票或取消真訂單。

首次僅做一個有 timeout 與可停止方式的新上下文預檢。宿主 unavailable／TLS／權限失敗就停止該路線，不重演先前無限 CLI 重試；不得以同一主模型文字走讀填補 12 次結果。可用子代理作受控執行時如實記宿主，不能當一般使用者新開桌面專案自動載入的證明。

### 真人與重用：分開列證據

- 真人只靠行程包找出下一步、交通、未確認與備案；未參與設計者才算此項，AI 走讀另列。
- 手機離線與 PDF／列印實際開啟，沒有設備或工具列 Not Run。
- 選兩組明確需求，與使用者既有人工方法比較研究／修正時間、錯誤、查詢成本與品質；人工基準沒人執行就 Not Run，不由 AI 假扮人工。
- 第一趟另列建置成本，第二趟重用適用方法／偏好並重查即時資料。不同需求難度、順序與學習效果記為限制；只有两個案例不推論統計可靠度。

```bash
py -3 -B -X utf8 -m unittest discover -s tests -v
py -3 -B -X utf8 -m unittest discover -s evaluations -p 'test_*.py' -v
py -3 -B -X utf8 scripts/check_structure.py
node --test offline/ui.test.mjs
node offline/build.mjs
py -3 -B -X utf8 evaluations/check.py --suite evaluations/scenarios.json --run-dir evaluations/runs.local/candidate
```

預期程式 tests／build exit 0；checker 合法完整紀錄 exit 0、無效或失敗 exit 1、空批次／未完成 exit 2。主模型另核對 12 次題目覆蓋與真實證據，checker 不保證批次跑齊或內容真實。

**回復與交付：** 保留 failed logs，不以新版覆蓋舊失敗。檢視任務差異與公開包內容；驗收紀錄附命令、exit、環境、時間、artifact path、未驗項。本計畫頁首更新到實際狀態，不把局部本機完成寫成全面完成。沒有額外 commit／push。
