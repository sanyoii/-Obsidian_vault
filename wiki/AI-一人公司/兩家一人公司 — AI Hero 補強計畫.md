## 目標與架構

保留現有 Python stdlib、Node、Markdown 和離線 Dashboard。共用工作原則，但兩家公司保持獨立資料與可攜性；不建立新後端、模型 API 框架、向量資料庫或常駐排程。研究依据：[[AI-一人公司/AI Hero — 兩家公司補強再審視]]。

## 派工規則

- 主模型：決定是否值得委派，負責規劃、資料邊界、跨檔整合、行為評測設計與最終驗收。
- Luna：只接明確、有限上下文、可客觀驗證的小任務。先做一個代表性試作，主模型重跑驗證通過再擴大。
- 同一時間僅一個寫入者；主模型在 Luna 寫檔時只讀、不改相同工作區。最多兩個子代理，平行只允許只讀，子代理不得再委派。
- 委派封包必含：目標、唯一檔案所有權、必要來源、交付物、驗收命令、停止條件。提醒不獨自在工作區、保留並配合既有修改。
- 同一缺陷退回兩次仍無改善，縮小任務或主模型接手。不把重複失敗無限重試。
- 純閱讀 reviewer 僅在主模型當段也維持只讀時使用；高風險才考慮獨立審查，不強制每個小修改派兩人。
- 角色方法不等於模型工作程序。沒有實際委派工具就主模型完成，紀錄「未委派」，不假報員工在執行。

紀錄欄位：scenario_id、suite 版本／雜湊、run_id、時間、實際模型／host／可用工具、規則版本、輸入、原始執行紀錄與產物指標／雜湊、需求判斷、品質判斷、授權檢查、執行結果、限制、原因分類、時間／成本（不可測填 null）。不要求私密推理內容。

| 題型 | C 內容公司 | Q 測試公司 |

| 範圍限制 | 不增加指定外平台 | 不擅加規格／產品範圍 |

## 失敗與回復

- 原檔備份保存本輪開始時內容（包含使用者既有修改）；不以 HEAD 取代 dirty 原檔。
- 回復前核對工作後雜湊；有他人後續修改就人工合併，不直接還原。
- 只撤銷本計畫的 diff，新增檔先保留並標記停用，不自行刪除；生成檔從回復後來源重建。
- 搜尋改善失敗先回復該變更，不保留無效複雜度。不能以放寬考題讓實作通過。
- 平台不提供真模型重跑或 UI 證據時，完成其餘工具／文件項，留下明確 Blocked；不用文字推演頂替。
