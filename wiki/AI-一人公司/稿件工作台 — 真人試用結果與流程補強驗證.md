## 真人試用發現

試用素材為公司 README 開頭介紹。使用者指定原稿，先比較三種寫法，再選底稿並針對第一段提出「加入可直接複製使用的提示詞」等回饋。AI 收到匯出的修改要求，回傳修訂 JSON；使用者表示已用完工作台，但沒有據此確認正式稿採用或所有回饋驗收通過。

| 發現 | 已知證據與判定 |
|---|---|
| 三稿原先無法逐段比較 | AI 提供了不同資訊順序，使用者指出同一段在講不同事情。後續改為三稿同為三段、相同主題順序，只調整同段表達；先前把標題貼入正文也導致段落編號偏移。 |
| 交接操作負擔過高 | 使用者須選稿、留言、複製修改指令、切回對話、取得 JSON，再回工作台。使用者實際回饋「很麻煩」，未達到期待的省事程度。 |
| JSON 存檔／上傳引導不清 | 現有程式已有「完整工具與需求 → 貼上修改稿 JSON」，可省掉另存檔案，但使用者未順利得知，AI 也只交 JSON 文字。既有捷徑沒有解決跨工具搬運。 |
| 使用者認為一筆建議未進入指令 | 本次對話收到的指令第二筆 feedback.note 完整包含「敘述的方式簡單明瞭. 一樣可以補上prompts給使用者,讓使用者可以copy and paste直接使用」。這份收到的指令未漏該筆；其他匯出或介面是否遺漏未重現，不能一概稱資料遺失。大量 JSON 不利於使用者確認回饋。 |
| 提示詞交付未充分貼近用途 | 修訂將提示詞放在正文引號內，沒有充分解決容易選取與複製的使用需求。修改者標「已處理」不等於使用者接受。 |
| 缺少 AI 自動往返 | 現有工作台整理回饋、產生要求、核對回傳資料；尚未接 AI 執行與自動回傳。此為目前能力界線，不以新按鈕或流程圖冒充完成。 |

期待的使用流程：在介面選稿／修改／留言 → 按修訂 → 系統帶入底稿與全部回饋 → AI 修改 → 結果自動回到對照畫面 → 使用者驗收。此流程尚未實作；本次暫停決定優先，不繼續建置。

## 其他流程可用什麼測試

以下是候選方案，尚未執行，也不授權改其他公司或重啟工作台。

| 優先 | 真實工作案例 | 要驗的方法 | 交付與通過判準 |
|---|---|---|---|
| 1（推薦） | 下一份確實要用的操作說明，例如一人公司 README 入門段落的精準修訂 | 範圍控制、回饋保留、版本對照、交付是否省事 | 使用者直接在對話給需求；AI 交可直接使用的正文／文件，回饋後只改指定段落。逐項對照無漏改、未要求部分保留、檔案可開啟；使用者不必製作 JSON 或搬運內部工作資料。正式檔採用仍依授權。 |
| 2 | 下一份實際要交付的報告或簡報中，一個代表頁與最終輸出 | 視覺可行性、同源實作、分開驗收 | 新方向依既有規則先交3–5張可行樣圖，選定後驗代表頁，再核對實際 PDF／HTML／簡報成品及長內容。已有核准模板直接沿用。沒有真需求就不另製報告測試。 |
| 3 | 從 Wiki 整理一份目前狀態／建議摘要 | 來源、版本、未驗界線及正確交接 | 每項結論可回到來源；舊 PASS 不冒充現況；缺答案明說。隔離案例中放入一筆過期或矛盾資料，確認能指出衝突，不改正式筆記來製造反例。 |
| 4 | 下一個已授權、範圍清楚的程式或文件批次 | 高階規劃、適當委派、首段關卡及驗收 | 工作量值得委派才交低階；先驗一段完整成果，再展開。記錄規劃、交接、自查、驗收、返工及接手總成本；極小修改直接由主模型完成，不為測委派增加工作。 |

## 最小驗證方式

1. 在該真實任務的既有文件或對話，先固定輸入、可改範圍、成品及通過條件，不另建立平台或帳本。
2. AI 完成一份可直接使用的成果；使用者給一輪真實回饋，AI 修訂後逐條回覆處理位置。使用者只負責需求與內容判斷，內部資料交換由承作處理。
3. 客觀部分核對來源、差異、未改部分及實際產物；清楚程度與操作感受由使用者判斷。自查與獨立驗收分開，不以文件存在當成流程落實。
4. 有重大錯誤、漏改、未核准差異或額外搬運負擔就暫停擴大並縮減流程。沒有原流程的可比基線，只能記本次時間／用量／感受，不報改善比例。一次成功只支持下一個局部試點。

## 尚未驗證與停止邊界

- 先前 A 工作台紀錄中的13項核心測試與27項瀏覽器檢查是指定版本／本機環境的歷史結果，本次未重跑；27項不等於27個獨立案例。
- 使用者這次已提供真人操作體驗，不能再寫「完全沒有真人試用」；但效率改善、全面可用性、最終修訂採用及所有驗收決策仍無證據。
- 本次使用者操作的網址協定、瀏覽器環境未確認，不藉此把 file://、真手機、screen reader 或獨立驗收改為通過。
- 工作台暫停；不自動建 API／CLI 接線、不新增服務、不刪現有檔案、不發布、不管理 task。其他流程方法仍可在另有真實需求的工作中驗證。
