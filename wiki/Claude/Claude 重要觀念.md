  
1. stop_reason — Claude 回應結束的方式有四種，不只「講完了」

回應被截斷、突然停、空白回應 — 寫 Claude API 應用最常踩的雷，多半是 stop_reason 沒判斷對。它不只是 debug 工具，是程式決定「下一步該怎麼做」的依據 — 每次回應都會回一個 stop_reason，告訴你這次是怎麼停的：
~~~
- max_tokens — 上限撞到，回應被截斷

- end_turn — 自然講完

- stop_sequence — 命中你設的停止觸發詞。例如要 Claude 生 JSON 包在 之間，可以設「」當停止觸發詞，Claude 一寫到就停，不會繼續多嘴

- tool_use — Claude 要你幫它呼叫工具
~~~
​把「有文字」當成「成功」直接用，遇 max_tokens 會看到半截字、遇 tool_use 會以為 Claude 沒回。先判斷怎麼停，再決定下一步。

2. System Prompt 定角色，Pre-fill 定開頭
多數人知道 system prompt，但 pre-fill 很少人聽過 — 它是 Claude API 才有、控制輸出最被低估的工具。
System Prompt 像演員的角色設定書 — 整場戲都這樣演（專業客服、有禮貌、不能洩漏內部資訊）。設定一次，整場對話都生效。
Pre-fill 像導演先幫演員講第一句台詞 — 「Coffee is better because」 — 演員（Claude）從這裡接下去，不會再說「That's a great question!」客套話。但角色還是設定書決定的，pre-fill 只管這次回答的開頭。
​常見錯誤：想強制 Claude 回 JSON，在 system prompt 寫「你只回 JSON、不要多話」 — 結果 Claude 還是會多嘴。因為 system prompt 管的是「行為傾向」，不是「格式」。要強制格式，必須用 pre-fill 替它把開頭講出來。
​一句話：System prompt 定角色，Pre-fill 定開頭。


3. Prompt Eval（評估）— 評分器不只一種，要看你在驗什麼
寫完 prompt 自己測幾次覺得 OK 就上線 — 多數人改 prompt 的方式。問題是「自己測 5 次」不算驗證 — 人下意識會挑會通過的 input。​
評估的做法：建一份固定題庫、寫一個評分器自動打分、每改一版 prompt 都讓它跑一次、看平均分動向。從「感覺變好了」變成「7.66 → 8.70 → 9.20」。
這節真正讓我學到東西的是 — 評分器不只一種：
~~~
- 程式評分器（Code Grader）— 用程式驗。輸出格式對不對、欄位齊不齊、長度有沒有超標 — 這類「能用程式檢查」的事，幾行 code 就驗完。確定性 100%、零 API 成本、零誤差。但只能驗「語法」，不能驗「對不對」。

- 模型評分器（Model Grader）— 叫一次 Claude 來打分。可以評語意品質（寫得好不好、有抓重點嗎、語氣對不對）。但不穩定 — 同個答案跑兩次可能 7 分 / 8 分，所以只適合比版本（v1 vs v2）、不適合當絕對指標。

- 人工評分（Human Grader）— 主觀、慢、貴。但「真的好用嗎」這種整體感受就是要主觀判斷 — 機器算不出來，最終還是得人來。
~~~
​實務上是混用：先用程式評分器篩掉硬性問題（語法錯、長度超標、缺欄位），剩下用模型評分器評語意，最關鍵的少量樣本給人工。
從「我覺得」變成「分數說」 — 任何認真做 LLM 應用的團隊，評估流程是第一件該建的東西。


4. Show, Don't Tell — 給 3 個範例勝過 10 條規則
​Prompt Engineering 整章 4 個技巧（Be Clear / Be Specific / XML tags / Multishot），最有威力的是 Multishot — 也就是業界常說的 few-shot：給 Claude 看幾個範例，比寫一堆規則有用。
想讓 Claude 寫得專業，多數人的直覺：寫「請使用專業語氣、避免口語、結構清楚⋯⋯」十條規則。沒太大用。
換個方式 — 給它 3 個範例：
~~~
範例 𝟷：[一段你覺得好的輸出]

範例 𝟸：[另一段]

範例 𝟹：[再一段]

​現在請用同樣風格寫 [新題目]
~~~
​
Claude 立刻抓到風格，不用定義什麼叫「專業」。
​關鍵差別：規則描述邊界，範例傳達語感。語感很難用規則寫清楚，但範例一看就懂。寫 prompt 卡關時，第一個該問的不是「規則寫清楚了嗎」，是「給範例了嗎」。

​5. Tool 是真的功能，但 Claude 看到的只是「使用說明書」
​「給 Claude 一個工具」直覺以為是 Claude 拿到一段 code 自己跑，像 import 一個 library — 不完全是。Tool 真正的能力（呼叫 API、查資料庫、開瀏覽器）是你的 server 在跑，Claude 看不到你的 code，它只看到一份 JSON Schema：
~~~
{

"𝚗𝚊𝚖𝚎": "𝚐𝚎𝚝_𝚠𝚎𝚊𝚝𝚑𝚎𝚛",

"𝚍𝚎𝚜𝚌𝚛𝚒𝚙𝚝𝚒𝚘𝚗": "𝙶𝚎𝚝 𝚌𝚞𝚛𝚛𝚎𝚗𝚝 𝚠𝚎𝚊𝚝𝚑𝚎𝚛 𝚏𝚘𝚛 𝚊 𝚌𝚒𝚝𝚢",

"𝚒𝚗𝚙𝚞𝚝_𝚜𝚌𝚑𝚎𝚖𝚊": { ... }

}
~~~

Claude 看到這份「說明書」決定要不要呼叫這個 tool、傳什麼參數。實際執行 tool 是你的 server 跑的 — Claude 自己從頭到尾沒碰過 code。執行完的結果你再塞回對話，Claude 拿到結果才寫最終回應。
整個流程是個雙向循環：Claude 寫紙條叫你查 → 你查完把答案塞進窗口 → Claude 看答案寫回應。Claude 永遠在密室裡。
所以 tool description 寫不清楚 = Claude 永遠不會正確呼叫。description 不是給工程師看的註解，是給 Claude 讀的說明書 — 這份說明書寫得好不好，直接決定 tool use 成不成功。
​整個分工很清楚：Claude 是「決策者」、開發者是「執行者」。Claude 寫紙條叫你呼叫工具，真正執行永遠是你的 server。這是 Anthropic 故意的安全設計 — Claude 不能自己連網、不能自己讀檔、不能自己亂跑 code。

​6. RAG 真正的工程難題：文件怎麼切、怎麼撈

​RAG（Retrieval-Augmented Generation）就是企業常做的「把內部知識庫接給 AI」那套架構。
想像要讓 LLM 去公司知識庫找答案 — 合約、法規、產品文件加起來幾百份，全部塞進一次 prompt 不可能（超過 context window、Claude 注意力分散、貴又慢）。RAG 的答法是先把文件切成小段、存成可搜尋的向量資料庫、問問題時只撈最相關的幾段給 Claude 看。

​講起來簡單，真正有 value 的兩個工程選擇是「怎麼切」跟「怎麼撈」。

​切的策略從最粗到最細有四種：固定字數切（每 500 tokens 一塊，會切斷句子）、按結構切（H2/H3、段落，保留語意邊界）、按語意切（用 embedding 算相似度合併，最聰明也最貴）、混合切（先按結構、太大再往下切，production 常見預設）。切壞了 Claude 看到的就是一堆斷頭片段。

撈也不是只有一招。多數人以為 RAG = 語意搜尋，但 production 級都是 hybrid search — 同時跑語意搜尋（抓概念相關）跟關鍵字搜尋 BM25（抓字面精確），合併兩邊的 top-K。為什麼要兩種？因為語意搜尋對「車≈汽車」很強，但碰到產品型號、法條編號、API 名稱這類精確字眼會變成模糊概念，反而漏掉。

​切壞或撈不齊的代價不是「答錯」，是「答得不完整你還看不出來」 — Claude 看到孤立片段會自信地給你不完整答案，不會自己說「我可能漏 context」。

​RAG 不是更好的 prompt，是更聰明的 context 篩選。怎麼切、怎麼撈，直接決定 Claude 看到的世界完不完整。

7. Cache 不是省錢小技巧，是「別讓對方重做你給過的功課」

Prompt Caching 第一眼看像個工程優化（省 90% input token 錢、加速）。但真正的觀念是這個：

Claude 收到 prompt 不是立刻回應，而是要先做一堆預處理（切 token、算向量、算 attention 關係） — 這些是很重的計算。回應送出後，Claude 把這些工作丟掉。下一個 request 進來，同樣內容又從頭算一次。

Caching 就是把這份預處理結果存下來重複用 — 在 prompt 裡標記哪幾段是「重複出現的」，下一個 request 進來如果開頭相同，直接撈上次算好的結果，跳過預處理。
對企業應用很重要：客服 bot 的 5,000 字公司政策、合約問答的 100 頁 PDF、長對話的歷史訊息 — 沒 cache 每次都重新計費，有 cache 直接 90% 折扣。
但有個陷阱：cache 不會自動開，要主動標記。而且變動的資料（使用者名字、當前時間）要放在 cache 範圍外，否則永遠 cache miss。

8. Citation 不是給 URL，是「指回我給你看的那段原文」
聽到 AI「給出處」直覺想到 ChatGPT、Perplexity 那種藍色連結 — 不是。
Citation 引用的是餵給 Claude 的私有文件 — 公司合約 PDF、客戶法規文件、網站爬下來的文章。Claude 不會跑去網路上找連結，它只能告訴你「根據這份文件，這句話在第 X 頁、原文是 Y」。
關鍵差別：對律師、保險、醫療、政府這類場景，「答對」不夠 — 必須能指回原文一字一句核對。沒 citation 的世界，使用者沒辦法區分「Claude 真的有讀文件」和「Claude 在用訓練資料瞎掰」。
打開方式只要兩個欄位（文件加標題、citations 設成 true），response 就會自動帶結構化的引用 — 含原文片段、文件名、頁碼。對企業導入幾乎是 must-have。

9. Workflow vs Agent — 控制權在誰手上
當任務 Claude 一次回答不完（要呼叫多次、用多個 tool、可能反覆 iterate），有兩種架構選擇 — 這個選擇會決定整個系統的成本、可預測性、debug 難度。
兩種架構的差別不在「用不用 tool」，在控制權：
~~~
- Workflow 像速食店 SOP — 你寫好流程：「客人點漢堡 → 拿麵包 → 加肉 → 加菜 → 包裝出餐」。每一步固定、Claude 是執行者。穩、準、便宜、出錯知道哪步壞掉。但客人說「不要番茄要加蛋」 — SOP 沒寫，店員愣住。

- Agent 像高級餐廳廚師 — 給廚師一個廚房、一袋食材、一袋工具，跟他說「讓客人滿意、預算 800」。廚師自己看冰箱、問客人喜好、自己決定怎麼做。彈性高、能處理沒見過的需求。但同個客人兩次來菜不一樣（不可預測）、廚師薪水貴、偶爾失手。
~~~
​

判斷標準很直覺 — 「這個任務你能不能畫出完整的流程圖？」能畫完（每一步都明確）= workflow；畫不完（「下一步要做什麼」要 Claude 自己決定）= agent。
容易誤會的是「agent 比較先進、應該都用 agent」 — 剛好相反。Anthropic Cookbook 的建議：先試 workflow，寫不出來時才升級成 agent。Production 使用者要的是「穩」，不是「聰明」。
實務上 production 通常混用：外層 workflow 控成本 + 可測試，內層某個 box 是 agent 處理開放式 sub-task。例如一條內容生產線「研究 → 創作 → 編輯 → 歸檔」是外層 workflow，但每個階段內部（研究員自己決定搜什麼、寫手自己決定怎麼寫）是 agent。
