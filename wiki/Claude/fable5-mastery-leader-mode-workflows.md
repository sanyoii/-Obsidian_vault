## Fable 5 的五大超能力

| 能力 | 特徵 | 實例 |
|------|------|------|
| **Never loses the thread** | 長時間任務不失焦，數小時前設的約束依然有效 | 18,000 行代碼遷移在單一 3 小時執行中完成，無需監看 |
| **Sees like a person** | 電腦視覺超強，能看截圖重建頁面、讀取精確數據、發現缺陷 | 電腦視覺評分歷史最高；能自動修復模糊圖像再讀取 |
| **Delivers finished work** | 交付成品而非答案（報告、財務模型、計劃） | 專業分析師需要數天的工作在數小時內完成；獨立測試超越所有模型 |
| **Gets smarter from files** | 讀寫筆記資料夾自動變聰明，記憶複合成長 | 持續迭代中成長速度超過所有前代模型 |
| **Built to lead** | 天生適合當團隊經理，自然協調小 agent 團隊 | 比前代模型更容易派工與管理 worker 團隊 |

## Leader 模式：核心架構

**核心觀念**：不要把 Fable 當工人，要當經理。最聰明的模型值得花更多時間在規劃、檢查與決策，而非鍵盤敲擊。

| 角色 | 責任 | 工具/技能 |
|------|------|---------|
| **Fable（Leader）** | 規劃、委派、審核 | 使用 Matt Pocock's Skills Collection（github.com/mattpocock/skills）做規劃 |
| **Worker（Opus/Codex）** | 執行工作，平行分工 | 各自擁有一個 lane，同步執行 |
| **Verifier** | 檢查交付成果的品質 | 新鮮視角，必須確認所有 worker 宣稱 |
| **使用者** | 定期 check-in，方向調整 | 按時間表檢查進展，批准或要求修改 |

**為什麼這樣工作**：Fable 比任何前代模型更樂於派工平行 agent，且能在數小時內保持整個工作流在頭腦中。它幾乎不會忘記約束、檔案或三小時前做的決策——這正是領導者需要的，也是前代模型無法做到的。

**經濟優勢**：Worker 用便宜模型，只有貴的腦（Fable）在規劃、檢查和決策上花 token，實際使用者報告他們的 token 帳單反而下降。

## 建置你的 Worker 團隊

### 最小工作單位

每個 worker 是 `.claude/agents/` 下的一個小檔案：
- 名稱（Worker 的識別）
- 模型（Opus / Codex 等）
- 簡短職責描述（兩行）

Fable 讀這個資料夾後自動知道可以委派給誰。

### Verifier 最關鍵

新鮮的眼光能抓到作者看不到的問題。一旦某個階段通過檢查，就不需要在三個階段後重做。

### 三條鐵律

| 規則 | 內容 |
|------|------|
| **One worker, one lane** | 平行執行只在任務不共享檔案時進行 |
| **Workers run on Opus** | 勞力層用便宜模型，Fable 留在領導座位 |
| **Everything verified** | Worker 宣稱的每件事都由 verifier 確認，無自我評分 |

補充：若搭配 Codex，它可以像其他工具一樣被 Fable 驅動（如透過終端），遵循相同規則與 verifier 機制。

## 三大秘訣

### 秘訣 1：不要過度引導

**錯誤的舊思維**：step-by-step 指示、冗長規則清單、詳細腳本——這些都是為弱模型設計的鷹架。

**在 Fable 上反而有害**：冗長規則會限制一個規劃能力超過腳本的模型。為舊模型寫的 skill 檔會主動拖累 Fable 的輸出。

**正確做法**：只給三件事，然後閃開：
1. **目標** — 你想要什麼結果
2. **約束** — 必須遵守什麼條件
3. **原因** — 你要它做這個的原因（「我正在為〔誰〕準備這個，他們需要〔什麼〕，記住這個：〔要求〕」）

第三項（原因）比人們預期的更有威力。單靠要求遠不如帶著脈絡的要求。

**兩項絕對禁止**（會破壞模型）：
- ❌ **不要叫它 show/explain reasoning** → 可能觸發安全過濾，悄悄降級成弱模型，你卻以為在用 Fable
- ❌ **不要露出剩餘 token 預算** → 可見的倒數會讓它提早收工、建議新 session，而非完成工作

### 秘訣 2：保持 CLAUDE.md 輕量

CLAUDE.md 是 Fable 在 Claude Code 中每次任務前讀的駐留記憶。直覺上想填滿它——**抗拒這個衝動**。

輕檔案超越重檔案在這個模型上的表現。

**三個區段足夠**：
1. 這個專案是什麼（兩行）
2. 你實際使用的命令
3. 它一直在犯的錯誤

**行動**：今晚打開你的 CLAUDE.md，刪除一半。更短的檔案是升級。

### 秘訣 3：濫用 /goal 和 /loop

讓 Fable 從聊天變成工作機器——可以在你生活時執行幾小時。

#### /goal：可驗證的終點線

`/goal` 讓你寫一條終點線，小型評判模型在每個 turn 檢查是否通過。若未通過，Fable 自行繼續工作直到完成。

**秘訣：寫一條終點線它無法造假**：
- ✅ **要求可見證據**：「執行測試並貼輸出，必須通過」優於「讓測試通過」
- ✅ **加煞車**：「或在 20 個 turn 後停止」（沒有內建限制；沒有煞車的鬆散目標曾向某人開了 $960 帳單在單一 prompt）
- ✅ **一條誠實條款**：每個進度宣稱都必須指向實際執行結果——這單獨就幾乎消滅了造假的「完成」報告

#### /loop：排程重複執行

在排程上做同樣的事：每晚、每小時、每週一。

- 複習昨天的工作
- 更新你的文件
- 監看數據，在需要時起草警報

**組合能力**：有了 /goal 和 /loop，你可以讓 Fable 在某個東西上工作數小時——證據在終點等候，而非承諾。

## 一次完成真實專案：登陸頁範例

以下是用上述架構完成的完整流程（用你自己的專案代換示例）。

### Step 1：簡報（Brief）

一條訊息：

> 我在為〔產品〕啟動〔客群〕，他們需要一個登陸頁來捕捉信箱。
>
> 建置它：一頁，一個清晰承諾，一個儲存註冊的信箱表單，看起來高級。
>
> 約束：沒有我得維護的框架，在手機上運作，載入快速。
>
> 先規劃，然後委派，驗核每個階段。

### Step 2：計劃模式

按 **shift+tab** 進入 plan mode，讓它先規劃再動手。

若已安裝 Pocock skills 庫（github.com/mattpocock/skills），說「使用規劃 skills」——計劃會以階段、範圍與可測試性回來。

讀計劃，砍掉你不要的，核准。

### Step 3：團隊開始工作

Fable 派 builder 去做第一個階段，verifier 冷眼檢查，第二個階段只在通過後開始。

**你不在看著任何東西。** 整個過程自動進行。

### Step 4：終點線

設定目標並離開：

```
/goal 頁面在本地跑，表單存一個測試註冊，
用貼伺服器回應和手機寬度頁面截圖來證明，
或在 25 個 turn 後停止
```

### Step 5：早上檢查

回來看一份執行日誌，其中每個宣稱都有證據附著。

複查截圖，要求你想要的改變，上線。

**第一次需要一個晚上。** 第二次你會領悟到流程對所有你擱置的專案是相同的——這正是下一章的主題。

## 五個變現工作流

現在指向值得建置的東西。這五個是 Fable 出現可測量差異的地方：

| 工作流 | 描述 | 優勢 |
|------|------|------|
| **Giant codebase job** | 沒人自願接的多週遷移，分階段執行 | 每個階段由新評審檢查，進度宣稱綁著真實測試結果——多週的工作縮到數天 |
| **Deep research sprints** | 一個目標進、Worker 平行蒐集、Checker 攻擊每個主張、結構化檔案出來 | 回來一份資料檔，每個主張都活過攻擊，可用於啟動、內容或市場決策 |
| **Orchestrator setup** | 把上述領導者系統當永久安裝 | 一個座位的團隊規模輸出，架構比這個模型活得久——無論什麼來下一代都插入同一座位 |
| **Reference-driven frontend** | 網站口味的截圖資料夾、DevTools 抽出的真實 CSS、Fable 針對參考建置並在迴圈中對比輸出 | 你提供口味，它提供眼睛和手 |
| **Knowledge base building** | 最長執行：指向你領域所有值得知道的東西，讓它建立一個聯通的 vault | 文案編寫者用最好的銷售頁面做這個，設計師用設計系統，代理商用案例研究——vault 為你執行的每個未來模型寫簡報 |

**現狀**：每個都是一個月前的「有朝一日專案」。每個現在是「本週專案」。

## 完整設定一句話總結

- ✅ 把 Fable 當領導者執行：Pocock skills 做規劃，Opus/Codex worker 勞力，Fable 審核一切
- ✅ 不要過度引導：結果 + 約束 + 原因，刪掉鷹架
- ✅ 保持 CLAUDE.md 輕量：專案是什麼、命令、錯誤——三段
- ✅ 濫用 /goal 和 /loop：有證據的終點線，加煞車（防 $960 帳單），排程重複執行
- ✅ 指向五個變現工作流：遷移、研究、編排、前端、知識庫
