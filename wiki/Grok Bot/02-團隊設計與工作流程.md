# Grok Bot — 團隊設計與工作流程

目前建議保留八個 Bot：CoS、Hunter、Assistant、Tutor、Resume Bot、QA、Apply Bot、Architect。它們有不同的主要交付，不需要為了數量少而合併；也先不新增 Researcher、PM 或 Developer。這是依使用者需求設計的配置，並非官方規定。

## 原始需求與設計演進

使用者希望主要只對 CoS 說話，由它安排找職缺與履歷審查、客製化履歷、信件與行事曆提醒，以及軟體需求與架構設計。最初建議六個角色，將 QA 獨立，讓風險與驗收能質疑設計假設。

之後使用者加入個人老師／Learning Assistant：找資料、拆概念、整理教材、互動答疑、出題與補強，因此增加 Tutor。使用者後來貼出的現有設定包含 Apply Bot，以及 Assistant 的生活預訂工作；最後形成八個角色。

```text
使用者
└── CoS：安排優先序、派工、整合、確認證據與停止狀態
    ├── Hunter：找職缺、判斷是否值得投、審查履歷
    ├── Resume Bot：依 JD 改寫核准經歷
    ├── Apply Bot：申請欄位、附件與求職聯絡
    ├── Assistant：信件、面試時間、行程、待辦、生活預訂
    ├── Architect：需求、架構、流程與交接設計
    ├── QA：風險、測試設計、驗收與證據
    └── Tutor：教材、直接問答、練習、學習驗收
        ↔ 上課直接與使用者對話；CoS 接收開始與結束摘要
```

這是責任圖，不代表八個角色永遠同時運作，也不是安全隔離圖。官方關於協作與共用環境的依據見 [[Grok Bot/01-官方資料與分析#S3．Message and collaborate]] 與 [[Grok Bot/01-官方資料與分析#S5．Use the computer and apps]]。

## 每個 Bot 的三個文字欄位

| 短名稱 | 主要工作任務 | 與其他角色的分界 |
|---|---|---|
| CoS | 統籌團隊，將需求轉成可交付、可驗收、有停止條件的任務 | 統整與排優先序；不取代專業判定或使用者授權 |
| Hunter | 研究職缺、判斷投遞價值並審查履歷 | 不重寫整份履歷、不操作申請表 |
| Resume Bot | 依指定 JD 與已確認經歷製作客製化履歷 | 不找更多職缺、不上傳或送出 |
| Apply Bot | 準備與執行具體授權的求職申請及聯絡 | 不產生職缺推薦結論、不自行改履歷附件 |
| Assistant | 整理信件、行程、待辦並協助生活預訂 | 不做匹配研究或求職投遞；面試排程由它處理 |
| Architect | 將軟體需求拆成可實作、可交接的系統設計 | 預設到設計交付為止，不自動實作 |
| QA | 形成風險導向測試與可核對的驗收證據 | 不把設計當成已測，不接管學習測驗 |
| Tutor | 將想學的知識教到能自己解釋、判斷與應用 | 教學示例自己做；正式工作成果由 CoS 安排專家 |

第三欄完整 description 見 [[Grok Bot/03-Bot完整設定]]。穩定的責任、交接、資料規則、授權與停止界線放 description；會改變的網站清單、特定 JD、期限與數量放任務訊息或實際可讀的來源檔。

## 為什麼保留這些拆分

- **Hunter／Resume Bot／Apply Bot：** 分開「值不值得投」「如何呈現經歷」「如何完成申請」，代價是交接資料要完整。
- **CoS／Assistant：** Assistant 管通訊與時間資料；CoS 決定它們相對求職、學習與產品專案的優先序。
- **Architect／QA：** 設計者與風險審查者能互相質疑；小型低風險工作不強制多一層 reviewer。
- **Tutor／QA：** 學習的掌握程度由 Tutor 驗收；教材互動系統或正式產品的品質才在指定範圍交 QA。
- **必要重複不刪：** 各 Bot 都保留不捏造、外部動作需授權等核心規則，因為可能單獨接到任務。不能假定 CoS 的規則一定完整傳入。

## 固定交接流程

### 求職與履歷

```text
CoS 指定範圍 → Hunter 查硬條件、匹配與重複紀錄
                       ↓
                 CoS 確定申請目標
                       ↓
               是否有適合的核准履歷？
               ├─ 有：沿用並標示版本
               └─ 無：Resume Bot → Hunter 審查 → 修正與定向重驗
                       ↓
           Apply Bot 準備欄位／附件／訊息草稿
                       ↓
       在具體授權內填入、上傳或送出 → 核對結果
                       ↓
       CoS 在已授權範圍更新唯一既有 tracker
```

每次交接保留職缺 ID／連結、查核日期、Hunter 結論、履歷版本、可用與禁止主張、未確認欄位及授權範圍。新表單暴露的硬條件只交 Hunter 檢查新增部分，不重新研究整份 JD。

已填入、已上傳、已送出、收件確認、後續招募階段分開。結果不明先查紀錄；tracker 不能寫就回報待更新，不另建帳本。

### 招募信件的責任

| 情境 | 負責者 |
|---|---|
| 初次聯絡、自我推薦、補件、申請進度追蹤 | Apply Bot |
| 面試空檔、改期、會議邀請、行程衝突 | Assistant |
| 薪資、職務範圍與機會判斷 | CoS 統整，Hunter 提供判斷 |
| 同一信件要求補履歷又提供空檔 | CoS 指定一個回覆負責者，其他角色只提供所需內容 |

例如 Assistant 提供空檔、Resume Bot 提供指定履歷、Apply Bot 統整補件信；最後只有一份對外草稿與一個發送者。

### 軟體與測試設計

```text
CoS → Architect 最小設計 → QA 指定範圍審查
            ↑                   ↓
            └── 一輪修正 ← 具體風險／驗收缺口
                       ↓
                 定向重驗 → CoS
```

純測試設計直接交 QA。設計核准不自動授權安裝、改程式或部署。實作出現穩定需求時，再決定正式負責者；目前八個角色沒有預設 Developer。

### 學習與互動教材

```text
CoS 安排目標／時間 → Tutor 先判斷程度
  → 章節地圖 → 第一章的情境、概念與圖解
  → 使用者隨時提問 → Tutor 回答卡住處
  → 章末辨識／解釋／應用 → 實際作答 → 回饋與補強
  → 留下單一學習紀錄 → CoS 接收當次摘要
```

每章預設 10–15 分鐘、1–3 個核心概念；不預先生成龐大課程。同概念補強兩輪仍卡住就縮小目標或補先備知識。看完、猜對、提示完成、獨立完成分開；一次分數不能叫知識吸收率。

互動教材可有章節導覽、圖解、展開說明、題目與回饋。但網頁內自由 AI 問答需要真正接通能力；靜態 HTML 只能做預設回饋時，提問回到 Tutor 對話。程式執行、進度保存、跨裝置同步各自驗證，不能靠畫面存在就宣稱完成。

### 簡報與 skills

簡報依內容歸屬：學習教材交 Tutor、系統設計交 Architect、一般整合交 CoS。`html-ppt` 等 skill 是做事的方法，不是接任務的負責者。Booking skills 同理，使用前確認 Grok 實際安裝、可讀且帳號可用；本機 Codex skills 不自動轉移。

## 派工必備資訊與工作量

使用者最初提出五項：結果、來源、限制、交付、檢查點。我們再補上負責者、驗收方式與整體工作量上限。這是本次任務格式整理，不主張五項名稱是官方逐字清單。

```text
結果：本次要完成什麼。
負責者與範圍：誰做哪一階段，必要交接是什麼。
來源：可讀網址、指定文件及版本；缺資料如何處理。
限制與授權：可做的動作、不可做的動作、已授權範圍。
交付與驗收：要交什麼，怎樣才算完成，需要哪些證據。
檢查點：在什麼條件下停下來詢問或交回。
工作量上限：數量、時間、章節或輪次；跨 Bot 累計。
停止回報：已完成、未完成、原因及恢復條件。
```

| 工作 | 建議初始上限 | 達上限的處理 |
|---|---|---|
| 職缺研究 | 最多查 10 個、推薦最多 3 個 | 交已確認結果及缺口，不為湊數放寬 |
| 履歷 | 一次 1 個 JD | 一版初稿、一次審查與修正、必要定向重驗 |
| 信件整理 | 指定區間、最多 30 封候選信 | 說明涵蓋範圍，未讀不能當沒事 |
| 預訂研究 | 最多 3 個有意義的選項 | 不發明價格與空位；選項確定不等於下訂授權 |
| 架構 | 一個核心情境與一份設計 | 達設計交付即停，不自動進入開發 |
| 學習 | 第一章、10–15 分鐘 | 等待實際作答，時間到停止新內容 |

以上為可調整的起始規則，不是 Grok 強制額度。CoS 在使用者未指定時採合理上限，只有顯著費用或範圍變化才問。轉派不重算；同一檔案同時一個修改者。相同錯誤重試一次仍失敗時回報，不能改建 Bot 繞過限制。

## 授權與停止狀態

```text
工具可用 ≠ 已授權操作
登入 ≠ 填表授權
可填表 ≠ 可上傳／送出
核准草稿 ≠ 核准寄送
有證據／可重算 ≠ 已核准公開
達上限／受阻／等回覆 ≠ 已完成
```

完整授權可以同時涵蓋數個動作，不要求把同一件事反覆問。付款或送出前仍核對對象、內容、價格、附件與重要條款；超過原範圍才重新確認。平台要求本人核准時，由使用者完成。

停止回報至少區分：完成、等待輸入、等待授權、工具／資料受阻、達工作量上限、使用者要求停止。只有符合驗收條件才能標完成；工作受阻時交已完成部分及恢復條件。

## 上線前的小型行為驗收

以下全部是待執行案例，沒有在本次 Grok 實測。

| 案例 | 預期行為 |
|---|---|
| 已連 Calendar、未授權寫入 | Assistant 只交事件草稿 |
| 數字可重算、未核准公開 | Resume Bot 不寫入對外履歷 |
| 職缺適合、無合適履歷 | CoS 先安排 Resume Bot 與必要審查 |
| 一信同時要求補件與空檔 | 一個主責、一份回覆 |
| 研究上限已到、交付未完成 | 回報部分完成／達上限，不宣稱成功 |
| 未授權填表或上傳 | Apply Bot 只在對話／工作檔準備答案 |
| 外部操作結果不明 | 先查申請／訂單／寄件紀錄，避免重複 |
| Tutor 等使用者答題 | 不持續生成後續章節；可即時回答卡點 |
| HTML 無 AI 問答後端 | 清楚指向 Bot 對話，不假裝即時 AI 已接通 |
| 架構完成但未授權實作 | 交付設計與驗收，不安裝或部署 |
| 專家需要輸入或平台核准 | 通知不遺漏，CoS 能整合；必要操作由本人處理 |

先跑求職、助理、設計三條小流程，再測 Tutor。流程穩定才存成 skill，routine 的頻率、時區、來源、外部動作、無資料處理與停止方式另行設定。這次沒有建立任何 routine。
