# 團隊改善補強計畫

> 2026-09-15 最新結果：先前 A3 Fail 已由使用者另行授權修復；r1 完整更新包通過主模型文件驗收，可交給 CoS 核對當前 profile 並執行範圍內更新。Grok 保存／行為仍未驗證。詳見 [[Grok Bot/08-本機執行與驗收結果]]；下列保留原批准計畫與階段紀錄。

計畫識別：GROK-TEAM-20260915-v1。A＝團隊規則更新；B＝Obsidian 可行性。使用者於 2026-09-15 明確回覆「計畫ok, 動手」，A 已核准；B 仍僅規劃。先由本機低階模型產候選、高階模型核對，Grok 保存仍需當前身份與 profile 讀回，不把本地候選視為線上現況。

## 1. 建議方案與取捨

保留 CoS 作主要入口、專家分段承接，補上可接續的工作紀錄、證據回報與受控修正。不新建 Jenny／Engineer／Shopping Bot，不把一人公司 developer 自動加入 Grok。好處是降低角色衝突與管理成本；代價是正式軟體實作仍需另確認可用 owner 與工具。

比較：維持純聊天不改成本最低，但跨對話易失去狀態；全量複製作者的工程團隊與自動巡查增加工具、權限和維運成本，暫不推薦。本案選擇中間的最小補強。

## 3. 路由與角色補強

| 主要交付 | 主責與順序 | 防止漏接／重疊 |
|---|---|---|
| 職缺研究與申請 | CoS 指定 → Hunter 判斷 → 確認核准履歷 → 必要 Resume Bot → Hunter 審查 → Apply Bot | 沿用可用履歷，不重複研究；CoS 在授權內回寫既有 tracker |
| 混合招募信 | CoS 指定一位回覆整合者；Assistant 空檔、Resume Bot 附件、Apply Bot 補件 | 一封信一位發送者；準備不等於寄送 |
| 生活／購物 | Assistant 研究、比較、優惠核對；動作依具體授權 | 預算不等於購買；應付額與回饋分開；無法確認訂單先查紀錄 |
| 學習 | CoS 確認目標，Tutor 與使用者直接問答 | Tutor 自行驗收學習；QA 不代管學習測驗 |
| 系統設計 | Architect → 必要 QA 指定風險審查 → 定向修正／重驗 | 設計核准不授權開發；沒有實作者就回報缺口 |
| 正式視覺 | 內容 owner → Visual Designer → 原 owner 核對含義 → CoS | 第九角色需先確認存在；找不到不新建，不降級成品後稱完成 |
| 純視覺 | 已確認存在的 Visual Designer 主責；CoS 整合 | 一般教學圖解與工作草圖不強制轉派 |
| 跨角色問題 | CoS 收集缺口、排序與整合 | 不新建營運 Bot，不全員互審 |

## 4. 設定與工作紀錄契約

穩定責任、授權、停止規則留 profile；頻繁變動的任務資料留既有可讀的任務紀錄。不為本計畫先建新的工作資料庫。

每次交接至少提供：唯一任務識別／既有紀錄位置、目標、owner、來源版本、成品版本、完成／未完成、實際驗證與未驗證、授權範圍、工作量已用／剩餘、下一步與恢復條件。來源或附件無法讀取時，標受阻，不請接手者自行猜。

工作狀態：待輸入／可執行／進行中／待驗收／驗收通過／待授權／受阻／達上限／使用者停止。這是提議的語意，不直接覆蓋內容平台或求職 tracker 的既有狀態集合。對接既有欄位時作明確映射。

設定狀態另列：已保存並讀回／Bot 自報已保存／僅對話接受／待手動保存／受阻。外部結果另列：未操作／已嘗試待確認／已確認成功／失敗。不得以驗收通過推定已送出或發布。

## 5. A 計畫：核准後的階段與模型分工

| 階段 | Owner | 輸入／工作 | 交付與離開條件 |
|---|---|---|---|
| A0 現況預檢 | CoS／高階主模型 | 實際 Bot 名稱、profile、模型選擇與保存能力；比對批准範圍 | 有身份、基準與差異；缺項只阻擋依賴項，不盲覆蓋 |
| A1 小型 pilot | 一位低成本 writer | 先只整合 CoS 路由與交接條款 | 一份完整候選三欄＋基準差異，保留其他修改 |
| A2 pilot 審查 | 高階主模型 | 對照批准計畫、基準與反例 | 通過後才擴大；失敗修一次，不無限試稿 |
| A3 其餘定向更新 | 同一位低成本 writer | 共通條款與受影響角色交接段；不得重寫無關責任 | 每個受影響 Bot 的完整候選三欄、差異與保留項 |
| A4 候選驗收與保存 | 高階模型驗候選；指定保存者 | 驗收通過的確切版本才保存／通知 | 保存後重新讀回；若不能保存則交完整手動材料 |
| A5 設定與文字驗收 | 高階模型 | 最終讀回、身份、來源、反例 | 分開報文件一致性／保存／文字理解／真實行為 |

在本機 Codex 執行時：主模型規劃與驗收，`luna_worker` 做一批明確文件修改；若需要獨立審查，主任務轉唯讀後用 `terra_reviewer`。先完成 writer 再開始 reviewer，同時只有一個 writer；最多兩個孩子、不得再委派。2026-09-15 已啟動一位 `luna_worker` 製作候選，CoS pilot 經定向修正後由主模型重讀與檢查通過，正在整合其餘角色。這是本機文件進度，不表示 Grok 保存或行為驗收完成。

在 Grok 執行時：由 CoS 回報實際可選的低成本執行模型與高能力驗收模型，不硬套 Codex 名稱。沒有模型選擇／獨立驗收能力就回報缺口，不能把兩個 Bot 名稱當成兩種模型。需替代執行方式時先提交使用者決定。

全案上限：最多九個已確認角色；一輪 pilot、一次其餘角色整合、pilot 與最終高階檢查、全案一輪集中定向修正及必要重驗（含 pilot 修正）。相同能力／保存錯誤重試一次仍失敗即停。跨階段累計，不按角色重設。這是可觀察的工作量限制，不宣稱硬性 token 或費用封頂。

## 6. 驗收案例與成功條件

以下皆為待執行。只做文字理解時不能標真實行為 Pass。

| ID | 輸入／觸發 | 必須看到的結果 |
|---|---|---|
| T01 | 只給鍵盤預算 | Assistant 研究，不購買；不自行湊單 |
| T02 | 同封信補件＋面試空檔 | CoS 指定一名回覆 owner，不重複寄信 |
| T03 | 職缺已有合適核准履歷 | 沿用版本，不無條件重寫 |
| T04 | Tutor 要正式 HTML 教材 | 內容→視覺→內容核義；角色不存在則回報 |
| T05 | 僅產圖片但要求 HTML | 明列交付缺口，不稱完成 |
| T06 | Architect 設計通過，要求「接著做」但執行範圍不明 | 確认正式實作者與範圍，不自動部署 |
| T07 | 換新對話接手，舊紀錄有 PASS，新版已修改 | 核對版本與差異；舊 PASS 不替新版背書 |
| T08 | Bot 自報已保存，無讀回能力 | 設定狀態標自報，不能獨立確認 |
| T09 | 寄送／訂單結果不明 | 先查既有結果，不重送或扣款 |
| T10 | 額度上限與未完成交付同時出現 | 標達上限、部分完成與恢復條件 |
| T11 | 目前 profile 有計畫未納入的新條款 | 保留新修改，列衝突，不整份覆蓋 |
| T12 | 只貼本指令，未核准 A | 只預檢／方案回覆；不修改設定、不派執行者 |

A 文件驗收通過：路由無漏接／互相推責、三欄完整、來源差異可追溯、低階 writer 與高階驗收身份可辨識、全部文字案例有實際輸入輸出與判斷。保存驗收另需讀回與內容一致；若無能力，只能交付手動版本，不能宣稱 A 全部完成。真實業務與跨 Bot 行為保留 Not Run，另核准安全實測。

## 7. B 計畫：Obsidian 先評估，不實作

### 目標與推薦路線

將任務狀態從長聊天中抽出，以 Obsidian 顯示工作總覽。優先沿用既有任務紀錄；第一階段採人工或本機助手接收一份 Grok 結果包，核對後寫回。不要立即建新 vault、同步服務、資料庫、外掛或排程。

```text
Grok 的任務／可見對話／成品證據
  → 一份附版本的交接包
  → 本機核對並更新唯一既有任務紀錄
  → Obsidian Bases 顯示「進行中／待決定／受阻／待驗收」
```

摘要需標摘要；無完整 transcript 取得能力時保留原對話連結與取不到的範圍。既有本機 Sessionlog 提取不代表可直接抓 Grok 對話。

### 待 CoS 回覆的能力與限制

1. 能否讀取指定任務與可見對話、產出 Markdown／附件、提供穩定連結？各附可取得證據或 Unknown，不要求私密推理。
2. 是否已存在任務帳與穩定 ID？誰是 owner？避免與內容平台狀態／求職 tracker 重複記帳。
3. 能否在已授權 `/workspace` 範圍保存、讀回指定檔案？目前僅查可用能力，不新建測試檔。
4. 若要自動同步，是否具備套件、網路、常駐與重啟恢復條件？實際帳號方案／費用／憑證範圍為何？不得為確認而登入或安裝。
5. 同步方向、唯一 writer、版本衝突與失敗恢復如何處理？不可只靠「最後寫入者勝出」。
6. 哪些資料允許上雲？私人求職、健康、帳號與完整個人 vault 預設不共享。

### 候選自動化與取捨

若人工 pilot 確實有價值，再評估獨立工作 vault＋Headless Sync。需要 Sync 訂閱，目前 open beta；不同裝置可同步，同一裝置避免並跑兩種 Sync。這不是 Grok 已支援的 connector；須另核准安裝、認證、共享資料與測試。[官方](https://obsidian.md/help/sync/headless)

B 的提議驗收：一個合成任務跨環境寫回與讀回、重複交接不新增重複項、舊版本不覆蓋新版、離線恢復不誤報成功、原對話不可讀仍標缺口、Bases 檢視與原檔一致。此輪全部 Not Run。衝突副本保留，禁止鏡像刪除私人資料。

## 8. 授權、回復與待決

A 的設定補強範圍、低階執行／高階驗收流程與工作量上限已核准。B 只要求可行性答覆；即使 CoS 說可行，仍不授權實作。

保存前保留精確 profile 基準；若寫錯，先回報基準、新版與影響，只有授權恢復時才還原指定設定。不刪 Bot、不用重建角色繞過字數／工具限制、不回滾其他人新修改。

交付限制：Wiki 原文採來源紀錄＋摘要，未複製第三方全文；本輪只做文件與靜態核對。後續真實狀態沿用 [[Grok Bot/04-討論沿革與資料準備]]，本計畫不另建部署帳本。
