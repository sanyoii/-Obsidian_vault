# 一人軟體測試公司 — 原始架構規劃

> 本頁保存 2026-09-09 對話中的完整第一版規劃。除移除系統 memory citation 標記外，正文不改寫。這是規劃存檔，不是實作或對外服務承諾。

> 後續檢視：[[一人軟體測試公司 — 顧問團架構審議與角色分工]]。

建議做成 **「你擔任負責人與最終 QA 決策者，AI 員工負責分析、測試準備、執行協作與營運」的一人軟體測試公司**。

第一版以 **Web／SaaS／API 測試服務**為主，Mobile、效能、安全、Web3 與 AI 產品測試依案件啟用。這樣能保留完整公司架構，又不會一開始就承諾所有專業服務。

我已查看 [原始 ZIP](</D:/Codex/AI-一人公司/AI-One-Person-Company-2026.08.29.1.zip>) 的 README、SCHEMA、員工卡、資料地圖與流程。包內有 **12 張員工卡、3 張 pipeline 卡、48 份知識文件**；以下沿用其資料組織方式，重新設計測試公司的工作內容。**這是架構提案，尚未建檔、安裝或連接服務。**

**一、公司整體架構**

```text
你｜公司負責人、客戶窗口、最終品質判斷
│
├─ 營運中樞
│  ├─ 營運幕僚
│  ├─ 業務與方案顧問
│  ├─ 客戶成功專員
│  └─ 財務管理員
│
├─ 品質規劃
│  ├─ 測試策略師
│  └─ 需求與測試分析師
│
├─ 測試交付
│  ├─ 探索與體驗測試員
│  ├─ 自動化測試工程師
│  ├─ API 與資料測試工程師
│  └─ 測試環境與 CI 工程師
│
├─ 專項測試｜按案件啟用
│  ├─ 效能與可靠性測試員
│  └─ 安全與隱私測試員
│
├─ 交付覆核
│  └─ 品質證據審查員
│
└─ 公司資產與成長
   ├─ 知識管理員
   └─ 技術內容與品牌專員
```

這 **15 位是可交辦的角色**，不代表同時啟動 15 個 Agent。日常由營運幕僚辨識任務，再調用必要能力；你負責接案承諾、關鍵判斷、客戶交付核准。

完整關係沿用原版：

```text
公司目標
   ↓
客戶／專案 → 工作流程 → 員工.能力
                           ├─ 方法：怎麼做
                           ├─ 知識：怎麼判斷
                           ├─ 工具：用什麼執行
                           └─ 連接：讀寫哪個系統
                                  ↓
                           測試與執行證據
                                  ↓
                           覆核 → 核准 → 交付
```

**二、所有員工與能力**

能力使用穩定 ID，例如 `test-analyst.design`，讓流程能直接引用。

| 員工／ID | 能力清單 | 主要交付物 |
|---|---|---|
| **營運幕僚** `chief-of-staff` | `intake` 任務分流；`context` 組裝專案脈絡；`plan` 排工作；`capacity` 產能與期限管理；`status` 現況對帳 | 今日工作、案件進度、阻塞與待決事項 |
| **業務與方案顧問** `sales-consultant` | `qualify` 案件適配；`discover` 需求訪談；`scope` 服務範圍；`estimate` 工時與成本估算；`proposal` 提案 | 需求摘要、範圍書、估算與提案草稿 |
| **客戶成功專員** `client-success` | `onboard` 客戶導入；`update` 進度溝通；`change` 變更管理；`acceptance` 驗收協調；`follow-up` 售後追蹤 | 導入清單、週報、變更單、驗收紀錄 |
| **財務管理員** `bookkeeper` | `quote` 報價；`billing` 請款草稿；`reconcile` 對帳；`receivables` 未收款追蹤；`margin` 案件成本分析 | 報價單、收支、未收款、案件損益 |
| **測試策略師** `qa-strategist` | `risk` 風險分析；`strategy` 測試策略；`coverage` 覆蓋配置；`entry-exit` 進出場條件；`release-advice` 發版建議 | 風險表、測試計畫、品質門檻 |
| **需求與測試分析師** `test-analyst` | `review` 需求審查；`acceptance` 驗收條件；`model` 狀態與規則建模；`design` 案例設計；`trace` 需求追溯 | 問題清單、驗收條件、測試案例、追溯表 |
| **探索與體驗測試員** `exploratory-tester` | `charter` 探索任務；`explore` 流程探索；`compatibility` 相容性；`accessibility` 無障礙檢查；`reproduce` 缺陷重現 | 探索筆記、操作證據、缺陷草稿 |
| **自動化測試工程師** `automation-engineer` | `select` 自動化選案；`implement` 腳本實作；`regression` 回歸套件；`diagnose` 失敗分析；`stabilize` 不穩定測試治理 | 測試程式、執行設定、維護紀錄 |
| **API 與資料測試工程師** `api-data-tester` | `contract` 契約驗證；`authorization` 權限情境；`workflow` 跨服務流程；`consistency` 資料一致性；`resilience` 重試與冪等 | API 測試、資料核對結果、異常證據 |
| **測試環境與 CI 工程師** `test-platform` | `environment` 環境準備；`fixtures` 測試資料；`ci` 執行管線；`artifacts` 證據保存；`diagnose` 環境問題診斷 | 環境清單、資料準備方式、CI 設定 |
| **效能與可靠性測試員** `performance-tester` | `workload` 負載模型；`threshold` 門檻設計；`load` 負載執行；`soak` 長時間測試；`analyze` 結果分析 | 效能計畫、延遲與錯誤率報告 |
| **安全與隱私測試員** `security-tester` | `scope` 授權範圍核對；`threat` 風險建模；`baseline` 基線檢查；`access-control` 權限驗證；`privacy` 敏感資料檢查 | 安全發現、重現證據、修正驗證 |
| **品質證據審查員** `evidence-reviewer` | `audit` 證據完整性；`reproduce` 重現覆核；`coverage-gap` 缺口審查；`report` 報告查核；`gate` 交付門檻 | 證據審查結果、交付通過／退回清單 |
| **知識管理員** `librarian` | `ingest` 資料消化；`distill` 經驗萃取；`template` 範本維護；`audit` 過期與引用檢查；`sanitize` 客戶資料去識別 | 可重用知識、範本、來源與版本紀錄 |
| **技術內容與品牌專員** `technical-marketer` | `position` 服務定位；`case-study` 案例包裝；`article` 技術文章；`portfolio` 作品集；`distribution` 發布草稿 | 服務頁、匿名案例、展示報告、技術內容 |

**分工邊界：**測試策略師決定測哪些風險；測試員產生結果；證據審查員检查結論是否有依據。相同 AI 換角色自查，仍須標示為自查，不能稱為獨立驗證。

**三、知識庫**

沿用原版「一份知識對應一個可執行任務」，避免只有名詞百科。

| 知識分組 | 建議文件主題 | 主要使用員工 |
|---|---|---|
| **營運** | 案件適配、產能估算、優先序、風險升級 | 幕僚、業務 |
| **商務** | 需求訪談、服務範圍、報價估算、範圍變更、驗收與交接 | 業務、客戶成功、財務 |
| **產品** | 使用者旅程、業務規則、驗收條件、需求歧義 | 需求分析師 |
| **測試** | 風險排序、等價類與邊界值、決策表、狀態轉移、組合測試、探索測試 | 策略師、分析師、探索測試員 |
| **Web** | 瀏覽器差異、響應式、表單、Session、檔案上傳下載、無障礙人工檢查 | 探索與自動化測試員 |
| **API** | HTTP 契約、身分與權限、分頁、冪等、重試、限流、Webhook | API 測試員 |
| **資料** | 測試資料設計、資料遮罩、一致性、交易與對帳、時間與時區 | API 測試員、環境工程師 |
| **自動化** | 選案準則、Locator、隔離與清理、等待策略、斷言設計、不穩定測試 | 自動化工程師 |
| **環境** | 環境就緒、版本識別、CI 分層執行、證據保存、憑證處理 | 環境工程師 |
| **效能** | 負載模型、延遲分位數、錯誤率、資源飽和、結果可比性 | 效能測試員 |
| **安全** | 測試授權、存取控制、敏感資料、掃描結果判讀、安全重測 | 安全測試員 |
| **品質** | 缺陷分級、重現標準、追溯完整性、證據有效性、發版建議 | 全體測試角色、審查員 |
| **財務** | 工時與工具成本、收款節點、對帳、案件毛利 | 財務 |
| **品牌** | 證據導向寫作、案例去識別、成果宣稱邊界、客戶發布授權 | 品牌專員 |
| **領域選配** | Mobile 生命週期；Web3 簽名與交易狀態；AI 回答評估與工具權限 | 按案件綁定 |

每份方法型知識保留原版五段：

```text
用途 → 必要輸入 → 判斷規則 → 操作方法與範例 → 自檢與交接
```

例如「測試－邊界值設計」必須寫清楚：

- 沒有上下限規格時，先列待確認事項。
- 區分有效邊界、越界、空值與型別錯誤。
- 預期結果須連回規格或已確認規則。
- 不能把目前系統的行為直接當成正確答案。

**四、工具架構**

**起步建議以一套主要測試技術為核心，額外工具按案件加入。**下列是候選工具與用途，並非本機已安裝清單。

| 工具層 | 建議配置 | 使用方式 |
|---|---|---|
| 公司資料 | Markdown vault＋Git | 保存員工、方法、知識、專案與變更歷史 |
| AI 工作引擎 | 現有 Codex；其他引擎選配 | 分析、起草、實作與結果整理；執行結論仍靠工具證據 |
| Web 自動化 | Playwright | UI 測試、回歸與操作證據 |
| API 自動化 | 優先使用 Playwright API testing | 與 Web 測試共用技術；客戶既有 Collection 再評估沿用 |
| 人工調查 | 瀏覽器 DevTools、截圖／錄影、HTTP 請求工具 | 查 Network、Console、人工重現 |
| 資料驗證 | SQL 查詢工具＋專案既有測試框架 | 核對測試環境資料與業務結果 |
| CI | 客戶既有 CI；新案可評估 GitHub Actions | 按事件、手動或排程執行 |
| 報告 | 原生測試報告＋公司交付範本 | 執行細節與商務摘要各有用途 |
| 效能選配 | k6 | 依事前門檻判斷負載結果 |
| 安全選配 | ZAP | 授權範圍內的基線檢查與人工判讀 |
| 無障礙選配 | axe-core＋人工鍵盤／讀屏檢查 | 自動檢查後補人工測試 |
| Mobile 選配 | Appium＋約定裝置 | 有 Mobile 案件才建立對應環境 |

已核對官方文件：Playwright 提供 [API testing](https://playwright.dev/docs/api-testing) 與 [Trace Viewer](https://playwright.dev/docs/trace-viewer)；GitHub Actions 支援事件、手動及排程 [workflows](https://docs.github.com/en/actions/concepts/workflows-and-actions/workflows)。k6 可用 [thresholds](https://grafana.com/docs/k6/latest/using-k6/thresholds/) 判斷結果；[ZAP Baseline](https://www.zaproxy.org/docs/docker/baseline-scan/) 與 [axe 自動檢查](https://playwright.dev/docs/accessibility-testing) 都需要清楚交代覆蓋限制。

**五、連接與資料流**

「工具」是執行能力；「連接」則是它被授權存取的客戶、專案與環境。

| 連接 | 讀取內容 | 核准後可能寫入的內容 | 主要使用角色 |
|---|---|---|---|
| GitHub／GitLab | 程式碼、diff、版本、CI 結果 | 測試程式、PR、Issue | 分析、自動化、環境、審查 |
| Jira／Linear／客戶 Issue 系統 | 需求、驗收條件、缺陷狀態 | 缺陷單、重測結果 | 分析、測試、客戶成功 |
| Notion／Confluence／Drive | PRD、規格、會議紀錄 | 核准報告與交付文件 | 幕僚、分析、客戶成功 |
| 測試網站／API | 測試目標與回應 | 約定測試帳號中的測試操作 | 測試執行角色 |
| 測試資料庫 | 核准資料範圍 | 必要且核准的測試資料準備 | API、環境 |
| CI／Artifact 儲存 | Job、log、trace、附件 | 測試證據與執行摘要 | 環境、審查 |
| 錯誤與監控系統 | 錯誤事件、效能、相關 log | 原則上先以讀取為主 | API、效能、安全 |
| Email／Slack／Teams | 客戶提供的需求與回覆 | 核准的報告、進度與問題 | 客戶成功 |
| 財務／收款系統 | 請款與入帳資料 | 核准的請款紀錄 | 財務 |

每條連接登記：

```text
客戶／專案、用途、目標環境、讀寫權限、
憑證所在位置的指標、驗證日期、保留期限、撤銷方式
```

狀態分開記為「未設定／待授權／已連線未實測／已驗證／失效」。**設定存在不等於連接可用，連接可用也不等於可操作所有專案。**

**六、工作流程**

公司需要六條產線。產線只負責編排能力，不另假裝成員工。

| 產線 | 主要步驟 | 完成條件 |
|---|---|---|
| **接案產線** `engagement-pipeline` | 詢問 → 適配 → 訪談 → 範圍與估算 → 提案 → 核准 → 導入 | 範圍、環境、交付物、期限、驗收與授權已確認 |
| **測試交付產線** `qa-pipeline` | 脈絡 → 風險 → 設計 → 就緒檢查 → 執行 → 缺陷 → 重測 → 覆核 → 交付 | 約定範圍有結果與證據，未測與風險明確 |
| **持續回歸產線** `regression-pipeline` | 版本變更 → 影響分析 → 選案 → 執行 → 失敗分類 → 重測 → 彙整 | 結果綁定本次版本，失敗原因與阻塞有去向 |
| **專項測試產線** `specialist-pipeline` | 確認專項 → 專用計畫 → 環境與授權 → 執行 → 分析 → 重測 | 完成專項門檻與明確限制說明 |
| **結案營運產線** `closeout-pipeline` | 客戶驗收 → 交接 → 請款 → 對帳 → 權限與資料收尾 → 回顧 | 交付、款項、資料及權限責任都有紀錄 |
| **知識與成長產線** `learning-pipeline` | 結案資料 → 去識別 → 萃取 → 覆核 → 知識／範本 → 核准案例 | 內部可重用；公開材料另有客戶授權 |

核心測試產線如下：

```text
需求／版本／客戶目標
        ↓
[脈絡與範圍]
  缺規格 → 待確認；只推進不受影響的部分
        ↓
[風險與測試設計]
  需求 → 風險 → 驗收條件 → 案例／探索任務
        ↓
[環境與資料就緒]
  未就緒 → Blocked，指定解除條件
        ↓
[按範圍選擇執行]
  ├─ 探索／體驗
  ├─ Web／API／資料
  └─ 效能／安全／Mobile 等專項
        ↓
[結果分類]
  ├─ Pass → 保存證據
  ├─ Fail → 重現 → 缺陷 → 客戶開發修正 → 重測
  ├─ Blocked → 環境／資料／權限問題
  └─ Skipped／Not Run → 原因與剩餘風險
        ↓
[證據覆核]
  缺證據／結論過度 → 退回補測或修正報告
        ↓
[你核准交付] → [客戶確認驗收／決定是否發版]
```

缺陷修正預設由客戶開發團隊負責；代修程式應另列服務範圍。

測試程式放在專案指定 Git repo；大型 trace、影片與 log 放在指定證據儲存。Vault 保存識別資訊與連結，避免複製成第二份程式庫或附件庫。

若客戶已用 Jira 管缺陷，Jira 就是缺陷狀態來源；本地只存對應 ID 與交付所需快照，不能兩邊各維護一套現況。

**八、最重要的資料連接：證據鏈**

```text
專案 → 版本
         ↓
需求 REQ → 風險 RISK → 測試 TC → 執行 RUN
                                     ├─ 證據 ART
                                     └─ 缺陷 BUG → 重測 RUN
                                                   ↓
                                               交付報告
```

| 資料 | 最低必要內容 |
|---|---|
| 專案卡 | 客戶、產品、聯絡窗口、服務範圍、權威來源、環境與授權 |
| 需求／驗收條件 | ID、來源、版本、已確認規則、未決問題 |
| 風險 | 影響、判斷依據、優先序、對應測試 |
| 測試案例 | 前置條件、資料、步驟、預期結果與來源 |
| 執行紀錄 | Run ID、版本／SHA、環境、時間、執行者、命令或人工方法、結果、證據 |
| 缺陷 | 實際與預期、重現方式、影響、版本、證據、重測關聯 |
| 交付報告 | 已測範圍、未測範圍、結果、未解缺陷、剩餘風險、發版建議 |

第一次失敗與後續重測通過都保留。版本、環境或關鍵設定變動後，舊結果是否仍適用必須重新判斷。

**九、公司介面與經營方式**

原版的離線介面可對應成：

| 頁面 | 顯示內容 |
|---|---|
| **今日** | 要做的事、待決事項、阻塞、交付期限 |
| **公司** | 組織、員工與能力 |
| **專案** | 客戶、範圍、里程碑、環境 |
| **測試** | 風險、案例、執行結果、覆蓋缺口 |
| **缺陷** | 問題、影響、修正與重測 |
| **交付** | 報告、證據完整性、待核准項目 |
| **知識／工具／連接** | 方法、依賴、連通與驗證狀態 |
| **營運** | 商機、產能、工時、請款與收款 |

第一版可交付三種服務：

- **上線前品質評估**：關鍵流程探索、API 檢查、缺陷與剩餘風險報告。
- **回歸測試建置**：關鍵案例、自動化、執行方式、維護與證據交接。
- **持續 QA 支援**：版本影響分析、定期回歸、缺陷重測與品質週報。

這個提案與現有「AI 一人公司系統建置」及「QA Evidence」主線相接；後續可評估既有測試範本作為素材，但本輪沒有把它們當作已驗證的新公司能力，也沒有修改現有系統。
