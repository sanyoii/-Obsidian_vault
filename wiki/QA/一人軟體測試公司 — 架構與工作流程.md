# 一人軟體測試公司 — 架構與工作流程

> 公司統一入口：[[一人軟體測試公司/_index]]；委託企劃：[[一人軟體測試公司/PartyPiuPiu — 委託測試企劃]]（2026-09-17，32個情境尚未執行）。

> 後續研究：[[AI-一人公司/AI Hero — 兩家公司補強再審視]]；實作狀態：[[AI-一人公司/兩家一人公司 — AI Hero 補強計畫]]。2026-09-09 計畫已核准並完成本機補強；真模型與本輪畫面驗收受阻，詳見計畫頁首。

> 本頁為現行架構與實作對照。2026-09-09 已依使用者授權建立獨立本機公司：15 位角色、89 項能力方法、10 份知識、6 條產線、證據工具與離線工作台。角色實務能力與外部服務尚待逐案驗證。
> 來源：[[一人軟體測試公司 — 原始架構規劃]]、[[一人軟體測試公司 — 顧問團架構審議與角色分工]]。原版正文及顧問原始紀錄保留。
> 已建立 Git repo 與自有合成資料試跑，既有版本 0baf85e 已有遠端；本輪補強未提交或推送，未對外聯繫、付費或修改既有 QA 系統。

採用 **「你擔任負責人與最終 QA 決策者，AI 員工負責分析、測試準備、執行協作與營運」的一人軟體測試公司**。

起步以 **Web／SaaS／API 關鍵流程品質評估**為主，Mobile、效能、安全、Web3 與 AI 產品測試依案件啟用。這樣能保留完整公司架構，又不會一開始就承諾所有專業服務。

設計依據為原始 ZIP 與顧問團審議；以下保留架構基準，實際建置與差異以第十八節及新公司 SCHEMA.md 為準。

## 一、公司整體架構

```text
你｜公司負責人、Service Product Owner、交付核准
│
├─ 營運中樞
│  ├─ 營運幕僚（兼 Project Manager）
│  ├─ 業務與方案顧問
│  ├─ 客戶成功專員
│  └─ 財務管理員
│
├─ 品質規劃
│  ├─ 測試策略師（兼 QA / Test Architect）
│  └─ 需求與測試分析師
│
├─ 測試交付
│  ├─ 探索與體驗測試員
│  ├─ 自動化測試工程師
│  ├─ API 與資料測試工程師
│  └─ 測試環境與 CI 工程師
│
├─ 專項測試｜按案件啟用
│  ├─ 效能與可靠性測試員
│  └─ 安全與隱私測試員
│
├─ 交付覆核
│  └─ 品質證據審查員
│
└─ 公司資產與成長
   ├─ 知識管理員
   └─ 技術內容與品牌專員
```

這 **15 位是可交辦的角色**，不代表同時啟動 15 個 Agent。日常由營運幕僚辨識任務，再調用必要能力；你負責接案承諾、關鍵判斷、客戶交付核准。

完整關係沿用原版：

```text
公司目標
   ↓
客戶／專案 → 工作流程 → 員工.能力
                           ├─ 方法：怎麼做
                           ├─ 知識：怎麼判斷
                           ├─ 工具：用什麼執行
                           └─ 連接：讀寫哪個系統
                                  ↓
                           測試與執行證據
                                  ↓
                           覆核 → 核准 → 交付
```

## 二、所有員工與能力

能力使用穩定 ID，例如 `test-analyst.design`，讓流程能直接引用。

| 員工／ID | 能力清單 | 主要交付物 |
|---|---|---|
| **營運幕僚／Project Manager** `chief-of-staff` | `intake` 任務分流；`context` 組裝專案脈絡；`plan` 排工作；`capacity` 產能與期限管理；`status` 現況對帳；`project-scope` 範圍基準；`dependency-control` 依賴與阻塞；`change-control` 變更影響；`acceptance-close` 驗收結案 | 今日工作、案件進度、阻塞與待決事項 |
| **業務與方案顧問** `sales-consultant` | `qualify` 案件適配；`discover` 需求訪談；`scope` 售前範圍草案（核准後移交 PM）；`estimate` 工時與成本估算；`proposal` 提案；`offer-design` 服務方案假設（你決定採用與定價） | 需求摘要、範圍書、估算與提案草稿 |
| **客戶成功專員** `client-success` | `onboard` 客戶導入；`update` 進度溝通；`change` 收集並轉交變更請求（PM 維護基準）；`acceptance` 驗收溝通（PM 跟進完成）；`follow-up` 售後追蹤 | 導入清單、週報、變更單、驗收紀錄 |
| **財務管理員** `bookkeeper` | `quote` 報價；`billing` 請款草稿；`reconcile` 對帳；`receivables` 未收款追蹤；`margin` 案件成本分析 | 報價單、收支、未收款、案件損益 |
| **測試策略師／QA Architect** `qa-strategist` | `risk` 風險分析；`strategy` 測試策略；`coverage` 覆蓋配置；`entry-exit` 進出場條件；`release-advice` 發版建議；`architecture-review` 依賴與技術取捨；`test-layering` 測試分層；`architecture-decision` 必要設計決策 | 風險表、測試計畫、品質門檻 |
| **需求與測試分析師** `test-analyst` | `review` 需求審查；`acceptance` 驗收條件；`model` 狀態與規則建模；`design` 案例設計；`trace` 需求追溯 | 問題清單、驗收條件、測試案例、追溯表 |
| **探索與體驗測試員** `exploratory-tester` | `charter` 探索任務；`explore` 流程探索；`compatibility` 相容性；`accessibility` 無障礙檢查；`reproduce` 缺陷重現 | 探索筆記、操作證據、缺陷草稿 |
| **自動化測試工程師** `automation-engineer` | `select` 自動化選案；`implement` 腳本實作；`regression` 回歸套件；`diagnose` 失敗分析；`stabilize` 不穩定測試治理 | 測試程式、執行設定、維護紀錄 |
| **API 與資料測試工程師** `api-data-tester` | `contract` 契約驗證；`authorization` 權限情境；`workflow` 跨服務流程；`consistency` 資料一致性；`resilience` 重試與冪等 | API 測試、資料核對結果、異常證據 |
| **測試環境與 CI 工程師** `test-platform` | `environment` 環境準備；`fixtures` 測試資料；`ci` 執行管線；`artifacts` 證據保存；`diagnose` 環境問題診斷；`tenant-isolation` 客戶隔離；`execution-budget` 執行上限；`recovery` 恢復與事故處理 | 環境清單、資料準備方式、CI 設定 |
| **效能與可靠性測試員** `performance-tester` | `workload` 負載模型；`threshold` 門檻設計；`load` 負載執行；`soak` 長時間測試；`analyze` 結果分析 | 效能計畫、延遲與錯誤率報告 |
| **安全與隱私測試員** `security-tester` | `scope` 授權範圍核對；`threat` 風險建模；`baseline` 基線檢查；`access-control` 權限驗證；`privacy` 敏感資料檢查 | 安全發現、重現證據、修正驗證 |
| **品質證據審查員** `evidence-reviewer` | `audit` 證據完整性；`reproduce` 重現覆核；`coverage-gap` 缺口審查；`report` 報告查核；`gate` 交付門檻；`oracle-audit` 預期結果來源覆核；`negative-control` 正反例查核；`decision-summary` 客戶決策頁 | 證據審查結果、交付通過／退回清單 |
| **知識管理員** `librarian` | `ingest` 資料消化；`distill` 經驗萃取；`template` 範本維護；`audit` 過期與引用檢查；`sanitize` 客戶資料去識別 | 可重用知識、範本、來源與版本紀錄 |
| **技術內容與品牌專員** `technical-marketer` | `position` 服務定位；`case-study` 案例包裝；`article` 技術文章；`portfolio` 作品集；`distribution` 發布草稿 | 服務頁、匿名案例、展示報告、技術內容 |

**分工邊界：**測試策略師決定測哪些風險；測試員產生結果；證據審查員檢查結論是否有依據。相同 AI 換角色自查，仍須標示為自查，不能稱為獨立驗證。

## 三、知識庫

沿用原版「一份知識對應一個可執行任務」，避免只有名詞百科。

| 知識分組 | 建議文件主題 | 主要使用員工 |
|---|---|---|
| **營運** | 案件適配、產能估算、優先序、風險升級 | 幕僚、業務 |
| **商務** | 需求訪談、服務範圍、報價估算、範圍變更、驗收與交接 | 業務、客戶成功、財務 |
| **產品** | 使用者旅程、業務規則、驗收條件、需求歧義 | 需求分析師 |
| **測試** | 風險排序、等價類與邊界值、決策表、狀態轉移、組合測試、探索測試 | 策略師、分析師、探索測試員 |
| **Web** | 瀏覽器差異、響應式、表單、Session、檔案上傳下載、無障礙人工檢查 | 探索與自動化測試員 |
| **API** | HTTP 契約、身分與權限、分頁、冪等、重試、限流、Webhook | API 測試員 |
| **資料** | 測試資料設計、資料遮罩、一致性、交易與對帳、時間與時區 | API 測試員、環境工程師 |
| **自動化** | 選案準則、Locator、隔離與清理、等待策略、斷言設計、不穩定測試 | 自動化工程師 |
| **環境** | 環境就緒、版本識別、CI 分層執行、證據保存、憑證處理 | 環境工程師 |
| **效能** | 負載模型、延遲分位數、錯誤率、資源飽和、結果可比性 | 效能測試員 |
| **安全** | 測試授權、存取控制、敏感資料、掃描結果判讀、安全重測 | 安全測試員 |
| **品質** | 缺陷分級、重現標準、追溯完整性、證據有效性、發版建議 | 全體測試角色、審查員 |
| **財務** | 工時與工具成本、收款節點、對帳、案件毛利 | 財務 |
| **品牌** | 證據導向寫作、案例去識別、成果宣稱邊界、客戶發布授權 | 品牌專員 |
| **領域選配** | Mobile 生命週期；Web3 簽名與交易狀態；AI 回答評估與工具權限 | 按案件綁定 |

新增知識與能力的具體綁定見第十一節。每份方法型知識保留原版五段：

```text
用途 → 必要輸入 → 判斷規則 → 操作方法與範例 → 自檢與交接
```

例如「測試－邊界值設計」必須寫清楚：

- 沒有上下限規格時，先列待確認事項。
- 區分有效邊界、越界、空值與型別錯誤。
- 預期結果須連回規格或已確認規則。
- 不能把目前系統的行為直接當成正確答案。

## 四、工具架構

**起步建議以一套主要測試技術為核心，額外工具按案件加入。**下列是候選工具與用途，並非本機已安裝清單。

| 工具層 | 建議配置 | 使用方式 |
|---|---|---|
| 公司資料 | Markdown vault＋Git | 保存員工、方法、知識、專案與變更歷史 |
| AI 工作引擎 | 現有 Codex；其他引擎選配 | 分析、起草、實作與結果整理；執行結論仍靠工具證據 |
| Web 自動化 | Playwright | UI 測試、回歸與操作證據 |
| API 自動化 | 優先使用 Playwright API testing | 與 Web 測試共用技術；客戶既有 Collection 再評估沿用 |
| 人工調查 | 瀏覽器 DevTools、截圖／錄影、HTTP 請求工具 | 查 Network、Console、人工重現 |
| 資料驗證 | SQL 查詢工具＋專案既有測試框架 | 核對測試環境資料與業務結果 |
| CI | 客戶既有 CI；新案可評估 GitHub Actions | 按事件、手動或排程執行 |
| 報告 | 原生測試報告＋公司交付範本 | 執行細節與商務摘要各有用途 |
| 效能選配 | k6 | 依事前門檻判斷負載結果 |
| 安全選配 | ZAP | 授權範圍內的基線檢查與人工判讀 |
| 無障礙選配 | axe-core＋人工鍵盤／讀屏檢查 | 自動檢查後補人工測試 |
| Mobile 選配 | Appium＋約定裝置 | 有 Mobile 案件才建立對應環境 |

原始規劃核對過的官方參考（本輪未重新驗證版本、安裝或連通性）：Playwright [API testing](https://playwright.dev/docs/api-testing) 與 [Trace Viewer](https://playwright.dev/docs/trace-viewer)；GitHub Actions 支援事件、手動及排程 [workflows](https://docs.github.com/en/actions/concepts/workflows-and-actions/workflows)。k6 可用 [thresholds](https://grafana.com/docs/k6/latest/using-k6/thresholds/) 判斷結果；[ZAP Baseline](https://www.zaproxy.org/docs/docker/baseline-scan/) 與 [axe 自動檢查](https://playwright.dev/docs/accessibility-testing) 都需要清楚交代覆蓋限制。

## 五、連接與資料流

「工具」是執行能力；「連接」則是它被授權存取的客戶、專案與環境。

| 連接 | 讀取內容 | 核准後可能寫入的內容 | 主要使用角色 |
|---|---|---|---|
| GitHub／GitLab | 程式碼、diff、版本、CI 結果 | 測試程式、PR、Issue | 分析、自動化、環境、審查 |
| Jira／Linear／客戶 Issue 系統 | 需求、驗收條件、缺陷狀態 | 缺陷單、重測結果 | 分析、測試、客戶成功 |
| Notion／Confluence／Drive | PRD、規格、會議紀錄 | 核准報告與交付文件 | 幕僚、分析、客戶成功 |
| 測試網站／API | 測試目標與回應 | 約定測試帳號中的測試操作 | 測試執行角色 |
| 測試資料庫 | 核准資料範圍 | 必要且核准的測試資料準備 | API、環境 |
| CI／Artifact 儲存 | Job、log、trace、附件 | 測試證據與執行摘要 | 環境、審查 |
| 錯誤與監控系統 | 錯誤事件、效能、相關 log | 原則上先以讀取為主 | API、效能、安全 |
| Email／Slack／Teams | 客戶提供的需求與回覆 | 核准的報告、進度與問題 | 客戶成功 |
| 財務／收款系統 | 請款與入帳資料 | 核准的請款紀錄 | 財務 |

每條連接登記：

```text
客戶／專案、用途、目標環境、讀寫權限、
憑證所在位置的指標、驗證日期、保留期限、撤銷方式
```

狀態分開記為「未設定／待授權／已連線未實測／已驗證／失效」。**設定存在不等於連接可用，連接可用也不等於可操作所有專案。**

## 六、工作流程

公司需要六條產線。產線只負責編排能力，不另假裝成員工。

| 產線 | 主要步驟 | 完成條件 |
|---|---|---|
| **接案產線** `engagement-pipeline` | 詢問 → 適配 → 訪談 → 範圍與估算 → 提案 → 核准 → 導入 | 範圍、環境、交付物、期限、驗收與授權已確認 |
| **測試交付產線** `qa-pipeline` | 脈絡 → 風險 → 設計 → 就緒檢查 → 執行 → 缺陷 → 重測 → 覆核 → 交付 | 約定範圍有結果與證據，未測與風險明確 |
| **持續回歸產線** `regression-pipeline` | 版本變更 → 影響分析 → 選案 → 執行 → 失敗分類 → 重測 → 彙整 | 結果綁定本次版本，失敗原因與阻塞有去向 |
| **專項測試產線** `specialist-pipeline` | 確認專項 → 專用計畫 → 環境與授權 → 執行 → 分析 → 重測 | 完成專項門檻與明確限制說明 |
| **結案營運產線** `closeout-pipeline` | 客戶驗收 → 交接 → 請款 → 對帳 → 權限與資料收尾 → 回顧 | 交付、款項、資料及權限責任都有紀錄 |
| **知識與成長產線** `learning-pipeline` | 結案資料 → 去識別 → 萃取 → 覆核 → 知識／範本 → 核准案例 | 內部可重用；公開材料另有客戶授權 |

核心交付使用五個工作站，六條產線按場景復用它們，不另新增六套狀態：

```text
你＋業務：服務定位／方案（按需更新）
                    ↓
① 範圍確認［Project Manager］
   缺輸入／授權 → 暫停受影響部分
                    ↓
② 風險、判準與架構就緒［測試策略師／Architect］
   分析師準備判準；爭議由客戶指定人裁定
                    ↓
③ 執行［PM 指定一名執行責任人，調用必要專才］
   記錄首次結果；有界重試；產品／腳本／環境問題分開
                    ↓
④ 證據覆核［審查員＋你］
   證據不足 → 補測或降低結論；未核准 → 待審
                    ↓
⑤ 客戶交付與驗收［客戶成功；PM 跟進］
   客戶決定發版；修正由客戶開發 → 回③重測→④再審
                    ↓
結算、權限資料收尾、知識萃取
```

每站交接條件、失敗處理與責任人見第十二節。Run 結果不等於報告核准或發版決策。

缺陷修正預設由客戶開發團隊負責；代修程式應另列服務範圍。

## 八、最重要的資料連接：證據鏈

```text
專案 → 版本
         ↓
需求 REQ → 風險 RISK → 測試 TC → 執行 RUN
                                     ├─ 證據 ART
                                     └─ 缺陷 BUG → 重測 RUN
                                                   ↓
                                               交付報告
```

| 資料 | 最低必要內容 |
|---|---|
| 專案卡 | 客戶、產品、聯絡窗口、服務範圍、權威來源、環境與授權 |
| 需求／驗收條件 | ID、來源、版本、已確認規則、未決問題 |
| 風險 | 影響、判斷依據、優先序、對應測試 |
| 測試案例 | 前置條件、資料、步驟、預期結果與來源 |
| 執行紀錄 | Run ID、版本／SHA、環境、時間、執行者、命令或人工方法、結果、證據 |
| 缺陷 | 實際與預期、重現方式、影響、版本、證據、重測關聯 |
| 交付報告 | 已測範圍、未測範圍、結果、未解缺陷、剩餘風險、發版建議 |

第一次失敗與後續重測通過都保留。版本、環境或關鍵設定變動後，舊結果是否仍適用必須重新判斷。

## 十二、五個工作站與交接契約

| ⑤ 交付／client-success | 你核准的報告、接收人、範圍內傳送授權 | 傳送結果可核對、客戶驗收或待回覆狀態明確；PM 跟進結案 | 無回覆保持待回覆；拒收列差異；新增需求走變更 |

各工作站在既有任務或文件上記錄下列欄位，不另建「交接帳本」：

- 工作識別、客戶／專案、輸入來源與版本、範圍／授權引用。
- 唯一輸出位置、完成條件、責任人、下一責任人。
- 阻塞原因、誰處理、解除條件、對期限與成本的影響。
- 本次時間／費用／重試上限及目前消耗；未設定必要上限不得啟動會產生成本的操作。
- 正常下一步與失敗去向。重新執行保留首次結果並產生可關聯的新 Run。

例：登入案例的回應已取得但權限規格矛盾，Run 保留觀察；受影響案例標 Blocked 並引用待確認需求，不宣稱產品 Pass 或確認缺陷。客戶裁定後更新判準版本，重新執行。

### 變更、重試與中斷

1. 客戶成功收件，PM 記到原專案並評估影響；你與客戶確認調整後才更新範圍基準。舊 Run 繼續綁舊版本，不回填成新範圍證據。
2. 測試失敗不為求通過盲目重試。已知暫時性原因且仍在授權與預算內才重試；首次失敗、後續結果及原因都保留。
3. 對外寫入遇 timeout，先查實際結果再決定重送；不能確認且無防重複機制時轉人工，不直接再寄信或再建單。
4. 中斷後先核對版本、環境、已執行項目、剩餘預算與授權；條件變動先評估影響。恢復動作與理由記在原任務／Run。
5. 真人不在或無法覆核時，已核准範圍內工作可依既定上限繼續；對外承諾、交付及新增授權停在待審。

## 十三、證據、測試判準與品質門檻

測試預期結果（oracle）必須有來源與版本。客戶正式規格與已確認變更衝突時，需求分析師提出具體差異，由指定產品／業務負責人裁定；沉默不等於同意。探索發現可先記為疑似問題，不以現行系統行為反推「應該如此」。

| 狀態層 | 語意 | 防止混用 |
|---|---|---|
| Run 結果 | Pass／Fail／Blocked／Skipped／Not Run | Pass 只表示該版本、環境及範圍內斷言符合；與缺陷成因分類分開 |
| 證據有效性 | 有效／過期／待重驗／缺失 | 舊 Pass 可保持歷史事實，但不能自動支撐新版本 |
| 交付覆核 | 草稿／待審／核准／退回 | Build 或測試全綠不等於報告獲核准 |
| 客戶驗收 | 待回覆／接受／需修訂 | 無回覆不是接受，發送成功不是驗收 |
| 發版決策 | 客戶決定及正式引用，或 Unknown | 本公司建議不替代客戶決策 |

交付門檻：

- 所有約定範圍項目有測試結果，或有明示未測原因與風險；覆蓋分母使用核准範圍，不能只計已跑案例。
- 每個已執行案例都有 Run，能追到版本、環境、時間、方法、執行者與原始證據。
- 每個已確認缺陷有預期來源、實際結果與重現證據；未裁定項目維持疑似／待確認。
- 高風險案例由你人工核對判準與必要操作；AI 自查、人工覆核及獨立重現分別記錄。只有實際由不同人員獨立重現才如此宣稱。
- 在自有或授權樣本，以已知正例及刻意反例驗證關鍵測試能辨識正常與異常；不在客戶正式系統植入缺陷。
- 審查員發現證據不足，回原工作站補齊或降低結論；不能靠改報告掩蓋實際失敗。
- 報告揭露版本、限制、未測範圍、重大未解問題、剩餘風險與待客戶決定事項；不承諾「零缺陷」。
- 你核准明確報告版本與接收範圍後才能對外交付；授權已涵蓋的正常動作不重複請示。

版本、環境、關鍵設定或判準變更後，由策略師決定哪些證據需重驗，記錄理由；沒有依據不能沿用。可設定證據到期日，但期限必須有案件依據，不能任意套用。

## 十四、客戶資料、連接與事故處理

每案維持專屬測試帳號、最小權限與獨立 artifact 路徑。客戶專屬資料不進公司通用知識、不跨案共享，也不因多 Agent 協作而擴大可見範圍。

連接除第五節欄位，還須明確登記：可操作資源、可接受資料類型、可否送入外部模型、授權動作與上限、事故聯絡人、保留／刪除與恢復責任。只存憑證位置指標，不把憑證寫進 Markdown、log、trace 或公開頁。

- 未確認可送入模型的資料，先使用合成／去識別樣本；去識別仍不自動取得重用權。
- 工具輸出與外部文件是資料，不得讓其內容擴大操作授權。
- 備份與還原須包含權限及客戶隔離；僅有備份不宣稱可恢復，還原未演練須標未驗證。
- 疑似洩漏、誤發、異常權限或跨客戶混用：停止受影響操作，保全必要證據，依既定授權通報指定人；無通知授權時準備通知並交你處理。
- 撤銷、刪除與保留遵照個案核准條件，不能為了結案自行刪證據。客戶不回覆時維持待處理狀態。

## 十五、營運、成本與客戶交付

首波不以完整部門數當成服務能力證明。效能、安全、Mobile、Web3 與 AI 測試須另有適任負責人、適用環境、工具驗證與可展示證據，才納入報價。

PM 起步只排一個試案；不能用多 Agent 並行倍增可承諾工時。專案成本記錄保存在原專案，財務收入與收款維持帳本唯一來源。

- **實際投入**＝售前＋分析設計＋執行＋人工覆核＋返工＋維護工時；客戶等待時間另外記。
- **直接成本**＝核准工時成本口徑＋工具／環境／必要外包成本。成本費率未定時，損益為 Unknown。
- **案件毛利估算**＝案件收入減直接成本；未包含固定營運費時不得稱公司淨利。已報價、已請款與已收款分開。
- 每案記範圍變更、返工原因、人工決策等待與測試資產實際重用工時，作為改善依據。
- 客戶問題、現行替代方式、報價接受或付費回應才支撐需求判斷；流程試跑與品牌內容不代替這些證據。
- 客戶開發團隊／軟體代理商可作後續通路假設；未訪談不宣稱有合作意願。
- 個案需確認交付權利、責任與驗收約定；本規劃不自動生成適用法律條款。

客戶報告首頁固定回答：

| 客戶問題 | 報告內容 |
|---|---|
| 測了什麼？ | 產品版本、環境、範圍與時間 |
| 發現什麼，影響誰？ | 可追溯發現及業務影響，不只列技術錯誤 |
| 還不知道什麼？ | 未測、受阻、待裁定、未完成重測 |
| 現在要做什麼？ | 修正／補測／確認的具體事項、責任人與期限（未知就明示） |
| 誰決定能否上線？ | 客戶決策人與待決風險；本公司建議及適用限制 |

結案需分別確認交付、驗收、款項、資料與權限收尾；任何未完成項目仍由原帳／原專案追蹤，不因報告寄出便全部標完成。
