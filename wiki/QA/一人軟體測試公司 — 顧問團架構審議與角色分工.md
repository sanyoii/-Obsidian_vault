# 一人軟體測試公司 — 顧問團架構審議與角色分工

> **結論：需要 Architect、Project Manager 與自家服務 Product Owner 的責任；起步由現有角色兼任，不直接從 15 擴成 17／18 位員工。**

## 顧問團一致同意

原規劃的證據鏈、角色能力綁定、單一真相及人工核准值得保留。問題主要是責任和交接還不夠具體，不能用「15 位 AI 員工」推論已具備交付能力。所有顧問都主張先驗證一種有限範圍服務，再按實際瓶頸拆職。

Project Manager 的職責需要明確存在；Architect 需要處理技術設計與取捨，但不必每案全程常駐。角色卡不是常駐程序，也不代表要把每案拆成 15 次 Agent 交接。

## 顧問團吵起來的地方

- Product Manager：找碴的、路人甲與催你動的傾向暫不另設；找好處的主張由現有人員兼任。問方向的把自家服務定位與定價交給真人。
- Architect：多數把它放在複雜案件關卡；找好處的強調可重用測試架構應有持續責任。
- 先求穩還是先做續約資產：多數先看單案可交付性，找好處的看「首次評估→持續回歸」的上檔。

主席採用「自家服務產品管理必須有」這個少數意見，但不增加常設 Product Manager：服務定位、定價與方案取捨由你負責，業務與分析角色準備資料。這不授權 AI 替客戶決定產品。Architect 每案做短檢查，只有跨服務、複雜資料與權限、非功能需求或新框架取捨時，才做完整設計。

## 互評抓到的盲點

以下區分「原版已提但未具體」與「新增責任」，不把原本已有的驗收、變更、資料保留及自查限制誤稱全無。

| 優先 | 缺口與原版現況 | 必須補出的可檢查內容 | 責任 |
|---|---|---|---|
| P0 | 範圍、估算、驗收已提，尚無可執行服務契約 | 接受／拒收、輸入就緒、測試邊界、投入上限、包含的重測次數、變更處理、停止／恢復條件；未確認值標 Unknown | Project Manager 整理，你核准 |
| P0 | 有預期結果來源，缺爭議裁決權 | 每項預期結果標來源與版本；文件互相矛盾時由客戶指定產品／業務負責人確認，未確認不得當作已證實缺陷 | 需求分析師追蹤，客戶裁定 |
| P0 | 有人工核准，缺具體決策分工 | 你核准報告與對外承諾；客戶指定人決定發版及接受剩餘風險；真人未覆核不得自動交付 | Project Manager |
| P0 | 已承認 AI 自查非獨立驗證，缺抓共同誤判的方法 | 重要案例由人核對判準；用已知正反例檢查測試是否真的會報錯；獨立重現須記人員與條件，做不到標未驗證 | 證據審查員＋你 |
| P0 | 有連接與資料保留欄，缺多客戶隔離和事故處理 | 客戶專屬權限、artifact隔離、送入模型的資料邊界、刪除／撤銷核准、備份恢復；誤發或權限異常先停、保全與通知指定人 | Architect／環境工程師 |
| P0 | 有流程拓撲，缺能力交接契約 | 輸入、唯一落點、完成條件、下一責任人、阻塞原因、重試預算；失敗不無限重跑，外部寫入防重複 | Architect 定介面，Project Manager 管阻塞 |
| P1 | 有成本分析，缺計算口徑與產能限制 | 記錄售前、執行、人工覆核、返工、維護工時；等待時間另記；工具費與收入分開；先限定同時一個試案 | 財務＋Project Manager |
| P1 | 缺明確資產重用邊界 | 區分公司通用方法、客戶專屬程式與資料、可匿名公開材料；去識別不等於取得重用／發布權 | 你＋知識管理員 |
| P1 | 尚無客群與付費證據 | 誰受何種問題困擾、現在如何處理、願為何種交付付費；記真實訪談／報價回應，不能用本機試跑證明需求 | 你擔任 Service Product Owner |
| P1 | 有技術報告，缺客戶可理解的決策頁 | 首頁只說發現、業務影響、未測範圍、下一動作與決策人；技術附件另接證據 | 客戶成功＋證據審查 |
| P2 | 已列新專項，缺啟用能力門檻 | 特定人員、環境、工具與可展示證據達到要求才納入服務；自動掃描不等於完整專業審查 | 策略師＋你 |

契約責任、資產權利及責任限制在此只是需確認的商務事項，不提供已適用的法律條款。原版的資料保留、重測與能力狀態仍應寫回各自唯一來源，不另建第二本帳。

## 建議

**採用「責任完整、執行精簡」架構：保留 15 位能力目錄，補上 Architect、Project Manager、Service Product Owner 的明確責任，由既有角色兼任；日常交付只經過五個工作站。**

### Architect 與 PM 的具體位置

| 職責 | 現在是否需要 | 起步歸屬與最終負責 | 產出 | 不負責 |
|---|---|---|---|---|
| QA / Test Architect | 需要；每案短審查，複雜案件才完整啟用 | 測試策略師主責，環境工程師協作；關鍵技術取捨由你核准 | 系統依賴、測試層級、框架選擇、環境／資料隔離、證據介面、必要的設計決策紀錄 | 不自行重設客戶產品架構；不保證沒有缺陷 |
| Project Manager | 需要，從接案到結案都要有 | 營運幕僚明確兼任；你承擔對外承諾 | 範圍、時程、依賴、產能、變更、阻塞、驗收與交接 | 不決定測試結果、不代客戶批准發版、不替財務重建帳本 |
| Product Manager / Service Product Owner | 需要自家公司服務產品責任，暫不獨立增員工 | 你主責，業務顧問準備方案與訪談證據 | 客群、問題、服務方案、定價假設、方案取捨、需求驗證 | 不接管客戶產品路線圖或未授權的需求決策 |

目前說的 Architect 是「測試架構師」。若將來承接客戶系統設計／代開發，Software / Solution Architect 才是新增服務範圍，不能混入測試報價。公司內部 Agent／工具接線由同一 Architect 職責管理，初期也不另設 AI 平台架構部。

### 補充到原能力表的提案

| 現有員工 | 新增或明確化的能力 ID | 知識與輸出 |
|---|---|---|
| chief-of-staff | project-scope、dependency-control、change-control、acceptance-close | 專案－範圍與變更；責任、工時與驗收紀錄 |
| qa-strategist | architecture-review、test-layering、architecture-decision | 架構－系統依賴／測試分層；按需的架構決策 |
| test-platform | tenant-isolation、execution-budget、recovery | 環境－隔離／執行上限／恢復；受控執行設定 |
| sales-consultant | service-discovery、offer-design | 商務－客群問題／服務方案；交給你決定的方案證據 |
| evidence-reviewer | oracle-audit、negative-control、decision-summary | 品質－判準覆核／正反例／決策摘要 |

以上只是擬議能力，不已建 card、不改 SKILL，也不重複建立原本已有的能力：實作時應優先擴充既有條目。

### 改良後的日常流程

```text
服務方案與接案條件（你＋業務；按需更新）
                 ↓
① 接案與範圍鎖定［Project Manager］
   目標、客戶輸入、授權、交付、投入上限與停止條件
                 ↓
② 風險／判準／架構就緒［策略＋分析；Architect 按需深入］
   預期結果待確認 → 客戶裁定；影響範圍標待定
                 ↓
③ 測試執行［依風險選必要專才］
   有界重試；保存首次結果；產品／腳本／環境問題分開
                 ↓
④ 證據與結論覆核［審查員＋你］
   不足 → 補測或降級結論；無人核准 → 停在待審
                 ↓
⑤ 客戶交付與驗收［客戶成功；Project Manager 跟進］
   客戶決定發版；需要修復 → 客戶開發 → 限範圍重測
                 ↓
財務結算／權限資料收尾／知識萃取（依既有產線）
```

角色之間只交接已完成的工作產物與必要引用，不轉交整段聊天。每個工作站指定一名責任角色，異常回到原責任人。CI 已獲範圍授權的重複執行可依契約進行；新增目標、資料範圍、負載或對外寫入要重新確認。

在既有執行紀錄或任務落點補齊「輸入來源與版本、輸出位置、完成條件、阻塞、責任人、重試／時間上限」。沿用 Run 的 Pass／Fail／Blocked／Skipped／Not Run；交接就緒與報告核准另有意義，不可混為同一個 PASS。

### 何時才拆成獨立員工

- PM：當多案依賴或變更追蹤持續漏接，且兼任造成可觀察的延誤，再拆 Project Manager 卡；它仍不增加真人產能。
- Architect：當跨案設計衝突、框架維護或高耦合整合成為重複瓶頸，再拆 QA Architect 卡。
- Product Manager：當服務組合、客群與定價實驗已形成持續工作，再獨立成角色。
- 拆職依據是已記錄的返工、等待與決策負荷，不用「公司看起來完整」當理由。

## 先做的那一件事

**完成一頁「首案服務規格」，先把一件案子的責任、交付與停止條件寫清楚。**

以下已提供可審閱草案，尚未接案、測試或對外報價：

| 項目 | 試案草案 |
|---|---|
| 服務 | Web／API 關鍵流程品質評估 |
| 客群與痛點 | 假設為即將發版、缺乏固定 QA 的小型 SaaS 團隊；尚無訪談或付費證據 |
| 測試目標 | 自有或明確授權的測試環境；網址、版本、帳號、客戶決策人待確認 |
| 範圍上限 | 提案：1 條關鍵使用者流程、最多 5 個直接相關 API；固定一組瀏覽器／環境；不含效能、安全專項、代修與正式環境操作 |
| 必要輸入 | 已確認的業務規則與預期結果、範圍與授權、可用環境及測試資料 |
| 投入上限 | 提案：最多 1 個工作日的實際投入；起算點為輸入就緒，等待另記；工具付費預算待確認，確認前不新增付費操作 |
| 重測 | 提案：同範圍 1 輪；需客戶提供修復版本，未提供則交付未重測事實 |
| 交付物 | 風險／案例、Run 與證據、缺陷及未測清單、1 頁客戶決策摘要 |
| 驗收草案 | 每個範圍項目都有結果或明示未測原因；每個缺陷都有來源、版本、重現與證據；已執行案例有Run；沒有無證據Pass；不以「無Bug」驗收 |
| 流程試跑門檻 | 所有已執行案例可追至版本／環境／方法／證據；至少1個已知正例和1個刻意反例能被正確判別（僅在授權樣本）；記錄總工時、覆核與返工，超上限如實判未完成 |
| 停止與恢復 | 無授權、目標版本不明、關鍵判準衝突、資料隔離失效或投入到頂即停止受影響範圍；指定責任人補齊或核准變更後恢復 |
| 未決事項 | 真實客群、報價、客戶期限、權利與資料保留約定；全為 Unknown，不視為已同意 |
| 下一驗證的區別 | 本機試跑驗證流程；後續由你核准接觸目標客戶，才能取得需求、報價接受或付款證據。沒有這些證據不宣稱商業可行 |

此草案只將建議具體化，沒有啟動試案或外部行動。
