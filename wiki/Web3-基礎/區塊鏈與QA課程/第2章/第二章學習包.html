先接回第一章

交易是提出變更帳本的要求；檢查通過才可能改帳。驗證和共識分別處理「這筆符合規則嗎」和「共同採用哪段歷史」。簽章是驗證的一部分。兩筆互相衝突的付款各自都可能簽得正確，仍須檢查可花費資產、順序及重複使用。本章沒有送鏈、改帳或實作共識。

1. Hash：核對的是哪些資料？

Bob 收到一份寫著「Alice pays Bob 7」的訊息。Alice 說自己送出的也是這份內容，Bob 想核對途中有沒有被改動。除了逐字比較，也可以把內容交給一個固定算法，算出一段固定長度、方便比對的摘要；這個運算叫 Hash。

先看這次實際會觀察到什麼：

送進算法的內容 與原摘要比較 這個結果告訴我們什麼？
Alice pays Bob 7 相同 這次使用同一份內容重算，得到同一份摘要
Alice pays Bob 70 不同 這次金額文字改了，算出的摘要也變了
Alice pays Bob 7，末尾多一個空白 不同 電腦也把空白當成內容，不能只看畫面像不像

這章選用的算法叫 SHA-256。你先抓住「把內容算成摘要，再比較」這個用途，下面再把它接到 Python。這三個樣本的結果會實際重算，不要求你記住摘要字串。

要讓電腦算，先把文字轉成數值資料，這些資料以 byte（位元組） 為單位；一個 byte 是 8 個位元。UTF-8 是文字轉成這類資料的編碼方式。本章兩邊都用 UTF-8，比較的是送進算法的精確資料，也就是程式裡的 bytes。

Hash 不把內容藏起來，也沒有替內容背書。原文只有幾個候選時，人可以逐個算摘要來猜；兩份不同輸入也可能碰撞，不能說它保證唯一。驗證完整性時，你還需要可信的原摘要：如果 Eve 同時換掉檔案和旁邊的摘要，重新比較仍可能一致。

QA 從這裡切進：先把 bytes 看清楚

7、70、結尾空白及換行會形成不同資料。這次每一個字元都保留，不自動刪掉空白，也不用 Python 內建的 hash() 代替 SHA-256。

存成 hash_lab.py，在終端機執行 python3 hash_lab.py；Windows 可用 py -3 hash_lab.py。不用安裝套件。

import hashlib

def digest(text):
    return hashlib.sha256(text.encode("utf-8")).hexdigest()

original = "Alice pays Bob 7"
changed = "Alice pays Bob 70"
print("原文 bytes:", original.encode("utf-8"))
print("原摘要:", digest(original))
print("再算一次:", digest(original))
print("改金額:", digest(changed))
print("加空白:", digest(original + " "))
print("完全相同:", digest(original) == digest(original))
print("內容改動:", digest(original) == digest(changed))

encode 把字串轉成 bytes；hexdigest 把摘要顯示成十六進位文字；== 比較兩邊是否相等。最後兩行預期是 True、False。前面的摘要請保留完整值，再對照解答。測試紀錄要寫原文、bytes／編碼、算法、預期、實際及限制。「這三筆不同」不能推成「所有不同輸入永遠不同」。

十六進位是用 0–9、a–f 這 16 種符號表示數值的方式。SHA-256 的摘要長度是 32 bytes，這裡每個 byte 顯示成兩個字元，所以你會看到 64 個字元；那段長字串是結果的顯示方式，不是另一項付款資料。Python hashlib

進一步核對：為什麼看起來相同的資料也可能有不同摘要？

JSON 是用文字表示欄位與值的資料格式。例如 {"to":"Bob","amount":7} 與 {"amount":7,"to":"Bob"}，欄位值相同，文字排列卻不同。把欄位資料轉成文字或 bytes 的步驟叫「序列化」。系統若要把這兩種排列視為同一筆資料，就得先訂一致的轉換規則，再做 Hash。這章不操作 JSON；先用固定文字把精確資料的比較練好。Python 的 .strip() 會刪去字串兩端的空白，本例不使用它，因為這次規格把空白也算進內容。

2. 私鑰、公鑰與地址：哪一個用在哪裡？

Alice 不只要讓 Bob 看出內容有沒有變，還要能對這份內容留下別人可以核對的簽章。先把三種資料的用途分開：

資料 在本章做什麼？ Bob 需要拿到嗎？
Alice 私鑰 Alice 用它產生簽章，必須保密 不需要；驗證不能要求 Alice 交出它
配對的 Alice 公鑰 讓 Bob 核對相應簽章 需要；也要確認它是這次授權規則所指定的公鑰
Bob 的地址 在付款資料裡指定收款目標 需要指定；只看地址外形還不能判定選對收款人

由私鑰按算法算出公鑰的過程叫「推導」。選用安全算法與合適金鑰時，從公鑰反推私鑰在計算上不可行。公開公鑰不會因此把簽署能力交給 Bob。

地址是系統用來定位收款目標或帳戶的標識，產生方式依鏈與地址類型決定。Ethereum 有由私鑰控制的外部帳戶，簡稱 EOA；也有由程式規則控制的合約帳戶。合約地址沒有對應的帳戶私鑰，因此不能說「每個地址都由一個人的私鑰控制」。本章先掌握這個差異，不計算真實鏈地址。Ethereum accounts

圖上的「推導」是密碼學運算，「依規則產生」是各鏈的地址規則；它們不是付款、簽署或鏈上確認。只有私鑰那條路徑提供簽署能力。圖刻意把地址畫成分支，避免誤以為地址就是公鑰或簽章。

進一步核對：Ethereum 與 Bitcoin 地址為什麼不能共用算法？

一般 Ethereum EOA 的地址取公鑰 Keccak-256 摘要的最後 20 bytes，再加 0x；Keccak-256 是這裡使用的 Hash 算法名稱。本章的 SHA-256，以及 Python sha3_256，都不能拿來冒充它。

Bitcoin 舊式 P2PKH 是「付給公鑰摘要」這一類花費條件的名稱；其地址把公鑰摘要加上版本及校驗資料再編碼。其他 Bitcoin 地址類型各有規則。本章保留這個比較，不要求背算法；第三章會用 UTXO，也就是尚未花費的交易輸出，解釋資產與花費條件，該章仍待製作。Bitcoin Developer Guide

QA 從這裡切進：格式對，不代表對象對

假設收款指示寫的是 Bob 地址，你卻貼入 Eve 地址。兩個地址都可能長得合乎格式，程式仍要另查是否符合這次收款指示。接下來的函式只做第一件事：檢查外形。

它只檢查 0x 加 40 個十六進位字元。0x 是這裡的十六進位前綴，後面的字元只允許 0–9、a–f，也接受大寫 A–F。它不查 checksum（依地址規則檢查拼寫的校驗資訊）、鏈、資產、收款意圖、帳戶存在與合約行為，因此不是完整 Ethereum 校驗器。

def looks_like_address(value):
    return (
        isinstance(value, str)
        and value.startswith("0x")
        and len(value) == 42
        and all(c in "0123456789abcdefABCDEF" for c in value[2:])
    )

print(looks_like_address("0x" + "1" * 40))
print(looks_like_address("0x" + "1" * 39))
print(looks_like_address("0x" + "g" * 40))
print(looks_like_address(None))

isinstance 先確認輸入種類，後面的 and 只有前項通過才繼續；all 檢查每個字元。這裡預期 True、False、False、False。拿它當「收款人已驗證」會造成錯付風險；QA 需另外核對可信的收款指示與所選鏈／資產。

3. 簽章：誰對哪份內容同意？

Bob 要核對的是：「這份付 7 點給 Bob 的要求，有沒有符合 Alice 的簽署授權？」Hash 比較本身還答不了誰簽署。Alice 要用私鑰對特定內容產生簽章，Bob 才能拿相應公鑰核對。

這次完整內容寫成 course-v1|chain=lab-A|id=42|from=Alice|to=Bob|amount=7：course-v1 指教學規格版本；chain 指教學環境；id 是付款編號；from／to 是付款人／收款人；amount 是點數。這些都是教學欄位，不是 Bitcoin 或 Ethereum 的交易格式。

分隔符、大小寫及欄位順序都算內容，沒有換行。Alice 用自己的私鑰簽這份完整訊息，驗證者拿同一份 bytes、簽章及事先可信對應 Alice 的公鑰一起驗證。變更收款人、金額、環境或編號，原簽章應驗不過。

先讀上排：訊息和私鑰送進簽署運算，產出簽章。再讀下排：接收到的訊息、簽章與公鑰送進驗證運算，產出通過／不通過。公鑰還需要可信的身分或花費權限對應；若 Eve 提供自己的公鑰與自己的有效簽章，密碼學運算可以通過，卻不能據此同意從 Alice 的資產付款。

本包用名為 Ed25519 的簽章算法生成固定樣本，使用公開的教學測試金鑰。它不是 Bitcoin／Ethereum 的交易算法，也沒有送出真實交易。第一週白皮書圖用摘要說明資料綁定；本例把完整訊息交給簽章工具，算法內部如何處理資料由工具負責。不要自己把這兩個示例拼成「先 SHA-256，再加私鑰」的配方。

QA 從這裡切進：拆開運算結果與授權判斷

先把正常付款與換收款人的情況並排。原來 Alice 簽給 Bob，Eve 只改訊息裡的收款人，沒有拿到 Alice 私鑰，也沒有產生新簽章：

驗證需要的資料 原付款 C1 換收款人 C3
接收到的訊息 原訊息，to=Bob 只有 to 改成 Eve，其他欄位與排列不變
驗證用的公鑰 已按教學規格固定的 Alice 公鑰 同一把 Alice 公鑰
接收到的簽章 Alice 對原訊息產生的原簽章 同一份原簽章，未重新簽署

沿第二張圖逐步讀：① Alice 簽的是 Bob 那份內容；② 驗證者收到 Eve 那份內容；③ 驗證輸入的訊息已改，原簽章與它不相符；④ 所以這次應驗不過。下面結果由作者實跑，不是讓你從長字串猜答案。

作者實跑案例驗證結果這次能判定什麼？
C1：原訊息、Alice 公鑰、原簽章True這組資料的簽章驗過；付款合法性仍需其他檢查
C3：只把 Bob 改成 Eve，公鑰與簽章不改False原簽章驗不過改後訊息，符合這次應拒絕的預期
完整簽章樣本與執行版本｜需要核對時展開

本例的算法是 Ed25519。作者以 Node.js 的 crypto.sign／crypto.verify 簽署及驗證，學員不需安裝 Node.js。SPKI DER 是這裡公鑰的封裝格式名稱，hex 指十六進位顯示；下列長字串供完整核對，不要求背誦或手算。算法與 API 說明

C3 改後訊息（UTF-8）：

Alice 測試公鑰（SPKI DER hex）：

這裡 True／False 是簽章運算的通過／不通過。對 C3 而言，規格預期它被拒絕，實際也驗不過，所以這個負向測試可以判定符合規格；不能把「False」直接當成 QA 測試失敗。即使 C1 驗過，也還沒查餘額或已處理紀錄，不能因此核准實際付款。

接著只換成 Eve 公鑰來驗原訊息與原簽章：訊息與簽章都沒改，但公鑰與原簽署金鑰不配對，這次也驗不過。最後看冒用身分：Eve 若用自己的私鑰產生新簽章，再用 Eve 公鑰驗，運算可以通過；付款資料即使寫著 from=Alice，也不能取代可信的 Alice 公鑰對應。作業 C8 就查這一層授權。

這章要你預測結果、說出理由，再核對作者證據；Python 操作在 Hash 練習完成。看過固定結果不算你已執行密碼學工具。原始公鑰、簽章與版本仍完整留在同一包的可展開區，不需另開文章。

測簽章至少包含原訊息、改金額、錯公鑰與冒用身分。另一個缺陷是「只簽金額，沒有簽收款人」：如果被簽資料只有 amount=7，把 Bob 改成 Eve 不影響那份 bytes，簽章仍可通過。要修的是被簽資料及授權規格，不能只在 UI 顯示一句「簽章有效」。

重送完全相同的訊息，密碼學驗證仍會通過。這不等於能再付款；系統還需要防重送與狀態規則。本章的 id 是被簽的教學欄位，沒有實作「已處理 id」帳本。Ethereum nonce、Bitcoin 花費狀態與鏈上確認在後章教。簽章也不隱藏金額，不能證明餘額足夠、已打包或不可逆。

4. 錢包：使用者到底在確認什麼？

錢包是幫你管理帳戶、查看資產及與網路互動的工具；資產狀態記在鏈上。常見自託管錢包讓使用者控制簽署能力，託管服務則可能由服務方保管金鑰。助記詞是某些錢包的備份／恢復材料，不是公鑰，也不一定只恢復單一私鑰；本章不生成或輸入真實備份。Ethereum wallets

網站提出要求，錢包顯示內容，使用者同意後才可能產生簽章。連接錢包、簽訊息、送交易是不同動作；簽訊息不一定是轉帳，但也可能授權後續權利，必須看實際內容。不能只憑按鈕叫「登入」就判定沒有資產影響。

QA 從這裡切進：看顯示、被簽 bytes 與取消結果

教學產品規格：畫面及被簽訊息都顯示 lab-A、Bob、7、id=42；點取消不產生簽章，也不送出交易。測試要比較畫面／訊息的收款人、金額、環境與編號，並核對取消後的呼叫紀錄。這是本課程假設，不冒充所有錢包的共通實作。

例如畫面顯示 Bob，實際被簽內容是 Eve；即使 Eve 那份內容的簽章有效，產品仍不符合這份規格。缺少被簽 bytes 或呼叫紀錄時，結論是「證據不足」，不能只靠 UI 宣稱安全。

包內補課

Hash 一致，為什麼還不能相信付款內容？

假設 Alice 透過你已信任的渠道，提供原訊息的 SHA-256 摘要。你把收到的訊息用同一算法重算，再比較摘要，可以檢查這次收到的內容是否與基準相符。如果基準只是放在訊息旁邊、同樣由 Eve 提供，Eve 可以把 7 改成 70，再算一份新的摘要放在旁邊；你重算也會一致。兩次比較的算法一樣，差別在原摘要的來源能不能信任。相符不會自行證明 Alice 同意。

公鑰與地址容易混淆時

想像你桌上有兩份資料：一份是教學規格事先指定的 Alice 公鑰，另一份是收款指示裡的 Bob 地址。公鑰拿來驗 Alice 的簽章；地址用來指定這次付給誰。把地址填得合格式，只完成外形檢查，沒有驗 Alice 簽章，也沒有確認地址符合原收款指示。沿第一張圖指出兩條用途，別把地址塞進私鑰的位置。

驗過了，為什麼還不能從 Alice 付款？

把兩個檢查分開讀。第一步問「這份簽章能否用這把公鑰對這份訊息驗過？」第二步問「這把公鑰符合付款資產所要求的授權嗎？」本章規格把 Alice 授權對應固定為 Alice 公鑰。

訊息上的付款人 實際簽署者與驗證公鑰 簽章結果 本章 Alice 授權對應
Alice Alice 簽，Alice 公鑰驗原訊息 通過 符合；但仍需查資產及重送規則
Alice Alice 簽，Eve 公鑰驗原訊息 不通過 不能據此授權
Alice Eve 簽，Eve 公鑰驗同一訊息 通過 不符合，因為驗的是 Eve 的金鑰，不是規格指定的 Alice

錢包畫面與送出結果容易混淆時

把同一筆付款拆成三份證據：畫面說付 Bob 7 點；實際被簽訊息也應寫 Bob 7 點；送出呼叫紀錄則記是否真的送出。在這次產品規格下，畫面 Bob／訊息 Eve 是不一致；點取消後仍有送出紀錄，又違反取消不送出的規則。兩個問題各查自己的證據，不能用其中一份的「成功」代替另外兩份。

D 與六題

D1：畫面 Dana／被簽 Eve 不一致；取消仍送暫存交易。證據分別是畫面與精確被簽 bytes、取消前後簽署／送出呼叫紀錄及暫存識別。回歸測顯示收款人與訊息一致，並測有暫存交易時取消仍不送出。有效簽章只驗了 Eve 那份訊息，不能證明畫面一致；缺鏈上資料，不能判定是否真的扣款、到帳或確認。

D2：簽章可兩次通過，缺已處理 id／可花費狀態及鏈上結果。先訂重送規格，例如教學產品第二次應回傳已處理而不重複改帳，再用初始狀態、兩次相同輸入、回覆與前後快照核對；這是產品假設，不能套到所有鏈。「付款成功」字樣不能證明第二次合法或真的到帳。

六題必要要點：① 可信原摘要與同算法／精確 bytes；② 私鑰簽、公鑰驗、地址定位且規則依系統；③ 訊息、簽章、公鑰與可信授權對應；④ 收款人未被綁定；⑤ 只驗外形沒有驗意圖／鏈；⑥ 簽章不查已花費狀態、不產生收據或共識。
