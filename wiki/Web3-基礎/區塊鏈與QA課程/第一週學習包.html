第一堂：誰的帳本算數？（120 分鐘）

時間建議：診斷 15 分鐘、閱讀與推演 55 分鐘、練習 A 25 分鐘、讀圖練習與回顧 25 分鐘。這是估計；交易圖若需要多讀一次，就跨次接續，不跳過必要內容來湊時間。

Alice 有 10 點，Bob 和 Carol 都有 0 點。Alice 發出兩個要求：T1 付給 Bob 7 點，T2 付給 Carol 6 點。兩個要求單獨看都不超過 10 點，合在一起卻要花 13 點。

這個練習約定：錢不夠，這筆就不轉，任何人的餘額都不動。因此，付完 7 點後，Alice 只剩 3 點，接著想付 6 點就會失敗。表格最後一行才會跟上一行一樣。

如果重來一次，讓付 6 點的那筆先發生呢？拿紙筆算算看，練習 A 會用到你的結果。

Alice 的問題是：她把同一份可用的點數，拿去支應兩筆合起來付不起的款項。這個例子幫我們理解「雙重支付」的問題。處理第二筆時，要看第一筆處理後還剩多少，不能一直拿最初的 10 點來算。

本章用「每人還有多少點」來記帳。Bitcoin 用另一種記法，叫 UTXO，第 3 章才會學到。

把剛才的過程和名詞對起來：

  • Alice 說「付 7 點給 Bob」，這個轉帳要求叫做交易。系統還要檢查她能不能付。
  • 付完後，Alice 有 3 點、Bob 有 7 點、Carol 有 0 點。這份「現在各有多少」叫做狀態。
  • 把發生過的轉帳依序記下來，留下可查的紀錄，就是帳本的用途。

所以，收到轉帳要求後還要檢查，通過了才更新餘額。

如果這是某家店的會員點數，大家都接受店家記帳、處理錯帳，那店家可以用一般資料庫管理。它需要把同一帳戶的扣款排好順序，避免兩筆付款都拿舊餘額來判斷，也要保留備份與查帳紀錄。

這樣的需求可以先用資料庫解決。要不要用區塊鏈，得看大家願不願意交給同一個管理者，以及記錯時由誰處理。

三個節點看見不同順序

現在換個情境：有三台電腦一起記帳，每台都執行這個網路的軟體、按規則檢查交易。我們把它們叫做節點。

Alice 送出的訊息經過網路，不一定同時到達。A 可能先收到付 7 點的要求，B 先收到付 6 點的要求，C 暫時只收到一筆。即使一開始的帳本完全相同，後面也可能算出不同結果。

節點 A 問：「Alice 現在的餘額，夠付這一筆嗎？」這是在做驗證。驗證就是照規則檢查，這筆交易能不能接受。

但 A 和 B 各自檢查通過的第一筆可能不同。它們還需要一套共同規則，處理「大家最後採用哪個交易順序、哪份紀錄」；這就涉及共識。

把帳本複製成三份，只是讓三台電腦都有資料。要讓它們對交易紀錄取得一致，還得靠這套共同規則，以及規則能成立的條件。

Bitcoin 白皮書提出的問題，可以拆成兩件事。第一，付款是否由有權使用這份資產的人授權？數位簽章用來核對這件事。第二，同一份資產是否已經花過？即使兩筆都有有效簽章，收款人仍要知道它們是否互相衝突，以及網路採用哪份交易歷史。單靠簽章，還沒解決雙重支付。

白皮書以點對點網路與工作量證明提出解法，其安全性依賴誠實參與者掌握足夠算力等條件。第 2 章的學習包已提供 Hash、金鑰、地址與簽章解說；第 3 章的 Bitcoin 記帳與共識教材仍待製作。本章先把理解授權必需的交易圖教完，來源供選讀，無須另開文章完成練習。

白皮書交易圖：一份資產怎麼交給下一位？

剛才先問「Alice 的點數夠不夠付？」現在先不算餘額，改問「誰有權把這份資產交給下一個人？」這是同一筆付款要檢查的另一件事。餘額表處理數量，接下來的圖處理交接的授權；讀圖時先不考慮拆分金額或找零。

白皮書第二節用一串簽章描述所有權的交接。原圖的 Owner 0、1、2、3 是前後持有人。以下依原圖重畫資料關係，先看中間那筆：Owner 1 把資產交給 Owner 2。暫時把 Owner 1 想成 Alice、Owner 2 想成 Bob：Alice 先前收到這份資產，現在要交給 Bob。這個對照只幫你讀中間那筆，不把整串交接當成前面的點數計算程式。

讀中間交易時要問什麼？ 圖上到哪裡找？
誰要交出資產？ Owner 1；本筆留下他的簽章
要交給誰？ Owner 2；本筆指定他的公鑰
Owner 1 為什麼有權接著交？ 前筆交易指定 Owner 1 為接收者；核對他的本次簽章時，用前筆留下的 Owner 1 公鑰

最後一列是在追查前一次交接的資料，並不是只看交易文字寫了「Owner 1」就相信。下面四步會把被簽資料與驗證方式一起接起來。

三個詞先夠用：私鑰是持有人保密、用來產生簽章的資料；公鑰讓別人核對相應簽章，驗證者不需要拿到私鑰。Hash把輸入算成固定長度的摘要，本圖用它把前筆交易與下一位的公鑰綁在一起；它不負責把資料藏起來。完整演算法留在第 2 章。

讀中間交易時，按這四步走：

  1. 前筆把接收者指定為 Owner 1，留下他的公鑰。這是核對下一次交接的依據。
  2. Owner 1 準備把資產交給 Owner 2，把「前筆交易」與「Owner 2 公鑰」一起取 Hash。資料同時指向要接續哪筆，以及要交給誰。
  3. Owner 1 用自己的私鑰簽這個摘要，把簽章放進本筆交易。原圖的 Sign 虛線從 Owner 1 私鑰指向本筆的 Owner 1 簽章。
  4. 收款人可用前筆留下的 Owner 1 公鑰，核對本筆簽章與相應資料。原圖的 Verify 虛線連的是前筆公鑰與本筆簽章；本筆頂端的 Owner 2 公鑰指定下一位持有人，不能拿它來核對 Owner 1 的簽章。

右邊同理：Owner 2 用自己的私鑰，把前筆交易與 Owner 3 公鑰的摘要簽下來；核對這次交接用的是中間交易留下的 Owner 2 公鑰。因此，每格頂端寫的是下一位的公鑰，下方簽章屬於交出資產的上一位。交易中不需要公開私鑰。

如果有人把收款公鑰換成別人的，原簽章就無法通過對改後資料的核對；若改掉前筆資料，原簽章也不能照原樣證明那次交接。這說明簽章把授權連到特定資料，不能只檢查「有沒有簽章欄位」。

但 Owner 1 仍可能簽出兩筆互相衝突的交接。兩份簽章都核對得過，也不能讓同一份資產同時有效交給兩人。第二節接著討論可信任的中央檢查者作法，以及取消該角色時，如何讓參與者知道交易並接受共同歷史；後續章節再教網路、工作量證明與確認條件。這串所有權交接與「區塊如何串接」不同，不能看到一串箭頭就當成區塊鏈結構。

真實 Bitcoin 交易還有多個輸入／輸出、找零、費用及花費條件。上圖適合理解授權關係，不能直接拿來解碼所有實際交易；第 3 章須用 UTXO 樣本再教這些差異。此處依 Bitcoin 白皮書第二節 與 Bitcoin Developer Guide 的交易說明 編寫，後者用於核對概念圖的適用範圍。

dict 可以先想成一張表，例如 {"Alice": 10} 就是記著 Alice 有 10 點。問題是：寫 same = balances，會得到第二張表嗎？

這行只讓兩個名字指向同一張表；要保留修改前的內容，這裡可以用 .copy() 複製一張。程式裡的 snapshot 就是那張副本，我們也把這種留下當時資料的做法叫做「快照」。

balances = {"Alice": 10}
same = balances
snapshot = balances.copy()
balances["Alice"] = 3
print("目前餘額", balances)
print("另一個引用", same)
print("先前快照", snapshot)

執行前，寫下你猜三行各會印出什麼；執行後，再核對哪一份還留著 10 點。本週的表裡只有姓名和整數餘額，用 copy() 就能保留要比較的舊值。

後面檢查失敗交易時會用到它：轉帳前留一份，轉帳後拿來比較。若只寫 same = balances，兩個名字看到的都是修改後的資料，就看不出改過什麼。課前答不出來的原答照留，把現在弄懂的部分寫在旁邊。

接著是轉帳程式。balances 記餘額，sender 是付款人，receiver 是收款人，amount 是點數。apply_transfer 會用這四項資料，決定這筆要不要轉。

def apply_transfer(balances, sender, receiver, amount):
    if sender not in balances or receiver not in balances:
        return False, "UNKNOWN_ACCOUNT"
    if type(amount) is not int or amount <= 0:
        return False, "INVALID_AMOUNT"
    if balances[sender] < amount:
        return False, "INSUFFICIENT_BALANCE"
    balances[sender] -= amount
    balances[receiver] += amount
    return True, "APPLIED"


def run(order):
    balances = {"Alice": 10, "Bob": 0, "Carol": 0}
    transfers = {
        "T1": ("Alice", "Bob", 7),
        "T2": ("Alice", "Carol", 6),
    }
    for name in order:
        result = apply_transfer(balances, *transfers[name])
        print(name, result, balances.copy())
    return balances


print("A:", run(["T1", "T2"]))
print("B:", run(["T2", "T1"]))

讀 apply_transfer 時，可以把前三個 if 當成三道檢查：

  1. 付款人和收款人都在餘額表裡嗎？找不到就回傳 UNKNOWN_ACCOUNT。
  2. 點數是大於 0 的整數嗎？不符合就回傳 INVALID_AMOUNT。
  3. 付款人有足夠點數嗎？不夠就回傳 INSUFFICIENT_BALANCE。

只要其中一道沒過，return 就會結束這次函式，下面的扣款和加款不會執行。三道都通過，才從付款人扣除點數、加到收款人身上，最後回傳 True, "APPLIED"，表示已轉帳。

本週用整數點數，例如 1 點、2 點，先不處理小數。type(amount) is not int 還會擋掉 True、False，避免把 Python 的布林值當成金額。

run 每次都從 Alice=10、Bob=0、Carol=0 開始。["T1", "T2"] 是指定執行順序；換成 ["T2", "T1"] 就反過來。程式中的 *transfers[name] 會把那筆交易的付款人、收款人和點數，分別傳給 apply_transfer。這樣兩次比較都有相同起點。

這段程式只模擬一台電腦按順序算餘額，還沒有組成區塊鏈。它不會查「真的是 Alice 授權嗎」（簽章），也不會辨認「這筆是否已處理過」（交易 ID 與重放保護）。它沒有區塊、電腦之間傳訊息的網路、共識機制，也還沒處理多筆要求同時修改餘額的情況。

因此，跑對這個例子，只能說這段點數計算符合本週的規則。Bitcoin、Ethereum 各自還有其他交易規則。

把兩種順序的預測寫下來，再執行程式。跑完後，把 T2 金額從 6 改為 3，看看你的預測會怎麼變。本週作業 還列了 0 點、負數、錢不夠、找不到帳戶和連續付款的情況，每題都保留「我原本猜什麼」和「實際印出什麼」。

這個練習已經約定：付款人和收款人都要存在，點數要是大於 0 的整數，錢夠才轉。轉帳失敗時，所有人的餘額都應保持原樣。這裡不收手續費，也不會憑空增加點數。這些約定就是測試時的判斷依據，也常被叫作「規格」或「契約」。

成功轉帳後，把三人的點數加起來，應該跟轉帳前一樣多。轉帳失敗時，則連每個人的餘額都不該變。

只算總額還不夠。Alice 想付給 Bob，程式卻加到 Carol 身上，三人的總額照樣沒變。你還得逐一確認：誰少了多少、誰多了多少，沒參與付款的人有沒有被動到。

例：Alice 只有 3 點，要求轉給 Carol 6 點。

欄位 應寫的內容
規則 不允許餘額不足的轉帳；拒絕不改帳
初始狀態 Alice=3、Bob=7、Carol=0
輸入 Alice → Carol，6 點
預期 False／INSUFFICIENT_BALANCE，三人餘額不變
證據 留下轉帳前的餘額副本、這次轉給誰及多少點、程式回覆，以及轉帳後的餘額

QA 切入：程式說失敗，卻已經扣款

下面是刻意植入缺陷的教學版本，使用獨立的函式名稱，不取代第二堂的正常版本。貼到新的 Python 檔案執行即可，所需資料都在這段程式裡。

def apply_transfer_buggy(balances, sender, receiver, amount):
    if sender not in balances or receiver not in balances:
        return False, "UNKNOWN_ACCOUNT"
    if type(amount) is not int or amount <= 0:
        return False, "INVALID_AMOUNT"
    balances[sender] -= amount
    if balances[sender] < 0:
        return False, "INSUFFICIENT_BALANCE"
    balances[receiver] += amount
    return True, "APPLIED"


balances = {"Alice": 3, "Bob": 7, "Carol": 0}
before = balances.copy()
result = apply_transfer_buggy(balances, "Alice", "Carol", 6)
print("轉帳前", before)
print("程式回覆", result)
print("轉帳後", balances)

這次回覆是 (False, 'INSUFFICIENT_BALANCE')，Alice 卻從 3 變成 -3，Bob 仍是 7、Carol 仍是 0。只檢查回覆會以為測試通過；逐帳戶核對才發現「拒絕不改帳」被破壞。扣款發生在餘額檢查之前，失敗時也沒有把它還原。

第二堂正常版本在扣款前就檢查餘額。用那個版本、同一組初始資料再跑，應回覆相同的失敗原因，但餘額維持 Alice=3、Bob=7、Carol=0。先固定規則，再用同一輸入比較兩個版本，就是這個實驗的測試方法。

診斷判讀

  1. 銀行管理自己的帳務系統；區塊鏈由參與者依該鏈的規則提出、檢查及接受交易紀錄。重點是分清誰能做什麼。使用區塊鏈仍要了解它的管理方式，以及哪些條件值得信任。
  2. Alice 只有 10 點，兩筆合計卻要付 13 點。處理第二筆時，要用第一筆處理後的餘額來檢查。
  3. 多複製幾份，仍可能各自收到不同順序的付款要求。還需要規則，決定大家接受哪份紀錄。
  4. 查指定收款人有沒有收到正確金額，再核對交易成功、失敗或待處理，以及是否達到要求的確認程度。第一週能想到「還要查實際紀錄」，就抓到了方向。
  5. 兩個名字指向同一個 dict，透過哪個名字改它，看到的都是同一份改動。本週的簡單餘額表可以用 copy() 留下舊值；之後遇到表裡又包著其他表的資料，要再學怎麼複製。
  6. 這題是讓你說出疑問，沒有標準答案。暫時想不到也可以。

A 與 B1

T1→T2：T1 成功得 (Alice=3, Bob=7, Carol=0)，T2 被拒，維持原狀。

T2→T1：T2 成功得 (Alice=4, Bob=0, Carol=6)，T1 被拒，維持原狀。

兩種算法的總額都還是 10 點，但付到的人不同。不能拿第一種的 Bob=7，再拿第二種的 Carol=6，拼成一份帳本，這樣就超過原本的 10 點了。兩台電腦要接受同一份結果，還需要共同決定交易順序的規則。

T2 (True, 'APPLIED') {'Alice': 4, 'Bob': 0, 'Carol': 6}
T1 (False, 'INSUFFICIENT_BALANCE') {'Alice': 4, 'Bob': 0, 'Carol': 6}

題目 參考結果
B2 兩種順序都成功，最後 Alice=0、Bob=7、Carol=3；中間狀態不同
B3 INVALID_AMOUNT；狀態不變
B4 INVALID_AMOUNT；狀態不變
B5 INSUFFICIENT_BALANCE；狀態不變
B6 UNKNOWN_ACCOUNT；狀態不變
B7 兩次均成功，最後 Alice=4、Bob=6、Carol=0；模型沒有識別重送

B7 會扣兩次款，因為程式每收到一次要求，就再算一次。這是不是 Bug，要看系統答應使用者什麼。

如果系統答應「同一筆付款重送，也只扣一次」，就得能辨認哪幾次要求屬於同一筆付款，例如使用可辨識的付款編號，再約定已處理的編號怎麼回覆。光看金額和收款人還不夠，因為使用者也可能有意付兩筆相同金額。

這種讓同一次操作重送也不重複扣款的要求，會用到「冪等」這個詞。真實鏈上的 Nonce、UTXO 另有各自規則，後面會再學。本題能指出這段程式還分不出重送與另一筆付款，就抓到問題了。

C 參考結果

C1 的錯誤版本回覆 False／INSUFFICIENT_BALANCE，餘額卻成為 Alice=-3、Bob=7、Carol=0；正常版本回覆同樣的失敗原因，維持 Alice=3、Bob=7、Carol=0。規則是拒絕不改帳；回覆正確但餘額錯誤，仍判失敗。

C2 的預期是拒絕且維持 Alice=4、Bob=2、Carol=9。錯誤版本回覆失敗，但實際 Alice=-1、Bob=2、Carol=9；正常版本維持原狀。缺陷在扣款早於餘額檢查，證據須保留兩個版本各自的起始值、呼叫、回覆與結果。看過此答後重做，改用 Alice=2、Bob=8、Carol=5，Alice 付 Carol 3 點；不要沿用前次已修改的餘額。

D 與驗收

午餐點數可以考慮交給公司用資料庫管理，因為大家已接受公司記帳與更正。資料庫仍要防止重複扣款、留下可查的紀錄，出錯時也得能處理。

幾個組織一起記帳的情境，還要問大家是否願意共同管理資料庫，或者接受限定成員參加的網路、公有鏈。誰決定規則、哪些資料能公開、要花多少錢，都會影響選擇；光靠題目這幾句話，還選不出唯一答案。

  1. Alice 要付給 Bob 的要求是交易；付完後每個人剩多少是狀態；依序留下的轉帳紀錄屬於帳本。圖中的 A、B、C 是節點，收到交易後會按當時餘額和規則檢查，但它們收到的順序可能不同。
  2. 驗證像是在問「照現在的餘額與規則，這筆能付嗎？」共識則處理「大家接受哪份交易紀錄」，也要說清楚這套做法能成立的條件。
  3. 這段程式還沒有確認付款人授權的簽章、節點之間的網路、共識或辨認重送的機制。它算對餘額，也還不足以證明是一條安全的區塊鏈。
  4. 只加總所有人的錢，會漏掉付錯人的問題。還要逐一核對 Alice、Bob、Carol 各自應該增減多少。
  5. 以下依 Alice、Bob、Carol 的順序寫餘額：先 T1 得 (4,8,0)，T2 被拒絕；先 T2 得 (5,0,7)，T1 被拒絕。
  6. Owner 2 用自己的私鑰簽「前筆交易與 Owner 3 公鑰」的摘要。用前筆，也就是圖中中間交易留下的 Owner 2 公鑰核對。有效簽章證明相應授權，仍需判斷資產是否已花費及採用哪份歷史，不能同時接受衝突花費。讀圖欄的中間交易則是 Owner 1 簽、Owner 2 收，以左邊交易的 Owner 1 公鑰核對；欄位非空沒有執行這些核對。

本輪方法修正

原做法逐份找必讀連結，再從任務倒推材料；作者若漏出題，重要圖與原理也可能一起漏掉。本輪加入來源與任務兩個方向的核對，逐章製作時必須執行：

  1. 作者先讀本章採用的一手來源與版本，列出重要概念、圖、因果關係、前提及限制。每項標成「本章必修／後章必修／選讀／不採用」，寫理由與實際教材段落。後章只有大綱就標「待製作」，不能當成已有教學。
  2. 再由每項必修操作與驗收倒推先備、資料、規格、示範、提示及補課，核對是否全在 HTML。先用具體案例說明用途，再逐步比較資料與結果，最後接上名詞；必要術語初次出現就解釋，切換資料模型時先交代兩者的關係。每個必修概念應能交代誰做什麼、處理哪些資料、步驟與理由；圖須解釋標籤及關鍵連線，不能只放圖或留下結論。核對用的長字串與進階細節可放同頁展開區，必要機制與限制保留在主文。
  3. 分別核對來源是否漏教、說法是否準確、練習是否教過、答案是否可重算、HTML 是否可讀。補課須提供另一個具體例子或拆解方式，不能只叫學員重讀；驗收須含新情境與包內補課後的新變式，不能只靠作者自己出的題目或關鍵字掃描宣稱涵蓋完整。
  4. 沿既有章節審查紀錄保存來源、落點、延後理由與證據，不另建學員帳本。若未由另一位審查者核對，明示作者自查；技術 PASS、來源涵蓋與真人理解分開回報。
  5. 對後章先備先提供當前理解必需的最小內容。超出估計時間就調整時程、拆章或縮小已明示的學習目標；不把理解必需的圖與機制壓成一句，也不把來源全文照搬當成教學。

讀者仍從一個 HTML 學習。來源分類與核對由作者負責，不要求讀者常回原文幫教材找缺漏。這套方法降低漏教風險，不能保證完全無遺漏。
