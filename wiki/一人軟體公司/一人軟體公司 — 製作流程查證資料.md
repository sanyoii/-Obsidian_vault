## 1. 盤點另外兩家公司與擁有者的全域規矩

**結論**

- 測試公司與 AI-一人公司都沒有固定的派工單範本，也沒有「角色對應哪個模型」的設定檔。派工要給什麼、怎麼收回來驗，兩家都有寫，但散在好幾份文字條文裡。
- 兩家各自獨立寫出了幾乎一樣的幾條規矩：同一時間只有一個在寫、被派出去的不能再往下派、同一件事最多做一次加修一次、交回來要從四種狀態選一種、主對話要親自重跑檢查。這幾條可以取做法，文字重寫。
- 兩家都把角色做成「員工卡」。角色由同一個 AI 依序換身分來扮演，沒有一直開著的角色 AI。測試公司自己的顧問團發現 16 個角色只有 4 個真的上場過。
- 這間公司還缺的東西：固定的派工單與交回檔格式、檢查交回檔缺不缺欄位的指令、能力等級對應模型的設定檔。第一樣已經寫進草案，第二樣排在開第一個功能型案子時寫，第三樣草案放在每台電腦自己的設定檔。

### 1.1 來源上的限制

這間公司的 `來源與採用.md` 寫明：AI-一人公司是付費課程買來的系統，測試公司的原始架構也來自同一套課程包。課程網站的服務條款有一條限制重製、改作與散布，有沒有涵蓋買家拿到的系統檔案，條款沒有講清楚。所以參考這兩家時只看做法，文字和程式全部自己重寫，不複製任何一份檔；出售之前要向課程賣方取得書面答覆。

這一節的所有內容都只寫到做法層級，不引用兩家檔案的原文。

### 1.2 兩家公司並排

| 項目 | 測試公司 | AI-一人公司 |
|---|---|---|
| 做什麼 | 替別人的軟體做測試並交付報告 | 產出內容：社群貼文、簡報、銷售頁，另有日常營運 |
| 規則入口 | 一份入口檔，另有資料格式、機制、派工方法各一份 | 一份入口檔，另有常駐機制、人設、資料格式、安裝說明各一份 |
| 各家 AI 工具怎麼載入 | Claude Code 用一份只有三行的載入檔匯入入口；Codex 直接讀入口；沒有 Gemini 的載入檔 | Claude Code 用薄載入檔匯入三份；Codex 讀入口，其餘靠開場時自動附帶；沒有 Gemini 的載入檔 |
| 角色數 | 16 張員工卡、94 項能力，另有 6 條流程和 1 個派工入口 | 66 份做法檔，其中 18 份有員工卡（11 個執行角色、4 個治理角色、3 張其實是流程） |
| 角色卡的固定欄位 | 名稱、類別、部門、狀態，加一張能力表 | 大致相同，各卡之間欄位不完全一致 |
| 角色卡沒有的欄位 | 模型或能力等級、禁止事項、交接對象 | 同左，另外也沒有輸入輸出欄 |
| 角色是不是一直開著 | 不是。主對話依序套用各角色的方法 | 不是。同左 |
| 預設要不要派出去 | 預設不派。子任務獨立、範圍明確、能客觀驗證、交接成本划算才派 | 簡單工作直接做。缺角色時由主對話挑當下可用的幫手 |
| 派工時要給的東西 | 五樣：要給什麼、照哪份做法、結果放哪、怎樣算完成、被擋住時怎麼辦 | 八樣，大致是：目前狀況、做到哪裡為止、已經同意的設計、要讀的資料、檔案的歸屬、不能動的東西、怎麼驗收、什麼時候停 |
| 固定的派工單範本 | 沒找到 | 沒找到。只有一份已歸檔的實驗計畫裡有一組固定欄位 |
| 對被派者的限制 | 不能再往下派；同一時間只有一個在寫，其他只能讀；會改產品狀態的操作不同時做 | 相同，另外要交實際的差異、指令結果、產出與沒驗到的項目 |
| 同一件事最多做幾次 | 一次初次交付加一次定向修正；換模型或換人接手不重算 | 相同。另外有兩處訂了更早的停損：退回兩次沒有改善就縮小範圍或換人接手，改到第三次還沒好就停下來問 |
| 交回來的狀態 | 四選一：完成、完成但有疑慮、缺資料、卡住 | 四選一，名稱幾乎相同 |
| 誰驗收 | 主對話讀回成果並重跑檢查；重要的結論交另一家 AI 唯讀覆核，沒留覆核檔就當作沒覆核 | 主對話讀原始來源與實際修改並重跑關鍵檢查；主對話自己驗不能叫獨立驗收 |
| 什麼時候停下來 | 額度用完、規格互相衝突、需要擴大範圍、權限不夠 | 相同 |
| 自動檢查 | 8 支腳本，其中一支檢查公司結構（卡、能力、工具、知識互相對不對得上） | 沒有單一的結構檢查；建置工作台的程式順便驗引用，另有語氣檢查與寫檔前的硬性攔截 |
| 檢查會不會自動觸發 | 不會，要人或 AI 記得去跑 | 部分會：寫檔前的攔截是自動的 |
| 角色對應哪個模型 | 沒有設定檔，條文明寫角色名稱不代表模型 | 員工卡沒有；另一個 AI 工具的全域設定裡有幾個候選幫手，模型名稱前後寫法不一致 |
| 用量怎麼記 | 只記拿得到的數字，缺的不當成零，沒有統一的用量紀錄 | 排程工作逐階段記；派工用量只記拿得到的 |
| 每案問幾題、被推翻幾次 | 沒有這種紀錄 | 沒有這種紀錄 |
| 跨對話怎麼接 | 一份現況看板加交接資料夾，交接沒有固定格式 | 現況看板、跨對話的工單、決策卡三條線，另外自動保存對話紀錄 |

### 1.3 兩家各有哪些流程

| 公司 | 流程 | 重點 |
|---|---|---|
| 測試公司 | 接案（7 步） | 缺目標或窗口時只做訪談；提案與範圍要使用者和客戶確認才往下 |
| 測試公司 | 測試交付（19 步，五站） | 範圍、需求與風險與判準與環境、執行、證據覆核、交付。沒有授權、版本、判斷依據、隔離環境或預算就不進執行 |
| 測試公司 | 回歸（7 步） | 一個案例都沒選到要當成缺口 |
| 測試公司 | 專項（7 步） | 資安與效能兩條按需分支，沒有工具和適任的覆核者就記為擋住 |
| 測試公司 | 結案（6 步） | 先確認客戶驗收；請款草稿等核准；把確認過的缺陷類型記下來 |
| 測試公司 | 知識與成長（6 步） | 覆核過的結果才拿來整理，先確認權利再去識別 |
| AI-一人公司 | 內容產線 | 三種審查路線：已確認的母稿直接做、低風險短內容走精簡路線、長篇或方向未定走標準路線。每個平台的稿在標成完成前都要過品質關卡 |
| AI-一人公司 | 簡報、銷售頁、檔期 | 各有固定步驟；銷售頁的自我檢查是擋住式的，三張清單有一項不過就退回 |
| AI-一人公司 | 每日出貨、夜班、會議整理 | 沉默、排程到期、通過品管都不算發布的授權；對外動作一律要人確認 |

兩家的品質關卡有一個共通做法：把「需求有沒有符合」和「專業品質」分開寫，各自寫過、退、沒驗，必要項目全過才算過；通過不等於可以發布。

### 1.4 兩家自己記下的教訓

| 教訓 | 出處 |
|---|---|
| 規則只是文字約定，AI 忘了的時候沒有東西擋住它 | 測試公司 2026-11-14 顧問團與它自己的機制檔；AI-一人公司因為同樣的原因補了寫檔前的攔截 |
| 16 個角色只看到 4 個上場；結論是不再加角色、不再加文字規則，改做「沒讀方法就擋下來」的檢查 | 測試公司 2026-11-14 顧問團 |
| 同一個 AI 自己審自己是結構上的缺陷 | 同上 |
| 規則讀了不等於照做：語氣規則實測三次，AI 讀完照樣寫錯，所以改成機器檢查 | AI-一人公司的語氣檢查腳本 |
| 外部 AI 工具失敗時可能回報成功：權限被拒卻結束碼是 0、輸出全空；工具版本太舊時錯誤只出現在串流裡 | AI-一人公司的跨工具做法檔 |
| 兩個 AI 工具同時改同一個資料夾會出事，所以訂「一個工作區同時只有一位寫入者」 | AI-一人公司的協作決策 |
| 每次開對話自動塞進 AI 的內容太多，盤點後把擁有者電腦上常駐的做法檔從 77 份封存到剩 36 份（電腦層的，不是公司自己的 66 份） | AI-一人公司 2026-11 的工單 |
| 流程圖檔和流程的文字步驟對不上 | 測試公司的測試交付流程（這次盤點看到的，是否造成實際問題沒有查） |

### 1.5 擁有者的全域規矩

全域規矩是擁有者給所有專案共用的一份規則。跟派工、驗收有關的有這幾條：

| 規矩 | 內容 |
|---|---|
| 主對話不下場 | 預期輸出很長、要讀很多檔、要抓網頁、要掃整個版本庫、要批次改檔的工作，派給幫手，主對話只收結論 |
| 派工三件套 | 目標與動機、可以執行的驗收條件、回報格式，缺一樣就不派 |
| 驗收不由自己驗 | 驗收派給沒看過過程的 AI；機械式的批次工作例外，主對話親自跑驗收指令即可 |
| 交付契約 | 派出去和收回來用同一張表：交付項目、可執行的驗收指令、狀態。主對話親自跑驗收指令才算完成，不採信敘述 |
| 驗收腳本要先看過它失敗 | 沒看過它失敗，就不知道它在測什麼 |
| 失敗要大聲說 | 跳過的、不確定的、沒測到的，都要明講 |
| 每做完一步交代一次 | 已完成、已驗證、還剩什麼 |
| 視覺提案附示意圖 | 要人判斷看起來怎樣的提案，一定要畫出來 |

這一小節依據的是全域規則的入口檔。細則檔當天主對話讀過，但沒有另外寫成盤點報告，所以這裡只列到入口檔寫的程度。

### 1.6 可以搬、要改寫、還缺

「草案怎麼接」那一欄是對照製作流程草案第三版寫的。

| 分類 | 做法 | 來自 | 草案怎麼接 |

| 可以搬 | 交回來從四種狀態選一種 | 兩家公司 | 交回檔的四種狀態 |
| 可以搬 | 同一時間只有一個在寫 | 兩家公司 | 同一時間只有一個在改程式，沒有例外 |

| 還缺 | 固定的派工單與交回檔格式 | 兩家都沒有 | 草案第 3 節 |

| 還缺 | 更新包、工作台、公司結構檢查 | 兩家都有 | 等案子用到才做（這間公司的規矩 3） |
| 這間公司有、兩家沒有 | 每個案子記問了幾題、被推翻幾次 | 這間公司的規矩 5 | 繼續記 |

### 1.7 沒查到、沒實測

- 兩家公司都沒有執行任何腳本，全程只讀。
- 「沒有固定派工單」「沒有模型設定檔」「衝突時以誰為準沒有明文」都是搜尋後沒找到的結論。兩家各有一批沒讀的資料夾（工具自己的設定資料夾、各案件的資料夾、私人紀錄），裡面如果有就會推翻。
- AI-一人公司哪些檔是課程原廠的、哪些是擁有者自己改的，逐檔分不出來。
- 測試公司的盤點報告把員工卡架構的來源寫成「作者與授權查不到」；這間公司的 `來源與採用.md` 寫的是來自課程包。這一頁照公司的來源紀錄寫。
- 另一個 AI 工具（Codex）現在能不能用，兩處紀錄不一致：AI-一人公司有一張決策卡記它停訂，這間公司的實作計畫記它測過可用。沒有重測。
- 全域規矩的細則檔沒有留下盤點報告。

## 2. Agent Skills 跨工具的查證

Agent Skills 是一種公開的檔案格式：一個資料夾裡放一份 `SKILL.md`，開頭幾行寫名稱和用途，下面寫做法。AI 工具開場時只讀名稱和用途，用到時才讀全文。

**結論**

- 拿 `SKILL.md` 當「不綁工具的做法檔」可行，前提是只用規格規定的兩個必填欄位（名稱、用途）。查的 8 個工具官方文件都說會讀。
- 規格完全沒有規定「在乾淨的上下文裡執行」這件事。`SKILL.md` 載入後是進到目前這個對話裡。要乾淨的上下文，得靠各家自己的幫手機制，或用指令列另外開一個。
- 幾個工具共用的資料夾 `.agents/skills`，有 7 個工具會讀，Claude Code 不讀。所以沒有一個資料夾是 8 個工具都讀的。
- 各家都有「不用互動、下一行指令就跑」的方式，這是最接近通用的開新上下文做法。全部只讀了文件，沒有實測。

### 2.1 公開規格規定了什麼

來源：`https://agentskills.io/specification`（親讀；頁面沒有版本號和日期）

| 項目 | 規定 |
|---|---|
| 結構 | 一個資料夾，裡面一定要有 `SKILL.md`；可以另外放腳本、參考資料、素材 |
| 名稱 | 必填。1 到 64 個字，只能用小寫英文、數字和連字號，開頭結尾不能是連字號，不能連續兩個連字號，而且要跟資料夾同名 |
| 用途說明 | 必填。1 到 1024 個字 |
| 其他欄位 | 授權、相容性、自訂資料、允許使用的工具，都是選填。最後一項標為實驗性，各家支援不一 |
| 載入方式 | 分三層：開場只載入名稱和用途（約 100 tokens）；用到時載入全文（建議 5000 tokens 以內、500 行以內）；附檔要用才讀 |
| 幫手或獨立上下文 | 整頁沒有任何規定 |

名稱的限制是做法檔的資料夾必須用英文名的原因。檔案裡面的說明可以寫中文。

### 2.4 「新的上下文」沒有想像中乾淨

- Claude Code 的官方頁自己寫了：指令列模式不加特定參數時，會載入所在資料夾的規則與做法檔。

- 所以「審查的一方沒看過製作過程」目前靠的是不把檔案交給它，以及要求它不要去讀，沒有機制保證。

## 3. 多個 AI 分工的證據

**結論**

- 「同一時間只讓一個 AI 改程式」有四家公司的公開說法支持，方向一致，但都沒有附對照實驗的數字。
- 「規格寫成檔，再開新的對話照規格做」「審查的一方不看製作過程」是 Claude Code 官方文件的建議，頁面沒有附量測。
- 直接量過做法好壞的只有兩項，而且都是還沒經過其他學者審查的論文（下面叫預印本）：測試獨立寫（不看有錯的程式）找到的缺陷比較多；一個同模型加一個不同模型的審查者，比兩個同模型的找到更多。
- **沒有任何量測支持「七個角色」這個數字，也沒有任何量測支持「切成五段」這個切法。** 草案的五個階段是照上面幾條原則排出來的設計，沒有被量測證明過。
- 這次引用的資料裡，沒有任何一篇確認經過同儕審查。

### 3.4 只是各家經驗、沒有證據的

- 七個角色各一份做法檔，比「少數階段加獨立驗證」好：查不到任何量測。
- 研究、需求、規格要不要各用一個獨立的上下文：沒有量測。Anthropic 對互相依賴的前期工作傾向不拆。
- 前端和後端分給兩個 AI：只有七角色那篇文章主張。Anthropic 與 Cognition 的原則都反對在互相依賴的地方拆開。
- 人工檢查點要幾個、放哪裡：全部是經驗。
- 「用到才讀的做法檔比常駐的角色設定好」：沒有任何來源量過，是設計上的推論。
- 沒找到「同一批專案，AI 先寫測試對比後寫測試」在完整 Web App 上的對照。

### 3.5 最弱的假設，以及什麼會推翻它

| 最弱的假設 | 什麼證據出現就會推翻 |
|---|---|
| 把一個人加 AI 做中小型 Web App，比照大公司的產品場景與研究任務來推論 | 在有資料、有商業邏輯的 Web App 上，同模型、同預算，七角色流程比「單一 AI 加獨立驗證」在驗收通過率、重做次數、用量上有穩定優勢 |
| 獨立審查比自己審好 | 在真實的合併請求上，獨立審查者找到的缺陷，跟「自己審加測試加自動檢查」沒有顯著差別 |
| 測試先寫（不看實作）比較好 | 在完整應用上，先寫與後寫沒有差別 |

另外，多數資料來自 2026 年的新模型和還沒審查的預印本。模型進步很快，這些結論可能很快過時。

## 4. 7-Agent 工廠的來源

7-Agent 工廠是擁有者之前在其他專案用過的一套做法：把做軟體拆成七個 AI 角色接力，中間有三個等人確認的檢查點。

**結論**

- 七個角色的設計原型是一篇公開文章。
- 付費課程提供的只有四個軟體業通用的設計模式觀念。
- 這套做法沒有任何量測，文章裡的時間與通過數是示意。
- 擁有者實際用過，後來因為換了 AI 工具而帶不走。

### 4.1 三個來源

| 來源 | 工廠從它拿了什麼 | 查證程度 |
|---|---|---|
| 一篇公開文章：@sairahul1 在 X 發表的七代理設計（2026-05-25），中文由 blocktempo 轉譯 | 七個角色（查程式碼現況、寫使用情境、寫規格、後端、前端、只寫測試不改程式的測試員、只讀不改的驗證員）、三個人工檢查點、前後端同時做、沒過就退回重做 | X 的原文抓不到，只讀到一個轉錄頁：`https://youmind.com/landing/x-viral-articles/claude-code-software-factory-agents`（二手）。「原型是這篇」的依據是擁有者 Wiki 裡工廠那一頁的紀錄，以及 2026-07-02 的對照結論「文章與現有工廠是同一套設計」 |

事後在這四個專案的版本紀錄裡，找不到工廠格式的規格資料夾與交接檔。所以當時用了哪幾個角色、用量多少，沒有紀錄可查。

### 4.3 文章本身的證據

依轉錄頁，文章沒有任何量測、沒有公開的程式庫、沒有對照。文中的「2 到 3 小時」是估計，「7 項過 1 項沒過」是示意，約 280 萬次瀏覽只能說明熱度。

它的七個「角色」實際上是六個階段（查現況、寫情境、寫規格、建置、測試、驗證），用工具權限區隔（只讀、限定資料夾）。其中「寫測試的不改程式」「驗證的不修」兩條，跟第 3 節的證據方向一致。

### 4.4 沒查到、沒實測

- X 的原文沒有抓到。
- blocktempo 轉譯頁這次沒有重新讀，也沒有留網址。
- 課程的售價與條款沒有查。能不能把從課程學到的通用觀念寫進要賣的公司，沒有問過。這間公司只取通用做法，沒有用課程的文字。
- 工廠在那四個專案的成效沒有任何數字。

## 5. 擁有者的九份測試範本與草案的對照

擁有者自己寫過九份測試文件的空白範本，放在他的 RiskQADemoSite 版本庫（範本版本 0.3.0）。2026-11-26 他提出「有用就搬過來公司直接用」。

**結論**

- 九份裡八份接得上，第九份整份綁在那個專案的儀表板上，沒有搬。
- 這批範本是「拿做好的版本去測，再由人決定能不能放行」用的。最完整的三份接在審查和交付，寫測試那一段只用到其中一張表。
- 範本補上了草案原本缺的三塊：先看風險再決定哪裡多測、預期結果要有根據、交付時有一份給人看的摘要。
- 範本的說明寫「空白範本與方法源自測試公司 2026-10-25 的範本」，而公司的來源紀錄規定測試公司的東西要重寫。搬之前先問了擁有者，他確認這九份是自己寫的，所以原樣搬。

### 5.1 每一份對到哪裡

對照當時用的是草案第二版。第三版已經照這張表改過。

| 編號 | 用途 | 對到草案哪個階段 | 跟草案第二版的關係 | 搬了沒 |
|---|---|---|---|---|

### 5.2 範本有、草案原本沒有的觀念

| 觀念 | 解決什麼問題 |
|---|---|
| 風險決定測多深 | 測試的力氣平均分，最怕壞的地方沒有測得比較深 |
| 選測試方法要寫理由 | 案例數量看起來很多，其實都在測同一種情況 |
| 預期結果要有根據，而且分等級 | AI 自己補一個「應該是這樣」當預期。沒有核准過的來源就標「假設」，來源互相衝突或沒定義就標「未知」 |
| 講清楚涵蓋到哪、沒涵蓋什麼 | 交出去時說得出這些測試證明了什麼、沒證明什麼 |
| 停止條件 | 什麼時候可以不再加測試，看風險，不湊數量 |
| 執行紀錄只能往後加 | 修好後的「過」把之前的「沒過」蓋掉，事後看不出曾經壞過 |
| 結果分五種，沒跑的不能從分母偷偷拿掉 | 沒跑的、跳過的被當成通過 |
| 沒過不等於產品壞了 | 測試寫錯、資料錯、環境錯，被算成產品的缺陷 |
| 嚴重程度和先修哪個分開；延後修不能降級 | 因為「先不修」就把嚴重的問題寫成輕微 |
| 修好不等於驗過，重測是新的一筆 | 做的一方說修好了就關掉 |
| 測試全過不會自動變成可以放行，放行由具名的人決定 | 通過的測試自己批准自己 |
| 交付狀態四種，照順序判 | 已知的問題被藏成「不確定」 |
| 同一個人、同一個上下文的自己檢查，不能叫獨立覆核 | 跟草案「審查的一方沒看過製作過程」同方向，範本講得更死：要人 |
| AI 當評審，或 AI 的輸出每次不一樣時怎麼測 | 多跑幾次挑最好的那一次。草案到第三版仍然沒有對應的做法 |
| 評估有到期日 | 幾週前的通過被當成現在還有效 |

### 5.3 草案有、範本沒有的做法

| 草案的做法 | 範本的情況 |
|---|---|
| 測試先寫，功能還沒做，全部要先失敗 | 沒有。九份都以「已經有一個做好的版本」為前提 |
| 寫測試的一方只看規格，不讀程式 | 沒有這條限制 |
| 做的一方不准改測試、不准改規格 | 不適用，範本不管怎麼做 |
| 同一時間只有一個在改程式 | 不適用 |
| 審查的一方不給製作過程的任何紀錄 | 只寫了同一個上下文的自己檢查不算獨立，沒有規定不准讀什麼 |
| 同一項最多做兩次就交給人 | 沒有次數上限 |
| 派工單、用量、介面約定、審查固定要試的七種情況 | 都沒有 |

這些都留草案原本的。範本不反對，只是沒寫。

### 5.4 份量怎麼對

- 範本自己的說明寫：九份是一整套備用的，不必每次都填九個檔。最少份量只留三樣紀錄（申請與設計、執行紀錄、放行摘要），其中執行紀錄和放行摘要每次都不能省。
- 範本依風險分三級，草案依改動大小分小、中、大，是兩把不同的尺。草案第三版的對法：小和中用最少份量，只取要用的欄位收進案件自己的檔；大的才把完整的範本複製到案件裡填。
- 範本最高那一級的門檻，在讀過的檔裡沒有找到。
