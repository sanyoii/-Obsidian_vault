# 一人軟體公司 — 製作流程草案第三版

> [!important] 方向已同意，還沒有在任何案子上試過
> 這是 2026-11-26 草案第三版的全文快照。擁有者同一天說方向可以。裡面的做法來自官方文件、公開文章、擁有者用 7-Agent 工廠的經驗和兩場顧問團，沒有任何一項在這間公司實際跑過。第三版照驗收找到的 37 個問題改過之後，沒有再驗一次。公司裡目前只多了 `測試範本/` 資料夾，流程的做法檔要等第一個功能型案子開案時才建。

> [!note] 怎麼讀這一頁
> 草案原本是寫給擁有者看的，所以文中的「你」是擁有者，「我」是寫草案的 AI。內文照當時的原文沒有改：裡面寫「還沒定案」「你點頭之前」「還沒提交」的地方，都是寫的當下的狀態。討論的經過看 [[一人軟體公司/一人軟體公司 — 製作流程討論紀錄|製作流程討論紀錄]]，依據看 [[一人軟體公司/一人軟體公司 — 製作流程查證資料|製作流程查證資料]]。

2026-11-26。草案第三版，還沒定案。第三版把你的八份測試範本接進來（範本 2026-11-26 已照你的要求搬進公司的 `測試範本/`）。流程本身在你點頭之前不建檔、不加規矩。


**這份管什麼**。有資料、有邏輯的軟體怎麼從一句話做到可以上線，例如「我想要做一個記帳軟體」。

**這份不管什麼**。提案與接案那一段還沒寫，排在這份之後。品牌網站這種要一直來回問你的工作，照舊由跟你對話的這一個 AI 做。畫面設計接在哪一個階段也還沒定，見第 7 節。

**證據的範圍**。下面的做法來自官方文件、幾家公司的公開建議、你用 7-Agent 工廠的經驗，和兩場顧問團。沒有任何一項在這間公司實際跑過。

**這一版驗過什麼**。第一版寫完後，我請一個沒看過這段討論的 AI 照第 4 節的派工單試做並找矛盾，它找到 32 個問題，第二版是照那些問題改過的。

**第三版改了什麼**。你說測試的部分已經有自己做好的範本。九份讀完之後，八份接得上，接在哪裡看第 10 節。凡是照範本改過的地方，文字裡都寫了「照測試範本幾號」。第 4 節的例子還是第二版的寫法，沒有跟著改。第三版寫完後，我請另一個沒看過討論的 AI 拿八份範本逐處核對，它找到 37 個問題（10 個會讓人做錯），這一版照那些改過。改完之後沒有再驗一次。

**用詞**。這份裡單說「範本」或「網站範本」，是指公司的網站起始專案；你的測試文件一律寫「測試範本」加編號。比較難懂的詞在第 10 節最後有一張小表。

每一個階段的做法是一份用到才讀的 `SKILL.md`。階段之間只靠檔案交接，預期換工具、換模型都帶得走，這一點還沒試過。

## 2　五個階段各自的做法

每一份做法檔都寫下面這五件事，加上在哪裡做。定案後一個階段一份檔，下面是每份的內容摘要。

### 階段一　定義與規格（主對話）

|  |  |
|----|----|
| 開始前要有 | 你的一句話。 |
| 做什麼 | 先講出理解，再一次問一題，把不確定的問完：誰用、資料存哪裡、要不要登入、做到哪裡算第一版。要查資料時可以派只讀不寫的幫手。然後寫出兩份檔。<br>你點頭之後，主對話照範本的說明開好專案空殼：複製範本、改名、安裝、確認範本的檢查全過。預覽要用到的雲端資源要你同意才建，併在檢查點一一起問。 |
| 交出 | `規格.md`，固定七節：要解決什麼、給誰用；第一版做什麼；第一版不做什麼（每一項標「之後做」或「不做」，兩種分清楚）；驗收條件（照測試範本 03 分情境：一個情境是使用的人要完成的一件事，例如「記一筆帳」；底下每條驗收條件有編號，寫成「先有什麼、做什麼、應該看到什麼」，並標明是正常、失敗還是邊界的情況；某一類沒有就寫原因；只能由人看的條件標「只能人工驗」）；介面約定（畫面上的按鈕文字、欄位名稱、網址，測試要靠這些找東西）；資料（存什麼、存哪裡）；風險（照測試範本 01 的風險表，每一塊寫四件事：壞了後果多嚴重、多容易發生或多不確定、能不能及時發現、能不能復原，再定哪裡要多測；不知道就寫不知道，不能自己填成低）。<br>規格最後附一張問題表，七個欄位照測試範本 00 原樣，重點是每一題影響哪幾條、答案從哪來與日期、要不要重驗。後面階段新問的題，由主對話補進這張表。<br>這三樣是把測試範本 00、01、03 要用的欄位收進規格，不另存三份；大的案子才另存完整的（見第 10 節）。<br>`任務清單.md`：每項任務對應哪幾條驗收條件，照先後順序排。 |
| 不做 | 不寫功能，不寫測試。 |
| 怎麼算做完 | 每條驗收條件都寫得出一支檢查，或標了「只能人工驗」並寫明人要怎麼看；你看過說可以（檢查點一）；專案空殼開好。 |

### 階段二　寫測試（新的上下文）

|  |  |
|----|----|
| 開始前要有 | `規格.md`；主對話開好的專案空殼，裡面還沒有功能。 |
| 做什麼 | 每條驗收條件至少寫一支測試；規格的風險一節標為後果嚴重的地方，多寫失敗和邊界的情況。從使用的人的角度操作：開瀏覽器、點、填、看。只靠規格裡的介面約定找畫面上的東西。 |
| 交出 | 測試檔、交回檔。交回檔多一張設計決定表（照測試範本 02）：每組測試為什麼選這種測法、預期結果根據規格的哪一條、涵蓋到哪、沒涵蓋什麼。標了「只能人工驗」的條件不寫測試，改在交回檔列出步驟和每一步該看到什麼（欄位取測試範本 04 的步驟表），之後由審查的一方照做。 |
| 不做 | 不寫功能，不改規格，不改專案的設定檔。不讀功能的程式。規格沒寫清楚的地方分兩種，照測試範本 02 的分法：規格有寫但不夠細的（例如沒寫小數怎麼算），照字面最直接的讀法寫測試，設計決定表標「假設」，列進「要問的」，狀態寫「有疑慮」；規格完全沒寫，或兩處互相矛盾的，那一條先不寫，標「未知」，狀態寫「缺資料」。兩種都不自己補一個預期結果。 |
| 怎麼算做完 | 一行指令能跑全部自動測試（只能人工驗的不算在內）。現在跑要全部失敗，而且失敗的原因是「功能還不在」，不是測試本身寫壞。功能還沒做就通過的測試要列出來，那一支多半什麼都沒測到。<br>限制：這時候測試多半在第一步就因為找不到東西而失敗，後面幾步寫得對不對，要等功能做出來才看得出來。 |

### 階段三　實作（新的上下文，一次一項任務）

|  |  |
|----|----|
| 開始前要有 | `規格.md`、任務清單裡的那一項、測試、目前的程式。 |
| 做什麼 | 只做這一項任務，做到它對應的測試通過。同一時間只有一個在改程式，沒有例外；一項交回、收下之後才派下一項。 |
| 交出 | 程式、交回檔。 |
| 不做 | 不改測試，不改規格，不做這一項以外的事。覺得測試或規格寫錯了就停下來，交回時狀態寫「缺資料」（這一項沒做完，要等答案），不自己改。 |
| 怎麼算做完 | 這一項的測試通過；先前通過的測試還是通過；範本的檢查（`npm run check`）通過。 |

### 階段四　審查（新的上下文，沒看過製作過程）

|  |  |
|----|----|
| 開始前要有 | `規格.md`、成品、怎麼把它跑起來。不給實作階段的交回檔、任務清單、案件紀錄、版本紀錄，也不給對話。 |
| 做什麼 | 把成品跑起來，照每條驗收條件親手操作一遍，不能只跑測試；標了「只能人工驗」的，照派工單上抄過來的步驟做。「親手操作」是指用操作瀏覽器的工具，真的把頁面打開來點、填、看，不是讀程式去推測。<br>再找規格沒寫到、但用的人會遇到的，至少這七種：空的資料、很長或錯的輸入、連按、重新整理、手機寬度、離線、電腦開著減少動態。派工單可以再加這個案子特有的。<br>最後讀程式，找資料會不會遺失、密鑰有沒有寫進去這一類問題。<br>驗收指令沒有全過也照樣審完，把失敗寫進交回檔。 |
| 交出 | 交回檔。每條驗收條件的結果用測試範本 05 的五種，值照原文寫：Pass（過）、Fail（沒過）、Blocked（擋住：前提沒備齊所以跑不了）、Skipped（決定不跑：只有派工單寫明才可以，要有理由）、Not Run（還沒跑），各寫下實際看到的。Fail 要寫原因是哪一類：產品、測試、環境、資料，分不出來就寫不知道。有任何一條是 Blocked 或 Not Run，交回檔的狀態寫「缺資料」。<br>每個問題取測試範本 06 的這幾欄來寫：重現步驟、預期、實際、建議的嚴重程度（S1 到 S4，定義照測試範本 06）、原因類別；畫面上的問題附截圖。 |
| 不做 | 不改規格、程式、測試。建置產生的檔不算。自己寫的臨時腳本和截圖，放在交接資料夾裡這次審查的附件資料夾。 |
| 怎麼算做完 | 每條驗收條件都有五種結果之一和證據，沒有留空的；七種情況每一種都寫了試的結果。重要的案子再加一位不同模型的審查者，兩位分開寫、不互看。 |

### 階段五　交付（主對話）

|  |  |
|----|----|
| 開始前要有 | 審查的每條驗收條件都是 Pass。Blocked 和 Not Run 的，主對話補齊前提後開新的審查補驗；Skipped 的列進交付摘要給你看。規格以外找到的每個問題都有決定：這一版修、之後修，或不修。 |
| 做什麼 | 先照測試範本 07 寫交付摘要（07 在測試範本裡叫放行摘要）。小和中的案子必填四段：一眼看懂的結論、還沒解決的項目、建議、你的決定；其餘段落寫「不適用：最少份量」。建議的值照 07 的順序判：有擋住交付的問題（包含還沒解決的 S1）寫 Blocked；沒有擋住、但還有沒修的問題或你接受的風險（之後修、不修、決定不跑的都算）寫 At Risk；沒有已知問題但缺根據寫 Unknown；都沒有才寫 Ready。<br>網站範本的部署檢查通過後，部署到預覽網址，連同交付摘要請你看（檢查點二）。你的決定照 07 的寫法記在交付摘要上：Go（可以）、No-Go（不行）、Hold（先擱著）。問題的嚴重程度是審查的一方建議的，你在這裡可以改。你說可以，再問要不要部署到正式網域。<br>你說還沒到，照規矩 5 分兩種：做出來的東西有錯或不夠，記一次推翻，先把你說的補成驗收條件和一支會失敗的測試，再回階段三；是你新增的要求，不算推翻，回階段一改規格。 |
| 交出 | 預覽網址上的成品；`交付摘要.md`；你點頭的話，正式網域上的軟體。案件紀錄裡補上問了幾題、被推翻幾次、用量、每個階段退回幾次和原因。 |
| 不做 | 沒有你點頭，不部署到正式網域（規矩 6）。 |
| 怎麼算做完 | 你在預覽網址上看過說可以，並且決定了要不要上正式網域。 |

## 3　交接規矩

這一節會寫成一份檔，五個階段共用。它同時就是之前說要寫的「臨時派幫手的規矩」：派出去靠派工單，交回來靠交回檔。

### 派工單：主對話寫，一次派工一張

第一行固定寫「路徑：都從這個案件資料夾算起」。規則入口和它要求先讀的檔、這次的做法檔、交接規矩，一律可以讀，不用列。

| 欄位 | 寫什麼 |
|----|----|
| 做法 | 這次照哪一份做法檔做。 |
| 目標 | 兩三句：要做出什麼、為什麼要這樣做。 |
| 可以讀 | 列出檔案或資料夾。 |
| 不准碰 | 列出不准改的檔案或資料夾。 |
| 要交出 | 哪些檔，放哪裡。 |
| 驗收指令 | 一行就能跑的指令，以及現在跑應該看到什麼。主對話收回來時會親自跑。 |
| 停下來 | 遇到什麼情況要停下來交回，不要自己硬做。 |
| 交回檔 | 交回檔寫到哪個路徑。 |

各階段的做法檔可以加自己的欄位，例如審查多了「不要讀」「怎麼跑起來」「另外要試」。

### 交回檔：做的那一方寫

| 欄位           | 寫什麼                                                    |
|----------------|-----------------------------------------------------------|
| 狀態           | 四選一，見下表。講的是這次派工做完沒，不是成品好不好。    |
| 做了什麼       | 五行以內。                                                |
| 關鍵決定       | 自己拿主意的地方，每個附理由。                            |
| 產出           | 檔案路徑清單。                                            |
| 驗收指令的輸出 | 貼上實際輸出的最後幾行。不能只寫「都過了」。              |
| 沒驗到的       | 沒測、沒看、不確定的，全部列出來。                        |
| 要問的         | 需要你或主對話決定的問題。沒有就寫「無」。                |
| 用量           | 這次用了多少 tokens。工具有顯示就記，沒有就寫「查不到」。 |

各階段可以加自己的欄位，例如審查多了「驗收條件」「規格以外找到的」。檢查除了共用的八欄，也要驗各階段多出來的：結果的值是不是那五種、嚴重程度是不是 S1 到 S4、設計決定表有沒有缺欄。

| 狀態 | 什麼時候選 |
|----|----|
| 完成 | 做完了，驗收指令的結果跟派工單寫的一樣。可以有「要問的」，但答案不會改變這次交出的東西。 |
| 有疑慮 | 做完了，但有一處是自己拿的主意，或覺得規格、測試有錯，答案可能會改變這次交出的東西。 |
| 缺資料 | 沒做完。少了某個檔或某個答案，補上就能繼續。 |
| 卡住 | 沒做完，而且不知道怎麼繼續。例如跑不起來。 |

### 收回來的時候，主對話做四件事

1.  欄位缺了就當沒交，退回去補。這一條會寫成檢查，一行指令能跑。
2.  親自跑一次驗收指令，不看敘述就算數。
3.  在案件的 `執行紀錄.md` 加一筆：誰跑的、哪個版本（還沒有程式就寫還沒有）、什麼環境、指令、每條的結果。這個檔只有主對話寫，只能往後加，之前的 Fail 不改不刪。欄位取測試範本 05；大的案子才每次另存一份完整的 05。
4.  審查的交回檔另外多做一步：照重現步驟，親自重現每一個「沒過」和建議為 S1、S2 的問題。驗收指令只驗得出成品，驗不出審查有沒有做確實。
5.  看狀態：有疑慮，主對話對照規格判斷，牽涉需求就問你；缺資料，補上再派；卡住，停下來告訴你。

### 退回規則

- **沒過就退回，退給誰看原因**。產品的問題：開一個新的實作上下文，派工單附上那一項的重現步驟和實際輸出。測試寫錯：退回寫測試階段。環境或資料的問題：主對話修好之後重跑，不退回實作。分不出來：主對話先查，查不出來就問你。
- **同一項最多做兩次**。第一次做，退回後再做一次。第二次還是沒過，就停下來交給你。
- **修完要再審**。開一個新的審查上下文，只審退回的那幾項，另外把全部自動測試再跑一次（自動測試重跑很便宜，所以比測試範本要求的多跑；人工驗的只重驗退回的那幾項）。再審是新的一筆執行紀錄，之前的「沒過」留著不改。做的一方說修好了不算數，要有新的一筆「過」才算（照測試範本 05、06）。
- **規格改了，先補測試再做**。不管是你回答了問題，還是審查找到規格沒寫的：先把它寫進規格，開新的上下文只給規格去補或改測試，確認新的測試現在會失敗，才派實作。沒有一支會失敗的測試（或一條現在驗不過的人工步驟），就不退回實作，因為做的一方不知道怎樣算修好。
- **審查找到規格沒寫的問題**。嚴重的（S1、S2）一定問你這一版要不要修。輕微的（S3、S4）由主對話先決定，交付時一起列給你看。
- **實作的一方說測試寫錯了**。主對話對照規格。規格寫得清楚、是測試錯，退回寫測試階段修，一樣開新的上下文、只給規格。規格本身不清楚，問你，改規格，算一題。
- **每次退回記一筆**。哪一項、原因是哪一類（規格不清、測試錯、實作錯、審查看錯、環境問題、資料問題、不知道；後三類是照測試範本 06 加的）。功能型軟體的推翻會從哪裡來，現在沒有資料，這一欄就是在收這個。

### 什麼時候停下來找你

固定的檢查點兩個：規格之後、看成品的時候。另外只有三種情況會停：有需求上的問題要問你（每問一次算一題）、同一項做了兩次還沒過、有一張交回檔的狀態是卡住。

### 依大小選路

| 大小 | 怎麼判斷 | 怎麼走 |
|----|----|----|
| 小 | 改字、改樣式、改設定。不動資料和邏輯，既有的檢查就驗得出來。 | 主對話直接做，跑既有的檢查，在案件的 `執行紀錄.md` 加一筆。要部署的話，交付摘要寫必填的四段，各一兩行就可以。你原本的範本說明寫：執行紀錄和放行摘要每次都不能省。 |
| 中 | 在已經有的軟體上加一個功能，或改一個功能。 | 規格只寫這個功能，可以很短。然後寫測試、實作、審查。檢查點只留看成品那一個。 |
| 大 | 一個新的軟體，或是動到資料怎麼存。 | 五個階段全走，兩個檢查點。 |

拿不準屬於哪一種，就往大的那一種算。

## 4　例子：派工單和交回檔實際長什麼樣子


下面用你舉的記帳軟體當例子。內容都是我編的示意，沒有真的跑過。裡面的 `test:acceptance` 這支指令範本現在還沒有，要等第一個功能型案子時才加（預計用範本已經裝好的 Playwright，自己把建置結果跑起來再測）。<br>這一節還是第二版的寫法，跟上面的新規則大約有十處不一樣：規格只有六節、沒有問題表、驗收條件沒分三類、審查結果是過、沒過、驗不了三種、問題只分嚴重和輕微、沒記版本，也沒有設計決定表、執行紀錄和交付摘要的例子。等寫做法檔時照測試範本補。


### 規格的節錄

```text
## 驗收條件
A1 新增支出。先有：空的帳本。做：金額填 120，類別選「餐飲」，按「儲存」。
   應該看到：清單第一列是今天的日期、「餐飲」、「120」；合計顯示「本月合計 120」。
A2 擋掉錯的金額。先有：A1 做完。做：類別選「餐飲」，金額留空，或填 0、-5、abc，按「儲存」。
   應該看到：清單還是只有 A1 那一列，金額欄下方出現「請輸入大於 0 的金額」。
A3 資料留得住。先有：A1 做完。做：重新整理頁面。
   應該看到：清單和合計跟重新整理之前一樣。

## 介面約定
金額：一般的文字輸入欄，標籤是「金額」。什麼字都打得進去，按「儲存」時才檢查。
類別：瀏覽器內建的下拉選單，標籤是「類別」。
儲存：一個按鈕，上面的字是「儲存」。
清單：一個表格，表格上方的標題文字是「這個月」。一列三格，依序是日期、類別、金額，
      例如「2026/11/26」「餐飲」「120」。金額只顯示數字，不加「元」。新的排在最上面。
合計：一行文字，例如「本月合計 120」。

## 資料
每筆支出存金額、類別、日期。日期自動帶今天，第一版不能改。
第一版存在這台裝置的瀏覽器裡，不同步到別的裝置。
```

### 例一：依規格寫測試

派工單，存成 `交接/01-寫測試-派工單.md`：

```text
# 派工單 01　寫測試
路徑：都從這個案件資料夾算起

做法：../../做法/write-tests/SKILL.md
目標：照規格替記帳軟體第一版寫驗收測試。之後做功能的人只能靠這些測試知道自己做對了沒，
      所以測試要照規格寫，不要照你猜的做法寫。
可以讀：規格.md、網站/（主對話開好的空殼，還沒有功能）
不准碰：網站/src/、規格.md、網站/ 底下的設定檔（package.json 這一類）
要交出：網站/tests/ 底下新增的測試檔，A1 到 A3 每條至少一支
驗收指令：npm --prefix 網站 run test:acceptance
          現在跑應該全部失敗，失敗原因是找不到畫面上的東西
停下來：哪一條驗收條件沒有答案就寫不出測試，那一條先不寫，狀態寫缺資料，不要自己補規格

```

交回檔，`交接/01-寫測試-交回.md`：

```text

- 寫了 4 支測試：A1 一支、A2 兩支、A3 一支。

  4 failed
```

交回檔，`交接/05-審查-交回.md`：

```text

狀態：完成
做了什麼：
- 建置後跑起來，用操作瀏覽器的工具把三條驗收條件各做一遍。
```

```text
├─ 做法/
│  ├─ 交接規矩.md           第 3 節的內容；試行時開頭放「到哪個階段讀哪一份」的表
│  ├─ define-spec/SKILL.md   階段一　定義與規格
│  ├─ write-tests/SKILL.md   階段二　寫測試
│  ├─ implement/SKILL.md     階段三　實作
│  ├─ review/SKILL.md        階段四　審查
│  ├─ ship/SKILL.md          階段五　交付
│  └─ 這台電腦.範例.md       下面那份設定檔的空白範例
├─ 測試範本/               你的八份測試文件範本（2026-11-26 已搬進來）
├─ 檢查/check-handoff.mjs    交回檔缺欄位就 FAIL
├─ 私人/這台電腦.md          這台電腦怎麼開新的上下文（不進版本庫）
└─ 案件/<編號>-<名稱>/
   ├─ 規格.md
   ├─ 任務清單.md
   ├─ 交接/                 每次派工一張派工單、一張交回檔，照順序編號
   ├─ 執行紀錄.md           每跑一次加一筆，只有主對話寫
   ├─ 交付摘要.md           檢查點二給你看的那一份
   ├─ 紀錄.md
   └─ 網站/
```

做法的資料夾用英文名，是因為 `SKILL.md` 這個格式的公開規格規定：名稱只能用小寫英文、數字和連字號，而且要跟資料夾同名。檔案裡面的說明照樣寫中文。

### 「新的上下文怎麼開」寫在一份設定檔

做法檔只寫「開一個新的上下文」，不寫怎麼開。怎麼開跟你這台電腦裝了什麼工具有關，所以放在 `私人/這台電腦.md`，換工具只改這一份。規矩 9 說的「三級能力各對應哪個模型」也寫在這裡。

```text
# 這台電腦

主要工具：（例如 Claude Code）
開新的上下文：
  工具內建的幫手：（怎麼叫。沒有就寫「無」）
  指令列：（例如 claude -p "讀 交接/01-寫測試-派工單.md，照它做"）
不同模型的審查者：（例如 codex exec "讀 交接/05-審查-派工單.md，照它做"。沒有就寫「無」）
三級能力各用哪個模型：
  規劃與驗收：
  一般實作：
  重複性工作：
```

|------------------|--------------------------|
| 定義與規格、交付 | 規劃與驗收（就是主對話） |
| 寫測試、實作     | 一般實作                 |
| 審查             | 規劃與驗收               |

## 6　我替你先選的十五個地方，都可以推翻

| 選了什麼 | 理由 | 代價 |
|----|----|----|
| 做法檔靠規則入口的一張表來指，不另外在各家工具自己的 skill 資料夾各放一份。 | 各家工具讀的資料夾不一樣，要兩邊都看得到，就得用連結（Windows 和版本庫都麻煩），或複製兩份再加一支同步檢查。只有五份檔，一張表就夠。檔案本身仍然是 `SKILL.md` 的格式，要放進哪個工具的資料夾直接複製就行。 | 不能在工具裡打一個指令就叫出某一份做法，要靠 AI 照表去讀。 |
| 固定的檢查點兩個。 | 工廠原本三個。你說少了的是「會停下來等我確認」，沒說要幾個，先從少的開始。 | 規格和成品之間，你看不到中間過程。 |
| 中型的工作不停在規格，只停在看成品。 | 加一個功能的規格很短，停兩次不划算。 | 規格理解錯的話，要到看成品才發現。 |
| 實作不分前端和後端，同一時間只有一個在改程式。 | Anthropic、Cognition、OpenAI、Google 的公開文章和文件都提醒：多個 AI 同時改程式會互相覆蓋。前端和後端正好是最互相依賴的地方。 | 大案子會比同時做慢。 |
| 審查的一方不讀實作的交回檔。 | Claude Code 的文件和 Cognition 的文章都建議審查者不要看到製作過程。 | 實作那邊寫的「沒驗到的」，要由主對話轉成派工單上的「另外要試」。 |
| 寫測試和實作用「一般實作」級，審查用「規劃與驗收」級。 | 照你全域規矩的分法：規劃用高的、執行用低的、驗收用高的。 | 沒有數據。測試寫得不好，後面全部受影響。 |
| 同一項最多做兩次。 | 你全域規矩裡的「同一類失敗兩次就停」。 | 你被打斷的次數可能變多。 |
| 規格固定七節。 | 寫測試的一方只拿得到規格，少一節它就得猜。前六節是照例子裡實際缺過的東西定的，第七節「風險」是照你的測試範本加的。 | 小功能也要寫七節，可以很短，但不能省。 |
| 交回檔的狀態只有四種。 | 主對話收到之後要做的事只有四種：收下、判斷或問你、補資料、停下來。 | 介於兩種之間的情況要硬選一種。 |
| 派工單和交回檔放在案件資料夾，跟著案件的版本庫。 | 事後查得到每一步，也算得出每個階段退回幾次。 | 案件資料夾會多出幾十個小檔。 |
| 規格和測試設計不記版本，版本從執行紀錄開始記，交付摘要記最後驗過的那一版。 | 規格和測試是在功能做出來之前寫的，那時候沒有版本可填。你原本的範本說明寫「不適用的欄位寫原因」。 | 規格改了之後，舊的執行紀錄對的是哪一版規格，要靠日期去對。 |
| 測試範本裡要具名的人簽核的地方，併進兩個檢查點，不另外停。其餘由主對話核對，並寫明「不是真人驗收」。 | 八份範本有六個簽核的小節，另外還有幾個要具名的人填的欄位。每一處都停，至少多出六次等你。 | 規格和成品之間，你少了親自看測試設計和執行紀錄的機會。 |
| 結果、交付狀態、嚴重程度的值照測試範本原文寫（Pass、At Risk、S2 這些）；另存完整範本時，欄位名稱也照原樣用英文。收進規格和交回檔的說明用中文寫。 | 你說直接用。值用原文，檢查才好寫，也對得回範本。這是內部工作文件，不是對外的頁面。 | 買這間公司的人如果不懂測試術語，會看不懂這些值。 |
| 問題的嚴重程度由審查的一方建議。S1、S2 當下就問你；S3、S4 主對話先決定，全部列在交付摘要，你在檢查點二可以改。 | 測試範本 06 是測的一方建議、委託的一方裁定，兩邊都留。每個問題都先問你，會多很多題。 | S3、S4 你要到看成品時才看得到。審查的一方把等級估低的話，嚴重的問題會晚一步到你面前。 |
| 小和中的案子，測試範本只取要用的欄位，收進規格、交回檔、執行紀錄、交付摘要，不另存八份。大的案子才另存完整的。 | 你原本的範本說明寫最少留三樣。八份空白的加起來九百多行，小功能填不完。 | 哪些欄位算「要用的」是我挑的，可能挑掉你在意的。 |

## 7　還沒寫的，和我不知道的

- **提案與接案**。公司目標的另一半，排在這份之後寫。
- **畫面設計接在哪裡**。功能型軟體也有畫面，規矩 11（示意圖、定案後做樣本）和規矩 13（減少動態）照樣適用。問題是測試要靠「介面約定」找東西，而介面約定要等畫面設計完才定得下來。所以設計多半要放在規格之後、寫測試之前，由主對話跟你做，還會多一個檢查點。這一段沒有寫進這份草案。
- **登入、資料庫、付款**。範本現在只有前端和 Cloudflare Workers，沒有這幾樣的做法。第一個功能型案子用到哪一樣，才補哪一樣。
- **「新的上下文」到底有多乾淨**。新開的上下文沒看過前面的對話，但工具會自動帶進規則入口、你的全域規矩，有的工具還會帶進自己記下來的記憶。記憶裡如果有這個案子的製作過程，審查的一方就不算完全沒看過。驗這份草案的那個 AI 就回報它被自動帶進了這些東西。怎麼處理還沒想好。
- **「不准讀」只能靠自律**。第一輪寫測試時功能還不存在，沒有這個問題。之後補測試時程式已經在了，派工單寫不准讀，但沒有東西真的擋得住。審查的「不要讀」也一樣。
- **沒有實機試過**。`claude -p`、`codex exec` 這些指令的寫法是從官方文件讀來的，沒有在這台電腦上跑過。Codex 現在還能不能用也沒測。「換工具也帶得走」是照文件推的。
- **用量不知道**。每個階段開一個新的上下文，要重新讀規格和程式，會比一個對話做到底貴。貴多少沒有數字，你那四個工廠專案也沒留下數字。
- **測試先寫，會不會因為介面一直變而一直改**。不知道。第一個案子看「測試錯」這一類退回有幾次。
- **這份有多可靠**。「規格寫成檔再開新對話」「審查者不看製作過程」是廠商的建議，沒有對照量測。「獨立寫測試比較抓得到錯」只有一篇還沒經過其他學者審查的論文。五個階段這個切法本身，沒有人量過。

## 8　你點頭之後會怎麼做

規矩 3 說角色和規則等案子真的需要時才加，所以不會現在就把這份變成公司的規矩。分兩步：

你的八份測試範本不等這兩步。2026-11-26 你要求搬，已經放進 `測試範本/`；規則入口的「東西在哪」加了一列，來源也記了。這三處都還沒提交。

### 第一步：開第一個功能型案子的時候

1.  新增 `做法/` 底下七份檔（交接規矩、五份階段做法、設定檔範例），檔頭標明「試行」。
2.  `AGENTS.md` 只在「東西在哪」加一列指過去，註明試行，不加規矩。「到哪個階段讀哪一份」的表先放在 `做法/交接規矩.md` 開頭，第二步才搬進規則入口。
3.  新增 `檢查/check-handoff.mjs`。先拿一張缺欄位的交回檔跑出 FAIL，再確認完整的會 PASS。它也要驗各階段多出來的欄位，以及執行紀錄和交付摘要的必填段落。
4.  網站範本加一支 `test:acceptance` 指令。
5.  `來源與採用.md` 記來源（規矩 2）。

### 第二步：那個案子做完之後

1.  照實際退回的紀錄修做法檔，拿掉「試行」。
2.  `AGENTS.md` 加規矩。目前想到的兩條：同一時間只有一個在改程式；測試先寫，做的一方不准改測試。
3.  `實作計畫.md` 更新。

Wiki 不等這兩步：今天的討論和這份草案照規矩 8 要補進去。Wiki 是公開的，我會先列出變更給你看過再提交。

第一個功能型案子要用哪一個，是下一題。做一個小的記帳軟體，這份草案直接能用。重做你既有的 Web App 跟原版比，如果它有登入或資料庫，要先補那一塊。

## 9　來源

除了最後一項是你自己寫的檔、原樣搬進來，其餘全部用自己的話重寫，沒有複製別人的檔。

- 你用過的 7-Agent 工廠：規格寫成檔、分段做、沒過就退回、檢查點、依大小選路。它的原型是一篇公開文章（blocktempo 轉譯 @sairahul1 的七代理設計），另外借了水球流課程講的設計模式觀念和 chan_yu_chen 的工作流。
- 你的全域規矩：派工要有目標、驗收條件、回報格式；驗收指令要親自跑；驗收腳本先在舊狀態跑出失敗；同一類失敗兩次就停。
- 你貼的 Agent Skills 那篇：照階段切，不照角色切。那套做法庫的角色設定是給專門的審查用的；它的審查和測試平常是在主對話裡跑做法檔，只有交付前的總檢查才同時派幾個角色。草案讓審查開新的上下文，依據是下一項的 Claude Code 文件和 Cognition 的文章，不是這一篇。
- Claude Code 官方文件：規格檔寫好就開新的對話照它做；審查者不看製作過程。
- Anthropic、Cognition、OpenAI、Google 談多個 AI 同時寫程式的公開文章與文件。
- agentskills.io 的公開規格：`SKILL.md` 的格式與命名限制。
- 兩場顧問團（2026-11-26）與會後你補的兩件事實。
- 你自己寫的測試範本（RiskQADemoSite 版本庫的 `Templates/QA`，版本 0.3.0）：八份原樣搬進 `測試範本/`，只改了一個連結。第九份和網頁版沒有搬。

## 10　你的測試範本接在哪裡（第三版新增）

九份裡八份接得上。它們原本是「拿做好的版本去測，再由人決定能不能放行」用的，所以最完整的三份（05、06、07）接在審查和交付；寫測試那一段只用到 02 的一張表。圖在下面。

藍色是草案已經有類似的、範本比較完整；綠色是草案缺這一塊、範本補得上；虛線是沒有對應。

| 階段 | 用哪幾份 | 補了草案什麼 |
|----|----|----|
| 一　定義與規格 | 00 測試申請、01 風險評估、03 測試情境 | 問題表；先看風險再決定哪裡多測（每條至少一支不變）；驗收條件分情境，再分正常、失敗、邊界 |
| 二　寫測試 | 02 的設計決定表；只能人工驗的用 04 的步驟表 | 預期結果要有根據，沒有根據就標「假設」或「未知」；講清楚涵蓋到哪、沒涵蓋什麼 |
| 三　實作 | 沒有 | 測試範本不管怎麼做，只管怎麼驗 |
| 四　審查 | 05 執行紀錄、06 缺陷報告 | 紀錄只能往後加；結果五種；沒過不一定是產品壞了；嚴重程度四級；修好不等於驗過 |
| 五　交付 | 07 放行摘要（填好的那一份在案件裡叫 `交付摘要.md`） | 檢查點二有一份給你看的摘要；交付狀態照 07 的順序判 |

### 依大小用多少

| 大小 | 測試範本用多少 |
|----|----|
| 小、中 | 最少份量（測試範本叫 QA-Lite）。只取要用的欄位，收進 `規格.md`、交回檔、`執行紀錄.md`、`交付摘要.md`，不另存八份。 |
| 大 | 把完整的 00 到 07 複製到案件資料夾再填，不適用的欄位寫原因，不刪掉。 |

大小照第 3 節那張表判斷，是同一把尺。測試範本還有一級 QA-High-Risk，它的門檻在範本裡沒有寫，這裡也還沒定。

**測試範本沒有、留草案原本的**：測試先寫而且要先全部失敗；寫測試的一方不讀程式；做的一方不准改測試；審查的一方不看製作過程；同一項最多做兩次；派工單；用量。

**跟測試範本不一樣的三處，都列在第 6 節**：簽核併進兩個檢查點；嚴重程度不是每個都先由你裁定；小和中的案子不另存整份範本。另外，修完再審時自動測試全部重跑，比範本要求的多。

### 比較難懂的詞

| 詞 | 意思 |
|----|----|
| 情境 | 使用的人要完成的一件事，例如「記一筆帳」。一個情境底下有好幾條驗收條件。 |
| 邊界 | 剛好踩在界線上的情況，例如金額填 0、填到上限、月底最後一天。 |
| 版本、候選版本 | 程式在版本庫裡的哪一次提交。測的是哪一版要記下來，不然事後對不回去。 |
| S1 到 S4 | 問題的嚴重程度，定義照測試範本 06。S1：主要流程不能用而且沒有別的辦法，或資料毀損遺失、金額算錯、安全或隱私外洩。S2：主要功能或結果錯，只有很麻煩的替代辦法。S3：次要或邊界的錯，有簡單的替代辦法。S4：文字或外觀，不影響功能。 |
| 專案空殼 | 從網站範本複製出來、裝好套件、還沒有任何功能的專案。 |
| 建置 | 把原始檔轉成可以放上網的成品。 |
| Playwright | 用程式操作瀏覽器的測試工具，網站範本已經裝了。 |
| tokens | AI 讀和寫的字數單位，用量用它算。 |

**還沒做的**：這一節的接法沒有在任何案子上試過。第 4 節的例子沒有跟著改。測試範本講「AI 當評審，或 AI 的輸出每次不一樣時怎麼測」的那幾段，草案還沒有對應的做法。測試範本 01 提到五份附加的表（測試資料表、環境準備、資安隱私清單、無障礙相容矩陣、遷移驗證計畫），這裡沒有，遇到時先寫不適用和原因。「哪些欄位算要用的」只講了大方向，確切的欄位要等寫做法檔時定。
