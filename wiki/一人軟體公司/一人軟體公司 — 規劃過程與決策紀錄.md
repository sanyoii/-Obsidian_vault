# 一人軟體公司 — 規劃過程與決策紀錄

> [!important] 第一版規劃已定案，公司只建了最小的一版
> 2026-11-19 在一場對話裡完成規劃，同一天建了最小的一版公司（見 2.10）。這頁是過程快照；現行的計畫在 `D:/一人軟體公司/實作計畫.md`，就是原本的一頁規劃，同一天搬過去。第 0 號案子還沒開始，下面的做法都還沒經過實測。用到的素材見 [[一人軟體公司/一人軟體公司 — 規劃素材與來源]]。

## 1. 起點

使用者的問題：想仿照 AI-一人公司和一人軟體測試公司的架構，建一間軟體公司，目標是一句話就能交付完整的網站、App 或軟體。應該把測試公司擴建成軟體公司，還是另外建一間？

## 2. 過程

### 2.1 擴建還是另建

先查了測試公司的入口文件、現況、目標和 11/14 的顧問團紀錄，結論是另外建一間，測試公司保持獨立並負責驗收。理由有三個：

1. 測試公司的價值在獨立驗證。寫軟體和驗收放在同一間公司，就變成自己驗自己。
2. 測試公司的顧問團剛做出「不增加角色」的結論，擴建成軟體公司會反過來加很多角色。
3. 兩邊的目標不同。測試公司一次只做一個小範圍的案子，軟體公司要交付完整產品。

### 2.2 五個前提

AI 把會影響規劃的問題排好順序，一次問一題。

| 問題 | 使用者的回答 | 對規劃的影響 |
|---|---|---|
| 做出來的東西給誰用 | 自己用、接案、作品集都有，成熟後可以把整間公司賣給別人 | 公司本身也是產品，骨架和個人資料要分開放 |
| 第一版範圍 | 網站、Web App，加上可安裝的網頁 App（PWA） | 手機上架版和桌面軟體先不做 |
| 一句話要做到什麼程度 | 一開始在關鍵點停下來問，經驗累積後問題變少，成熟時一句話就上線 | 需要一套把回答累積起來的做法，也需要量成熟度的指標 |
| 部署到哪裡 | Cloudflare 為主 | 現有專案有 Cloudflare 的本機設定痕跡，帳號能不能部署還沒實測 |
| 用哪間公司當骨架 | 交給 AI 判斷 | 參考測試公司的骨架，後來修正為全部自己重寫（見 2.4） |

### 2.3 設計品質要求

使用者分兩次提出，原話如下：

> 這間公司設計出來的視覺,(如UI/UX, 公司文件, Logo....等等) 都必須要有具備「國際設計大獎（如 Red Dot 紅點、iF、Awwwards）」質感

> 品質標準以 awwwards、webby awards、FWA 獲得獎項的程度為目標，透過自我檢查，反覆自行提升品質，直到達到該品質標準為止。

為了讓「得獎質感」可以檢查，定了這些做法：

- 開工前挑三個同類型的得獎作品，由使用者選方向。
- 先定設計系統（字級、色彩、間距、動態），再開始做頁面。
- 做完後自我檢查、反覆修改，直到達標。
- 網站與 App 對標 Awwwards、Webby Awards、FWA；Logo 與公司文件對標 Red Dot、iF，因為三個網站獎不評 Logo 和文件。
- 對標哪個獎依案子類型決定。FWA 偏重創意和互動實驗，工具類的 Web App 以 Awwwards 的易用性和 Webby 的功能性為主。
- 反覆修改要有停止條件：改 5 輪還沒達標就停下來，告訴使用者差在哪裡。

使用者對後三點都回覆同意。

### 2.4 換模型後重新檢視，修正七處

使用者中途換了模型，要求把前面的結論重新檢查一遍。補查了骨架的來源、一人公司的目標和測試公司的資料格式後，修正七處：

| # | 之前的說法 | 修正後 | 原因 |
|---|---|---|---|
| 1 | 骨架用測試公司，開發和設計能力從一人公司借過來 | 參考做法後自己重寫，不直接複製檔案，並記下每個做法的來源 | 一人公司是付費課程包，條款沒有明講能不能轉售或改作，而這間公司最後要賣 |
| 2 | 沿用測試公司的骨架 | 能沿用的是派工入口、更新包、工作台、結構檢查；案件資料格式要重新設計 | 測試公司的案件紀錄是為測試設計的 |
| 3 | 評審 AI 拿截圖跟得獎作品並排打分 | 評審要實際操作網站、看動態效果，而且正式使用前要先校準 | 得獎網站的差距多半在動態和互動；沒看過評審把普通網站判成不及格，就不能相信它給的及格 |
| 4 | 成熟度指標是每案問幾題 | 問幾題，加上被推翻或要求重做幾次，兩個一起看 | 只看問題數的話，AI 不問、自己亂猜，數字一樣會下降 |
| 5 | 測試公司是驗收關卡 | 兩間公司之間用固定格式交接 | 買家手上沒有測試公司 |
| 6 | 第 0 號案子是公司品牌 | 第 0 號案子是公司自己的官網，Logo 和文件範本包含在裡面 | 官網才會把設計、驗收、部署整條流程走一遍 |
| 7 | 先寫完整規劃再做案子 | 規劃只寫一頁，角色和規則等案子真的需要時才加 | 測試公司的顧問團結論是少角色、少規則、多用機器檢查；這間公司也會跟使用者手上的其他主線搶時間 |

同時講明兩個限制。得獎網站靠的常是原創素材和概念，素材不夠的案子改幾輪也到不了標準。另外，第一階段的每一步都要留下能公開的成果。

### 2.5 三方會審

使用者問：評審的部分能不能轉給另外兩間公司一起做？

結論是有幫助，但只解決一半。評審會越評越寬有兩個原因：評審知道製作過程，以及評審和製作者是同一個模型。換另外兩間公司來審能解決前者，解決不了後者。所以這樣安排：

- 每一輪的小修改，仍由一位沒看過製作過程的評審快速打分。
- 交付前開一次三方會審：軟體公司的評審看設計與創意，測試公司量測易用性、無障礙和效能，一人公司看內容與文案。
- 再加一位不同模型的評審。
- 意見衝突時量測結果優先。

### 2.6 一場演講帶來的三項修改

使用者貼了一篇整理 Lauren Tan 演講的文章，並附上逐字稿。對照逐字稿後，規劃多了三項（演講內容與查核見素材頁）：

| # | 改前 | 改後 |
|---|---|---|
| 1 | 使用者回答過的問題累積成文字的預設值 | 能檢查的寫成檢查放進起始專案範本，需要判斷的才寫成文字 |
| 2 | 每個案子從頭開新專案 | 每個案子從同一份起始範本開始，做完把好的做法收回範本、把壞的清掉 |
| 3 | 兩間公司的交接格式還沒定內容 | 交付包固定有功能地圖、執行方式、AI 自己跑過的截圖和錄影；測試公司抓到的缺陷回頭變成範本裡的新檢查 |

### 2.7 最後追加的三項要求

使用者的原話：

> 之後若有規劃任何事情, 皆要把過程記錄及相關用到的資源都整理放到Wiki中

> 另外記得也要把軟體公司做成可攜式

> 還有一點, 要確保公司可以有接入任何LLM都能使用的彈性

可攜和不綁模型寫在一起處理：規則只放在一般文字檔，檢查都做成可以直接執行的指令，不依賴某一家 AI 工具才有的功能。

### 2.8 評審校準第一輪之後，品質關卡照事前標準修改

第一輪校準（見 [[一人軟體公司/一人軟體公司 — 評審校準實驗第一輪]]）沒有通過得獎門檻那一項。事前寫好的標準規定，這種結果下評審只能當地板檢查，品質關卡要跟著改。使用者同意照提案改：

| | 改前 | 改後 |
|---|---|---|
| 每輪評審 | AI 評審實際操作網站、看過動態後打分，改到達標 | AI 評審擋下限、指出具體缺點；有沒有達到得獎水準，前幾個案子由使用者把成品和對標作品並排判斷；校準通過後才交給 AI |
| 停止條件 | 改 5 輪還沒達標就停 | 改 5 輪還沒過下限就停；過了下限交給使用者判斷 |

同一天使用者換了模型，要求重新檢查。查出前一版的三個問題並修正：

| # | 之前的說法 | 修正後 | 原因 |
|---|---|---|---|
| 1 | 第二輪校準排在第 0 號案子之後，用官網的中間版本當缺的那組樣本，使用者的判斷當正確答案 | 第二輪什麼時候做還沒定 | 使用者同意的只有品質關卡的改法；同一個網站的幾個版本不是獨立樣本，數量也不夠 |
| 2 | AI 評審只能擋下限 | 只看截圖的做法只能擋下限；實際操作網站、看動態的做法還沒測，保留為待測 | 第一輪測的是 2.4 已經換掉的截圖做法，結果不能套到沒測過的做法上 |
| 3 | 使用者的判斷另外計數，不算進問了幾題 | 使用者判斷「還沒到、重做」算進被推翻或重做幾次 | 不算的話數字會顯示成熟，實際上把關的還是使用者 |

另外記下兩個缺口。「下限」的線還沒定：第一輪只驗過評審擋得住免費範本，範本和得獎之間那一段沒有樣本。使用者那一關最多改幾次也還沒定。

### 2.9 先補測中間那一段，再開第 0 號案子

複查時提出把第二輪校準拆成兩塊：小的一塊只補「還可以但沒得獎」的樣本，放在第 0 號案子之前；貴的一塊（處理 cookie 視窗、加入動態、並排二選一）留到之後。理由是小的那一塊會決定官網那一案怎麼跑。使用者同意先做小的。

開口問之前先查了樣本來源：Awwwards 的報名名單是公開的，官方規則寫明評審期 5 天、評審團 6.5 分以上才有榮譽提名，所以報名多週仍然只有 Nominee 的網站就是沒得獎的網站。

補測當天做完（見 [[一人軟體公司/一人軟體公司 — 評審校準補測]]）。結果是主要標準「無法判定」，兩條下限候選線都不能用。照事前的對應，第 0 號案子不拿 AI 的分數判斷好壞。使用者同意把一頁規劃的停止條件改成「下限只擋範本等級，AI 的分數照記、只當參考」。

### 2.10 第 0 號案子開工前先把公司獨立出來，只建最小的一版

使用者問：開工前需不需要先把軟體公司獨立出來。當時公司的資料夾還不存在，所有文件都放在 AI-一人公司的資料夾裡。

結論是要，理由有三個：

1. 在 AI-一人公司的資料夾裡做，每場對話都會自動載入那邊的規則。量到的問題數和重做次數會是那套規則的表現，可攜和不綁模型也測不到。
2. 公司最後要賣。官網的程式、範本和檢查如果先寫在放滿課程包檔案的版本庫裡再搬出去，版本紀錄證明不了它們是從零寫的。
3. 測試公司有自己的資料夾和版本庫。軟體公司也獨立，固定格式的交接才有兩邊。

並排了三條路：先建最小的一版、照工單建完整骨架、先在一人公司裡做完再搬。使用者先要了一張現況圖（員工、架構、工作流程），看過之後選最小的一版。

當天建好的內容：自己的資料夾與本機版本庫（沒有遠端）、一份規則入口、Claude Code 與 Gemini CLI 的薄載入檔、來源與採用、從一頁規劃搬過去的實作計畫。新寫的文字跟課程包和測試公司的檔案比對過，最長只重複到檔名和一個網址。

還沒做到的：兩個載入檔都沒有實測；個人資料要放哪一層還沒設計；派工入口、更新包、工作台、結構檢查、模型設定檔、打包後重建的檢查，都等案子用到才補。

### 2.11 使用者那一關的上限定為 3 次

2.8 留下的缺口是：AI 那一關有 5 輪上限，使用者那一關沒有。補測之後 AI 那一關大概第一輪就會過，每一版好不好都要使用者看，所以真正在跑的是使用者這一圈。

並排了三條路：最多改 3 次、最多改 5 次、不設次數。使用者選 3 次。意思是他第一次說「還沒到」之後最多再交 3 版，還是沒到就停下來談，先整理各版改了什麼、哪些問題一直沒解決。

3 和 5 都沒有數據支持。AI 建議只先套在第 0 號案子、跑完再依實際次數調整，使用者沒有另外表態。

### 2.12 校準第二輪排在第 0 號案子之後

第二輪要補的有五件：截圖前關掉 cookie 視窗與彈窗、加入動態、改成並排二選一、用不同廠商的模型、樣本加大。

並排了三條路：第 0 號案子做完檢討時再決定、開工前先做、不排時間。使用者選第 0 號案子之後。理由是第 0 號案子沒有任何一步在等它，前幾個案子本來就由使用者看並排判斷；前兩次校準都沒過，沒有證據顯示先做就會過；別家模型的評審工具在三方會審那一步本來就要解決。

代價是第 0 號案子全程靠使用者判斷每一版，重做上限是 2.11 定的 3 次。

### 2.13 擁有者的偏好：公司裡只放一個不進版本庫的指向檔

接手後查到，四種個人資料裡實際存在的只有擁有者的偏好，而且都在公司外面：一處是 AI-一人公司的記憶檔，一處是擁有者自己的個人檔案。新資料夾的對話要靠交接文件提醒才會去讀。

並排了三條路：公司裡放一個不進版本庫的資料夾，裡面只放指向檔；同一個資料夾，但把偏好複製進來；維持現狀。使用者選只放指向檔。理由是偏好只留一份，不會兩邊各改各的。

做了什麼：新增忽略清單擋掉 `私人/`；規則入口的規矩 7 加一句「有 `私人/先讀這個.md` 就先讀」；實作計畫的未確認事項改成偏好已定。

還沒做到的：案件、帳號、密鑰、品味設定要放哪裡還沒設計；「打包只取版本庫裡的檔」還沒寫成規則。另外有一個後果：任何照規則入口接手的工具都會去讀擁有者的偏好，換成別家的工具時，這些內容會送到那一家的伺服器。

### 2.14 實測 Gemini CLI 的載入檔，卡在登入

同一場對話先確認了 `CLAUDE.md` 的載入是通的：新資料夾的第一句問規矩第 6 條的標題，答得出來。

`GEMINI.md` 的實測，使用者同意在匯出的副本裡做。副本只有版本庫裡的檔，沒有 `私人/`。用這台的 `gemini` 指令 0.40.1 和個人 Google 帳號，問同一題。

結果是登入被拒，題目沒有被回答。錯誤訊息說這個用戶端不再服務個人帳號，要改用 Antigravity。搜尋到的 Google 停用公告寫生效日是 2026-06-18，這個日期沒有逐字核對原頁。

所以 `GEMINI.md` 仍然沒有實測，「不綁模型」目前只在 Claude Code 上驗過載入。換哪個工具來驗，併進「不同模型的評審用什麼工具」那一件一起解決。

### 2.15 起始範本的框架：先查四個候選，再拿 Astro 試裝

接手時還沒確認的事之一是範本用哪一套技術。先看了現有四個專案：兩個是網站，共用同一套底（vinext、React、Tailwind、TypeScript）；另外兩個是桌面軟體和沒有任何套件的小工具，不在公司的範圍內。那套底來自一份沒有授權檔的起手範本，設定綁在別家的託管服務上，不能當範本的基礎。

接著查了四個候選的官方現況：vinext、Next.js 加 OpenNext、Astro 加 React、React Router。四個都部署到 Cloudflare Workers。四種組合加上 PWA，官方都查不到相容說明，只能實測。並排之後，使用者選先拿 Astro 做本機試裝。

試裝的內容是一頁有 React 互動和 GSAP 動畫的首頁、一條由伺服器即時產生的路由、PWA 的 manifest 與 service worker。本機 11 項檢查全過，並把關鍵設定拿掉重建，確認檢查真的會失敗。試裝發現三件事：

- Astro 的設定少了 `output: 'server'` 時建置照樣成功，但 service worker 會放錯資料夾，離線失效。
- PWA 套件標 2.0.3，底層是一個 0.0.7 的新套件，有一份官方文件還是舊寫法。
- GSAP 的授權不是 MIT，放進範本之前要先讀條款。

用量：盤點現有專案約 7.5 萬 tokens，查四個候選約 19 萬，本機試裝約 11.7 萬，都是子代理的用量。主對話的用量沒有量。

### 2.16 第一次部署到 Cloudflare

使用者同意把試裝部署到自己的帳號，測預覽網址。走通之前卡了三處：

1. 帳號沒有設定過 workers.dev 子網域。
2. Astro 的工作階段 KV 不會自動建立，要先建好，再把編號寫進設定的最上層和 `previews` 區塊。
3. 設定要加 `previews` 區塊和 `preview_urls`。

後兩項沒有分開驗哪一個才是必要的。預覽指令目前是 open beta。之前的研究寫「預覽網址本機一行指令就有」，實測不是這樣。

正式網址和預覽網址都部署成功，線上與離線檢查各跑兩次都過。正式網址第一次開啟時，React 的計數器有一次沒反應，原因沒有確認。測完後使用者決定把試裝的 Worker 和 KV 都刪掉，子網域留著。

### 2.17 定案：框架用 Astro 加 React，部署到 Cloudflare Workers

並排了三條路：定案用 Astro、再試一套來比較、還不定案。使用者選定案用 Astro（2026-11-20）。

定案的範圍只有框架與部署。樣式怎麼做、動畫用哪個函式庫、PWA 套件用哪個都還沒定，範本本身也還沒寫。

這次只證明了 Astro 行得通。其他三個候選沒有試裝，互動很重的 Web App 也還沒測過。AI 建議等回放 RiskQADemoSite 時再看要不要換，使用者沒有另外表態。

### 2.18 起手檔從零自己寫

問題是 Astro 官方的 MIT 起手樣板算不算「別人的檔案」。查了授權全文：第一段是 MIT，另外兩段只管 Astro 套件裡來自 SvelteKit 與 Vite 的部分，沒有提到樣板。最小樣板共 11 個檔，會留在範本裡的只有 4 個設定檔、共 52 行，其餘是說明檔、編輯器設定和 Astro 的標誌。

並排了兩條路：從零自己寫、用官方指令產生後再改。使用者選從零自己寫（2026-11-20）。理由是要寫的量很小，「不複製別人的檔案」這條規矩可以不加例外，範本也不用附別人的版權聲明。AI 另外提議 Astro 升大版時，在暫存資料夾跑一次官方指令只做對照，使用者沒有表態。

### 2.19 樣式用純 CSS 變數

查了現有兩個網站專案的實際寫法：都引入了 Tailwind，但 `className` 裡幾乎沒用它的類別（一個 0 次，一個只有 2 次），其餘全是自己取名的類別配 CSS 變數。Tailwind 在這兩個專案裡等於裝了沒用。

並排了純 CSS 變數和 Tailwind 4。兩條路都擋不住有人直接寫死色碼，所以不管選哪條都要一支檢查。使用者選純 CSS 變數，並採用 AI 提的組合：設計變數只寫在一個檔，加一支檢查擋住那個檔以外寫死的色碼（2026-11-20）。以後真的要換 Tailwind，它的 `@theme` 可以引用同一組變數。

### 2.20 範本不放動畫函式庫

讀了 GSAP 現行條款全文（2025-04-30 生效，版權屬 Webflow）：網站與 Web App 商用免費，以前要付費的外掛也包含在內；限制是不能拿它做跟 Webflow 競爭的視覺動畫工具；Webflow 可以單方面改條款，不同意可以留在舊版。網頁原始碼裡有一段「終端使用者付費就要買商業授權」的舊摘要，核對後發現它在註解裡，已不是現行條款。

另外查到現有四個專案都沒用任何動畫函式庫。使用者選照 AI 的建議：範本只用 CSS 動畫，動畫的時間長度與緩動曲線也寫成設計變數；案子需要時先試 Motion（MIT），不夠用才換 GSAP（2026-11-20）。

### 2.21 PWA 沿用試裝過的套件，用檢查守住

查到的現況：`@vite-pwa/astro` 2.0 在 2026-10-31 發布，三週內出了 4 版，底層是 0.0.7 的新套件；1.x 只支援到 Astro 5，不能用；Serwist 的 Astro 版只有預覽版。Google 的 `workbox-build` 從 2017 年就有，但沒有測過。

使用者選 AI 提的兩件事一起做（2026-11-20）：沿用試裝通過的 `@vite-pwa/astro` 2.0.3 並釘死版本，用三支檢查守住（`sw.js` 的位置、預覽設定的 KV id、離線檢查）；哪天檢查擋下來，再改成自己寫建置後腳本、呼叫 `workbox-build`。

### 2.22 範本寫好，四支檢查都先看過它失敗

範本放在公司的 `範本/`，由子代理照規格從零寫，主對話親自重跑驗收。所有相依套件寫死精確版本，設計變數只在一個檔。四支檢查都能用一行指令執行：

| 檢查 | 擋什麼 | 壞的狀態怎麼造 |
|---|---|---|
| 設計變數 | 設計變數檔以外寫死的色碼 | 在頁面樣式寫死一個顏色 |
| 建置輸出 | `sw.js` 放錯資料夾 | 拿掉 `output: 'server'` |
| 部署設定 | 頂層或預覽設定的 KV id 沒填 | 佔位不換，或只填一處 |
| 離線 | service worker 沒註冊、離線打不開，順便驗 manifest 與 React | 拿掉 `output: 'server'` |

四支在壞的狀態都跑出失敗，還原後整套全過，沒有留下佔著連接埠的行程。

沒測到的：只在 Windows 與 Chromium 跑過，macOS 的行程收尾沒有實測；離線只測首頁；新頁面忘了 `prerender = true` 會不會漏掉離線快取，仍是推測。用量：子代理約 11.3 萬 tokens，主對話沒有量。

### 2.23 打包只取版本庫裡的檔

規則入口加了規矩 10：整間公司要交給別人或搬到別台電腦時，用 `git archive` 從已提交的內容打包，不直接壓縮資料夾。`私人/` 裡的偏好指向檔就是靠這條才不會進包。

實測打出來的包只有版本庫的 27 個檔，資料夾裡的 `私人/` 和兩萬多個 `node_modules` 檔都沒進去，中文檔名都標了 UTF-8。

它擋不住已經提交的檔。查到實作計畫裡有兩處這台電腦的絕對路徑，會跟著進包，交給別人之前要排除或拆開，怎麼做還沒決定。這條規矩只管「整間公司」的包；交給測試公司驗收的交付包格式還沒設計。

### 2.24 不同模型的評審：Codex 與 Antigravity

交付前的三方會審要多一位不同模型的評審。查了這台的候選：Gemini CLI 用個人帳號已停用（Google 2026-05-19 公告，2026-06-18 生效，付費 API 金鑰仍可用）；這台兩把 Google API 金鑰有效，但預付額度用完；Codex 已登入；Antigravity 只裝了桌面版。

使用者選 Codex 與 Antigravity 兩個（2026-11-20），並自己裝了 Antigravity 的指令列工具 `agy`，它沿用桌面版的登入。

測法：產生一張只有隨機 6 碼代碼和一個紅色方塊的圖，模型要真的看到圖才答得出來。圖放在空資料夾，答案放在別處。

| 評審 | 指令 | 結果 |
|---|---|---|
| Codex（OpenAI） | `codex exec -m gpt-6-luna -i <圖>` | 17 秒答對，約 5 萬 tokens |
| Antigravity（Google） | `agy -p "<題目>" --model gemini-4-neon-medium` | 25 秒答對，用量沒量 |

踩到的事：第一次測 Codex 時答案檔放在同一個資料夾，模型可能直接讀答案，那一次作廢重測。Codex 設定檔預設的模型在指令列會被拒，要指定。兩個工具都會讀所在資料夾的規則檔，在公司資料夾裡跑會把擁有者的偏好送出去，所以只能在空資料夾裡跑、只給截圖。Antigravity 的模型清單裡也有 Claude，當評審要指定 Gemini。

還沒做的：兩個評審都還沒校準，第 0 號案子裡的分數只當參考。評審指令與模型還沒寫進模型設定檔，那個檔等三方會審真的要開時再建。

### 2.27 案件資料放哪：公司資料夾裡、版本庫不收的 `案件/`

### 2.28 檢討：挑參考作品只比了首屏截圖，漏掉動態

使用者一個一個點進三個參考網站，發現它們真正有價值的是滑動時的動畫，得獎不會只因為靜態的樣子；而 2.26 挑參考時沒有考慮到（2026-11-21）。AI 查證後的原因：

1. 找參考的條件只有調性形容詞（正式、文青留白、知性、冷幽默），派工只要桌面與手機的首屏截圖。
2. 核對得獎紀錄時抓過三個 Awwwards 得獎頁，只看了標題與日期。同一頁上 Awwwards 自己的標籤：NEWFOLK 有 Transitions、Interaction Design，Spring/Summer 有 Interaction Design；Signal-A 只有 Typography、Minimal 這類，沒提動態。所以標籤只是線索，還是要實際看。
3. 公司早就知道只看截圖不夠（評審校準顯示截圖分不出每日最佳與榮譽提名），但這個教訓只用在評審，沒延伸到挑參考。
4. 缺口有寫出來（參考清單寫「沒有實際操作過每個互動」、交接寫「只比了首屏一個畫面」），但只放在不確定事項裡，沒有在使用者選方向前講明；給使用者選的示意圖也是靜態的。

根本原因：把得獎網站當成靜態視覺參考，沒先問它為什麼得獎；截圖最省事，查證的範圍就被工具決定了。

使用者同意三項改善：

| 改善 | 落在哪裡 |
|---|---|
| 挑參考作品時每個都記四樣：得獎頁的標籤與分項分數、桌面與手機滑到底的錄影（加上進場、滑鼠移上去、換頁）、動態用什麼做的與搬進範本的代價、首屏截圖；缺一樣要在給使用者選之前講明 | 公司規則入口規矩 12 |
| 一支一行指令的檢查，擋下缺錄影、缺動態表、缺四節之一、引用的檔不存在 | `檢查/check-refs.mjs`；空資料夾、缺項、齊全、只寫明部分沒錄到四種狀態都先跑過，結果照預期 |
| 提案涉及動態時示意要能動，靜態圖不算 | 規矩 11 補一句 |

這次案子的補法：三站的動態錄下來並排給使用者看，再確認「B 為主、借 A 和 C」在看過動態後是否成立。這是 AI 漏掉的，不算使用者推翻。

### 2.34 官網文案：首頁選丁（甲丙合併），其他四頁照同一個語氣

聯絡：AI 建議乙，理由是甲的表單要先決定收件方式（第三方表單服務或自己的後端），真的聯絡方式也還沒定。使用者給了一張頁尾那一屏的截圖，說先留這頁、等要加表單再說。截圖置中的是標語「說一句，得全套。」，乙置中的是「需要編譯什麼嗎？」，AI 回頭確認要哪一種；使用者反問那句不是本科系的人會不會看不懂。AI 認同：一般人知道的「編譯」多半是新聞署名的「編譯○○○」，會把那句讀成要不要翻譯；程式的編譯只有寫程式的人懂；有人直接打開聯絡頁時，也看不到首頁對「編」的解釋。英文的 Need something compiled? 也會被讀成整理資料。改成：置中用標語，下面一句白話「想做什麼軟體？寫一句話給我們就好，其他的我們會問。」（英文 Want some software made? Send us one sentence. We will ask about the rest.），再一行大字信箱，沒有表單。說明句寫「軟體」，網站、App、桌面軟體都包在裡面。使用者同意（2026-11-23）。這算糾正，不算推翻。品牌名「編譯所」本身也有同樣的雙關，首頁有解釋，這次沒動。

照規矩 11，兩題定了之後把整組做成內頁定案樣本 J：首頁（樣本 I 加上導覽連到內頁）、作品全集、編譯方法（甲）、關於、聯絡（新文案），中英各一份。驗證多加一項，檢查聯絡頁置中是標語、說明句是白話、頁面上沒有「需要編譯什麼嗎」，先在放回舊句子的複本上看到失敗；寫這項時發現右下說明面板本身提到舊句子會造成誤判，改成只看頁面本身。J 組 10 頁 119 項、樣本 I 156 項全過。使用者看過 J 確認一樣（2026-11-23），內頁定案。

### 2.39 官網搬進 Astro：動態沿用自寫的 JS，Lenis 改用 npm 裝

內頁定案後，AI 建議先把首頁加內頁搬成正式專案，搬的時候碰到的實作細節（標誌位置、字型自架、減少動態）再一題一題問；使用者選先搬（2026-11-24）。官網沒有寫進範本本身：範本要給買家，必須中立，官網屬於案件內容，所以照範本 README 開新案子，複製到案件的 `網站/`。

搬之前有一個衝突：範本的規則是不放動畫函式庫、只用 CSS 動畫，案子需要時先試 Motion（見 2.20）；樣本的動態是自己寫的原生 JS（約 17KB），只有桌面的慢速慣性捲動用到 Lenis（MIT，壓縮後約 4KB，從 unpkg 載 1.1.20）。那個慢速是在模仿 NEWFOLK 自製的捲動（實測約滾輪的 0.33 到 0.45 倍）。AI 並排四條路：

| 做法 | 好處 | 壞處 |
|---|---|---|
| 甲：沿用原生 JS，Lenis 改 npm 裝並寫死版本 | 手感跟定案樣本一樣、不用重寫、不靠外部網站 | 案子多一個套件；Lenis 不在 2.20 的名單裡，算 AI 的解讀 |
| 乙：用 Motion 重寫 | 字面上最符合 2.20 | 已經能動的效果全部重寫；Motion 沒有慣性捲動（AI 的認知，沒實測），最後還是要 Lenis 或自寫 |
| 丙：自己寫慢速捲動 | 不靠外部套件 | 鍵盤、錨點、觸控板等情況容易出錯，程式碼較多 |
| 丁：拿掉慣性捲動 | 最簡單 | 改掉已定案的手感 |

AI 建議甲，使用者選甲（2026-11-24）。2.20 的解讀因此補一句：2.20 管的是範本本身；案子要用慣性捲動時用 Lenis，Motion 管不到這一塊。

搬的工作派給一個子代理，驗收用樣本原本的兩支檢查，改成也能直接測架起來的網站。做法與結果：

- 網址：中文 `/`、`/works/`、`/method/`、`/about/`、`/contact/`，英文在 `/en/` 底下；導覽第 6 個連結切到另一種語言的同一頁。拿掉樣本右下的說明面板；色碼全部收進設計變數檔；題數與退回次數建置時從案件紀錄讀，日期固定用臺灣日期。
- 子代理抓到一個樣本沒有的錯：service worker 接管後點導覽到作品全集，網址對、內容卻是首頁，原因是預快取的網址少了結尾斜線，設定 `trailingSlash: 'always'` 修好。原本的檢查只看網址抓不到，補了一項看作品列。
- 導覽右上的臺灣時間在樣本裡寫死不會走，正式網站改成會走，補了一項檢查。
- 範本的離線檢查寫死要首頁有 React 範例元件和 h1「範本首頁」，官網兩樣都沒有；案件裡改成沒有 React 元件時略過、改看頁面標題。範本本身還沒改。
- 驗收：範本的三支檢查全過（拿範本原本那支跑會失敗 3 項）；兩支網站檢查 159 項、160 項全過，先在故意弄壞三處（慢速捲動倍數、作品列、時鐘）的網站上看到失敗。80 張樣本與網站的對照截圖，差異只剩題數、日期、隨機強調色。

部署到預覽網址（`wrangler preview`，open beta；先在帳號建了網站用的 KV）後，使用者自己點了一輪，指出兩件樣本本來就有、檢查沒抓到的事（2026-11-24）：

- 編譯方法那段在矮視窗被切掉：他的瀏覽器多一條偵錯提示列，加上 Windows 顯示縮放，可用高度約 587px；那段釘在畫面上、內容約 770px、置中顯示，標題與「6 上線」各有 92px 跑出畫面。檢查只測過 900px 與 844px 高。改成視窗不夠高時竹簡圖跟著縮（約 800px 高以上不變），加一項 1200×587、1440×700 的檢查。
- 中文頁出現英文、英文頁出現中文：標誌旁的「COMPILED WORKS SOFTWARE」、「EST. 2026」、自介右欄的英文小字，英文頁反過來是「編譯所 · SOFTWARE STUDIO」與中文小字。改成每頁只用自己的語言：中文頁「編譯所軟體」「2026 年創立」，英文頁照定案寫「COMPILED WORKS SOFTWARE」，兩頁的對照小字拿掉；導覽的語言切換、GMT+8、編號、信箱，與英文頁解釋「編」「編譯」的句子保留。加一項逐頁檢查。

兩項新檢查都先在舊的預覽網址上看到失敗，改後全過。

看了改後的頁面，使用者補充標誌要中英都顯示（2026-11-24）。AI 把兩種做法直接套在預覽網址上截圖給他選：甲照標誌規範④的橫式組合，主語言名稱大字、另一種語言小字兩行（中文頁「編譯所／COMPILED WORKS」，英文頁「Compiled Works／編譯所 · SOFTWARE」，標誌從 44px 放大到 64px）；乙維持一行等寬小字、中英並列。AI 建議甲，理由是網站上的標誌跟規範一致、讀起來是標誌而不是說明字；使用者選甲。字重用網站已載的 400，規範是 300。標誌組合因此是「每頁只用自己的語言」的例外，檢查跟著改。

改完跑驗收時抓到一個這次引出來的錯：手機中文頁捲回頂端，頁面停在紅底。AI 先猜是標誌那排不屬於任何區段，補進去後仍失敗；實際量到的是畫面中線（422px）落在標誌組合（底 367px）與自介（頂 423px）之間的空白。樣本的整頁換色只在中線碰到區段時才換，落在兩段之間的空白就停在舊顏色，以前是版面剛好沒踩到。改成「中線往上最後經過的區段」決定顏色，空白跟著上一段；先補的那一段拿掉。

同一輪使用者指出編譯方法第 5 步「驗收：交給另一間測試公司」會讓人以為測試外包出去。實際上測試公司是他自己另外建、刻意跟製作分開的一組 AI。AI 給兩種寫法：乙「另一組只負責驗收的 AI」、甲「我們自己的測試團隊」（「團隊」聽起來像有真人），建議乙；使用者選乙，接著自己提「公司底下」，AI 建議改「公司裡」（「底下」偏口語）；他再提「負責測試驗收」（比「驗收」好懂），AI 建議加「專門」補回「只」的意思。定稿：「做的跟驗的分開：公司裡另一組專門負責測試驗收的 AI，量易用性、無障礙與效能。」英文「Building and checking stay apart: a separate in-house set of AI testers measures usability, accessibility and performance.」（2026-11-24）。

### 2.40 PWA 圖示換成標誌，範本的離線檢查不再寫死首頁內容

交接第 10 份的待辦裡，AI 問先做兩件小事（PWA 圖示、範本離線檢查），還是先定字型自架與減少動態；AI 建議先做小的，使用者選先做小的（2026-11-25）。

- PWA 圖示：裝到手機桌面時看到的 192、512 兩張圖原本是範本的佔位圖（深藍底白圈）。標誌規範寫 48px 以上用主標誌，所以從標誌的唯一來源 `mark.py` 加一段輸出，米白配色、底色鋪滿；網址列的 16、32 小圖示本來就是逐像素版，沒動。圖示宣告的用途照範本只寫一般用途，沒有另做 Android 會裁成圓形的版本。加一項網站檢查讀 manifest 列的每張圖，看角落米白、線頭朱紅、竹簡墨色；先在舊的預覽網址上看到失敗。
- 範本的離線檢查：原本寫死首頁要有 React 範例元件和 h1「範本首頁」，案子換掉範例就失敗（2.39 在案件裡先改過）。改成不寫死內容：上線時記下頁面標題，離線重新載入要看到同一個標題；首頁沒有 React 元件就略過那一項。先把範本首頁暫時換成沒有 h1、沒有 React 的頁，舊檢查失敗 3 項、新檢查全過；換回範本原本的首頁，新檢查照樣驗 React 而且全過。案件裡的副本換成範本這一份，兩邊一致。

驗收：網站檢查 180 項、動態檢查 160 項都在預覽網址上全過，範本與案件的三支檢查都沒有失敗。

## 4. 被否決或延後的做法

| 做法 | 為什麼不採用 |
|---|---|
| 把測試公司擴建成軟體公司 | 會變成自己驗自己，也跟顧問團「不增加角色」的結論相反 |
| 第一版就做手機上架版或桌面軟體 | 上架要開發者帳號、簽章和審核，都要本人處理；範圍太大會拖慢第一個成品 |
| 一開始就完全不問 | 一句話沒講到的細節只能猜，猜錯就要重做 |
| 直接複製課程包的檔案 | 條款沒有明講能不能轉售或改作 |
| 只用截圖評審 | 動態和互動看不出來 |
| 反覆修改不設上限 | 評審可能越評越寬，或卡在自己修不好的問題上原地打轉 |
| 每一輪都開三方會審 | 用量太大，只在交付前開一次 |
| 形式化驗證 | 演講者自己說還在實驗，對網站來說太重 |
| 讓 AI 自己合併、不經人審 | 那是演講者投資六個月之後的結果，這間公司照「越問越少」的路走 |
| 官網動態以 Signal-A 為主 | 幾乎靜態，動畫轉場分 7.40 是三站最低（見 2.29） |
| 照搬 NEWFOLK 的 WebGL 與約 4 秒的開場 | 範本沒有 WebGL，搬進來代價最高；開場期間不能捲動，拖慢首屏（見 2.29） |
| 官網中文字體用仙人掌明體 | 只有一種字重，做不出超黑大字標；字形不是教育部標準（見 2.31） |
| 官網英文字體用 Bodoni Moda 加 Newsreader | 高反差，縮小時細線會斷，字母方塊動畫裡的小字也受影響；要兩套字體（見 2.32） |
| 官網字體用 justfont、文鼎、華康 | 付費，justfont 禁止轉讓與再授權，另兩家沒有公開網頁條款；範本要賣給很多買家（見 2.31） |
| Logo 用現成字體把名字排出來再加裝飾（純標準字、「」括號、印章） | 使用者嫌設計感、質感、意象不夠，三個一起退回（見 2.33） |
| 直接用 Gemini 畫的 Logo | 說的 C 其實讀成 D，沒有中文版，細線到 16px 會消失，著作權沒查（見 2.33） |
| 用 `ai-website-cloner-template` 做官網 | 它是照原樣仿製別人網站的工具，目的相反，技術是 Next.js 加 Tailwind（見 2.29） |

## 5. 第一階段順序

1. 校準評審：拿幾個得獎網站和幾個普通網站測評審 AI，分數要能把兩組分開。
2. 第 0 號案子：公司自己的官網，含 Logo 與文件範本。
3. 回放 `RiskQADemoSite`：用一句話重做，跟原版比較差距。
4. 檢討：把前兩案的糾正落成檢查，再決定補哪些角色和規則。

## 6. 還沒確認的事

- Cloudflare 帳號能不能部署，還沒實測。
- 不同模型的評審要用哪一個工具，還沒試。
- 設計迴圈加三方會審每案的用量，第 0 號案子跑完才知道。
- 起始專案範本用哪一套技術。
- 公司名稱的台灣商標與公司登記（名稱與定位已定，見 2.25）。
- 課程包能不能轉售或改作，出售前要向賣方取得書面答覆。
- 設計獎項的評分項目是憑既有認知寫的，這次沒有重新查官方頁。
- 官網動態的配色與細節（強調色、換色順序、開場長度）之後再調；直排標點的字型、系統「減少動態」設定還沒處理（見 2.29）。
- 官網字型要不要自架；自架時思源黑體與 IBM Plex Mono 要改名、直排標點怎麼補（見 2.31、2.32）。
- Logo 在官網上的正式位置；字轉外框；AI 生成圖的著作權與商標問題（見 2.33）。
- 官網的聯絡方式（見 2.34）；聯絡頁的表單等要加時再決定收件方式（見 2.38）。
- 官網的 PWA 圖示還是範本的佔位圖；範本的離線檢查寫死 React 範例元件與 h1，案子換掉範例就會失敗，要收回範本修（見 2.39）。
