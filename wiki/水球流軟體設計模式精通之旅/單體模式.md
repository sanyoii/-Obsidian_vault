> **分類：** 創建型模式

## 核心定義

保證某一類別在整個系統中**只存在唯一一份實體**，並提供全域存取入口。透過將建構子設為私有存取權，從根源阻止 Client 自行創建物件。

---

## 詳細說明

### 解決的 Forces

- **Force 1（創建成本昂貴）**：此類別的實體化過程耗時長或記憶體消耗量大
- **Force 2（資源同步存取）**：此類別封裝的資源必須同步存取，不允許多位 Client 同時各自操作，否則會產生不可預期的後果（如帳單超支）
- **Force 3（多位不受控的 Client）**：有多位 Client 存在，且你無法信任他們會遵守「共用同一物件」的規範——他們可能為了圖方便直接 `new` 出新物件

### Problem

如何強制讓所有 Client 都依賴相同的物件，以避免昂貴的重複創建或非預期的後果？

### 結構（Form）

```
Context（單體類別）
  ├── - constructor()                  ← 私有建構子（-）
  ├── - static instance: Context       ← 靜態單體屬性，預先創建
  └── + static getInstance(): Context  ← 靜態 Getter，回傳唯一實體

Client → 呼叫 Context.getInstance() 取得單體
```

### 套用步驟

1. **將建構子設為 private**——外部無法呼叫 `new`
2. **宣告靜態屬性 `instance`**，預先創建單一實體
3. **提供靜態方法 `getInstance()`**，回傳此單體

### Resulting Context

1. **保證唯一性**：不管在何種系統、何種情境下，此類別的實體只會存在一份
2. **全域變數的缺點**：`getInstance()` 本質上是全域存取入口，會延續全域變數的所有缺點

---

## 全域變數的缺點（務必注意）

| 缺點 | 說明 |
|------|------|
| **不明確的間接耦合** | 多個 Client 透過全域變數共用同一物件，彼此之間的影響關係在程式碼表面完全看不出來（如小明印完論文就關印表機，小華再呼叫就炸掉） |
| **難以抽換實作** | 未來要換新的實作類別，必須逐一修改每一處 `Context.getInstance()` 的呼叫，違反 OCP |
| **難以除錯** | 任何人在任何地方都可能改變單體的狀態，問題來源難以追蹤 |

**小優化**：透過依賴注入取代直接呼叫 `getInstance()`，至少能讓依賴關係更明確。但仍無法從根本上阻止有人手癢直接用全域存取。

## 水球流教學重點

- **嚴正警告濫用**：單體模式是最簡單的模式，但也是最容易被濫用的，逐漸被評為反模式
- **判斷標準**：真正該反對的不是單體模式本身，而是「濫用」——如果你只是想「圖一個方便」讓某物件全域可取，而不是真的需要保證唯一性，那就是**過度設計（Over-Design）**
- **正確思路**：回到 Christopher Alexander 的描述方式，先感受到 Forces 的衝突，再確認是否真的需要嚴格保證單一實體
- 水球的判斷邏輯：Force 1（創建成本）或 Force 2（資源同步）至少存在一項，且 Force 3（不受控的 Client）與之衝突 → 有套用的必要性

### 課程中的案例（ChatBot）

- OpenAI 對話 API 有額度收費，公司帳單爆表
- 第一次修正：加入節流機制（Throttling）
- 小華的對策：每次對話都 `new ChatBot()` 繞過節流
- 最終解法：套用單體模式，強制所有 Client 共用同一個 ChatBot 物件來統一節流

---

## 實作要點

1. **Private Constructor** 是核心——封住創建入口
2. **靜態屬性 + 靜態 Getter** 提供唯一存取點
3. 多執行緒環境下需考慮 **Thread Safety**（挑戰題 B-3 要求在非同步執行下仍保證單體唯一性）
4. 可結合 **延遲載入（Lazy Initialization）** ——不預先創建，等第一次呼叫 `getInstance()` 時才創建（挑戰題 B-2）

---

## 課程中的範例

- **ChatBot 對話機器人套件**：為了統一節流 OpenAI API 的使用額度，強制所有 Client 共用同一個 ChatBot 單體
- **挑戰題——計算模型**（★）：三種計算模型（Reflection/Scaling/Shrinking）各自持有 1000x1000 的矩陣，創建成本極高且消耗大量記憶體——必須保證矩陣不被重複創建，套用單體模式；進階版本要求延遲載入和 Thread Safety
- **Java 經典案例**：`Runtime.getRuntime()`、`Desktop.getDesktop()`、資料庫連線池
