## 🧩 責任鏈模式 (Chain of Responsibility, COR) 簡介

> **責任鏈模式** 是一種行為型設計模式，允許將多個處理者串成一條鏈，讓請求沿著這條鏈傳遞，直到某個處理者能夠處理該請求為止。此模式強調**行為的封裝與解耦**，使系統具備良好的擴充性和彈性。

---

## 💡 主要情境與需求分析

- **案例背景**：為 Discord 平台開發一個名為 Waterbowbot 的機器人，該機器人需能識別並處理多種訊息指令 (Message Command)，例如 Help、Currency、Dcard 等。
- **需求特點**：

    - 不同訊息指令對應不同處理行為。
    - 訊息指令不區分大小寫。
    - 系統未來會持續增加更多功能（例如支援 CNN 新聞、天氣查詢等）。
    - 處理行為需具備獨立性，以方便維護和擴充。
---

## 🔍 設計挑戰與三道 Forces

| Force 名稱 | 說明 | 影響方向 |
| --- | --- | --- |
| **行為變動性 (Behavioral Variation)** | 訊息處理種類會隨時間由少變多，需支援不斷新增的功能。 | 行為數量持續增加 |
| **擴充性與維護性 (Extensibility & Maintainability)** | 希望每個處理行為皆獨立，避免程式碼相互干擾，方便後續擴充和維護。 | 程式碼需解耦、職責分離 |
| **系統彈性 (Flexibility)** | 需要能有彈性地決定系統支援哪些需求，並能輕鬆新增或移除處理行為。 | 需求可動態調整 |

---

## 🏗️ 問題定義 (Problem)

如何在 Waterbowbot 與多個訊息處理者之間**解耦**，使系統能夠靈活地決定支援哪些訊息處理，並且方便擴充與維護？

---

## 🧱 責任鏈模式的解決方案 (Solution/Form)

1. **封裝行為變動**  
  將不同訊息的處理行為封裝至獨立的 **Handler 類別** 中，每個處理者只負責自己責任範圍內的訊息。2. **抽象共同行為**  
  定義一個抽象類別（或介面） `MessageHandler`，包含：

    - `handle` 方法：負責處理訊息。
    - `next` 屬性：指向下一個 Handler。3. **串接成鏈**  
  各 Handler 透過 `next` 連結起來，訊息從鏈頭開始依序傳遞：

    - 若 Handler 能處理該訊息，則處理並停止傳遞。
    - 否則，將訊息交給下一位 Handler。4. **解耦 Context 與 Handler**  
  Waterbowbot 作為 Context，只需將訊息交給責任鏈的入口 Handler，完全不需了解處理細節。
---

## 🦾 責任鏈模式類別結構

| 元件 | 功能說明 |
| --- | --- |
| **MessageHandler (抽象類別)** | 定義處理訊息的共同行為，持有下一個 Handler 參考，並提供 `handle` 方法。 |
| **ConcreteHandler (具體處理者)** | 繼承自 MessageHandler，實作特定訊息的判斷與處理邏輯。 |
| **Waterbowbot (Context)** | 接收外部訊息，將訊息委派給責任鏈的入口 Handler 處理。 |

---

## 🔄 依賴反轉與重構三步驟

透過 **依賴反轉 (Dependency Inversion)**，將變動行為封裝並抽象，重構流程如下：

| 步驟 | 說明 |
| --- | --- |
| **封裝變動行為** | 將每個訊息的處理行為封裝成獨立類別，如 HelpHandler、CurrencyHandler、DcardHandler。 |
| **抽象共同行為** | 抽出 MessageHandler 抽象類別，定義共同行為並持有下一個 Handler。 |
| **依賴注入組合責任鏈** | 透過建構子注入方式（Dependency Injection）將 Handler 按照責任順序串接形成鏈條。 |

---

## ⚙️ 責任鏈中 Handler 的 `handle` 方法範例（樣板方法）

責任鏈中各 Handler 的 `handle` 方法包含重複程式碼，可用 **樣板方法 (Template Method)** 模式優化：
```plaintext
handle(request):
    if match(request):       # 判斷是否屬於自己處理範圍
        doHandling(request)  # 執行實際處理
    else if next != null:    # 傳給下一個 Handler 處理
        next.handle(request)
```
- `match`：判斷訊息是否屬於該 Handler 的責任範圍。
- `doHandling`：實際處理訊息的具體邏輯。

---

## 🎯 責任鏈模式的 Resulting Context（結果）

- **Context (Waterbowbot)**：完全看不到各個訊息處理細節，僅與抽象 Handler 互動。
- **Concrete Handler**：獨立實作各自處理行為，彼此不受影響。
- **系統彈性與擴充**：新增或移除功能只需新增、串接或移除 Handler，無需改動 Context 內部程式碼。
- **符合開閉原則 (Open-Closed Principle, OCP)**：

  > 「既有類別應對擴充開放，對修改封閉。」
---

## 📋 相關設計模式關聯

| 模式名稱 | 功能定位 | 與責任鏈模式的關係 |
| --- | --- | --- |
| **策略模式 (Strategy)** | 封裝一組可替換的行為，讓演算法可動態切換。 | 與責任鏈模式類似，皆用來封裝行為，但策略模式是直接選擇一種行為。 |
| **樣板方法 (Template Method)** | 定義演算法骨架，將變動部分抽象為子類別實作。 | 用於責任鏈中抽取共用程式碼，減少 Handler 間的重複。 |
| **依賴注入 (Dependency Injection)** | 將相依物件由外部注入，降低耦合度。 | 用於組合責任鏈時注入下一個 Handler，使系統更彈性。 |

---

## 🔑 關鍵觀念整理

| 觀念 | 內容說明 |
| --- | --- |
| **解耦 (Decoupling)** | 責任鏈讓 Context 與各 Handler 實作解耦，Context 不需知道處理細節。 |
| **行為封裝 (Encapsulation of Behavior)** | 每個 Handler 封裝一種訊息處理行為，方便獨立開發和維護。 |
| **鏈式傳遞 (Chain of Passing)** | 訊息依序傳遞到鏈上的每個 Handler，直到有 Handler 處理或鏈尾無人處理。 |
| **行為變動性 (Behavioral Variation)** | 系統支援的訊息種類會增加，責任鏈模式可輕鬆因應此變動。 |
| **擴充性與彈性 (Extensibility & Flexibility)** | 新 Handler 可動態加入或移除，系統決定支援哪些訊息，且不影響既有程式碼。 |
| **開閉原則 (Open-Closed Principle)** | 現有類別對擴充開放，對修改封閉，實現此原則可提升軟體彈性與生命力。 |

---

## 🛠️ Waterbowbot 與責任鏈模式的實作步驟

1. **定義抽象類 **`MessageHandler`

    - 包含 `handle(request)` 抽象方法。
    - 持有 `next` 參考，指向下一個 Handler。2. **實作具體 Handler**

    - `HelpHandler`、`CurrencyHandler`、`DcardHandler` 等繼承自 `MessageHandler`。
    - 覆寫 `match` (判斷責任範圍) 與 `doHandling` (處理邏輯)。
    - 若不處理，呼叫 `next.handle(request)`。3. **組合責任鏈**

    - 在主控類別中依序建立各 Handler，並以建構子注入串接起來。
    - 傳入 `null` (或 `no`) 作為鏈尾。4. **Waterbowbot 委派處理**

    - Waterbowbot 接收訊息後，將訊息交給責任鏈的入口 Handler 處理。
    - Waterbowbot 本身不負責具體處理邏輯。5. **擴充與維護**

    - 新需求只需自行實作新 Handler，並串接到責任鏈中。
    - 不需修改 Waterbowbot 或其他 Handler 程式碼。
---

## 🔄 責任鏈模式與樣板方法的結合

| 角色 | 功能說明 |
| --- | --- |
| **樣板方法 (Template Method)** | 將 Handler 中的 `handle` 方法寫成具體方法，內含流程骨架。 |
| **抽象方法** | `match` (是否匹配訊息)、`doHandling` (實際處理)，由子類別實作。 |
| **重複程式碼移除** | 減少 Handler 之間重複 if-else 判斷，程式碼更精簡易讀。 |

---

## ⚠️ 容易混淆的重點說明

| 容易混淆點 | 解釋 |
| --- | --- |
| **責任鏈是否會多個 Handler 處理同一請求？** | 不會。請求只會被第一個符合責任範圍的 Handler 處理，未處理的會繼續傳給下一個 Handler。 |
| **責任鏈和策略模式差異？** | 策略模式是直接選擇一個行為執行，責任鏈模式是將多個 Handler 串成鏈條，依序嘗試處理請求。 |
| **為何要抽象出 **`next`** 屬性？** | 讓每個 Handler 都知道下一個 Handler，才能將未處理的請求委派出去，實現責任鏈傳遞機制。 |
| **開閉原則如何實現？** | 新增功能時只需新增 Handler 並串接，無需修改既有類別內部程式碼，使系統對擴充開放，對修改封閉。 |

---

## ⚙️ 設計模式應用實例流程示意

| 流程步驟 | 說明 |
| --- | --- |
| 1. 使用者發送訊息 | 在 Discord 頻道中輸入指令（如 Help、Currency、Dcard）。 |
| 2. Waterbowbot 接收訊息 | Waterbowbot 透過 Discord API 偵測新訊息事件，並將訊息與頻道資訊傳給責任鏈入口 Handler。 |
| 3. 責任鏈依序處理訊息 | HelpHandler 判斷訊息是否為 Help 指令，否則交給下一位 Handler；CurrencyHandler 判斷是否為 Currency 指令… |
| 4. 符合條件 Handler 執行處理 | 例如 CurrencyHandler 執行爬蟲取得匯率資訊，並回覆至 Discord 頻道。 |
| 5. 訊息處理完成 | 處理結束後不再傳遞；若無 Handler 處理則忽略該訊息。 |

---

## 🎓 重要概念總結

- **責任鏈模式** 透過串接多個 Handler 物件，使請求能在鏈上依序尋找合適的處理者。
- **抽象 Handler** 將共同行為與串接機制抽象化，Concrete Handler 負責具體處理。
- **樣板方法** 用於提取 Handler 中重複的控制流程，讓子類別只需實作變動部分。
- **依賴注入** 使得 Handler 的串接與管理變得靈活且符合開閉原則。
- **開閉原則** 是軟體設計的核心，確保系統能在不改動既有程式碼的前提下，輕鬆擴充新功能。
- **解耦設計** 使得系統維護與擴充更容易，尤其適合多團隊合作開發。

責任鏈模式使系統設計在面對多樣且持續變動的需求時，能夠保持結構清晰且易於擴展，提升軟體的生命力與彈性。
