## 🌳 复合模式（Composite Pattern）與樹狀結構的物件導向設計

> **復合模式**是結構型設計模式中用來解決**樹狀結構（Tree Structure）**的複雜性與擴充性問題，透過抽象化樹葉節點與樹枝節點，讓客戶端（Client）能無感知地操作整個樹狀結構。

---

### 1. 案例背景與需求說明

- **檔案系統結構**：由目錄（Directory）與檔案（File）構成階層式架構。

    - 目錄可包含多個子目錄與多個檔案。
    - 目錄與檔案皆以名稱識別，名稱合法字元為大小寫英文字母、數字、句點、橫線與底線。
    - 每個檔案含有二進位內容（文字、圖片等）。
    - 有一個根目錄（Root Directory）為整個檔案系統的入口，其他目錄和檔案皆存在於某個副目錄中。- **命令列介面 Comilite Interface**：

    - 使用者透過命令列指令操作檔案系統。
    - 預設當前目錄為根目錄。
    - 初版支援指令：

          - `CD Name`：切換當前目錄至當前目錄底下名稱為 Name 的子目錄。
          - `CD ..`：切換當前目錄至父目錄（若為根目錄則無法再往上）。
          - `Size Name`：印出當前目錄底下名稱為 Name 的子目錄或檔案所佔用的記憶體大小。- **大小計算邏輯**：

    - 目錄大小為所有子目錄與檔案大小總和。
    - 檔案大小為其二進位內容的位元組數。
---

### 2. 初版物件導向分析與設計

| 類別 | 屬性與方法 | 關係描述 |
| --- | --- | --- |
| **File** | - `Name`（名稱）   - `Content`：位元組陣列   - `Bytes()`方法回傳內容長度 | - 有一個父目錄（Parent Directory） |
| **Directory** | - `Name`（名稱）   - `AddDirectory()`、`AddFile()`   - `GetDirectoryByName()`、`GetFileByName()`   - `TotalBytes()`方法（加總所有子目錄與檔案大小） | - 0..* 子目錄與檔案的關聯   - 有一個父目錄（Parent Directory），唯獨根目錄無父目錄 |
| **Comilite Interface** | - `Current Directory`（當前目錄）   - `Start()`方法啟動命令行互動輸入   - `CD`及`Size`指令實作 | - 與Directory關聯（Current） |

- **關聯類型**：

    - 目錄與子目錄、檔案間為**複合（Composition）**關係（子物件無法脫離父物件存在）。
    - 命令行介面依賴目錄物件進行操作。
---

### 3. 初版程式設計問題與三道設計力（Forces）

| 設計力（Force） | 內容說明 |
| --- | --- |
| **高結構複雜度** | 目錄與檔案的遞迴關聯（Self Association）導致樹狀結構的無限延伸，結構複雜。 |
| **結構變動性** | 新檔案種類（如 Link）或類別關係變更會造成類別間關係改變，導致結構變動。 |
| **擴充性要求（符合開放封閉原則 OCP）** | 希望新增檔案種類時，能最小化對 Comilite Interface、Directory 等類別的修改，避免影響現有程式碼。 |

- **問題（Problem）**：如何在保持樹狀結構的擴充性與階層性同時，讓客戶端程式不受結構複雜度與變動性的影響。

---

### 4. 樹狀結構定義

- **條件**：

    1. 結構中存在至少一條遞迴關聯（Self Association）。
    2. 結構必須是嚴格的階層關係（無環路）。
    3. 每個物件最多只有一個父物件。
---

### 5. 复合模式（Composite Pattern）解決方案

#### 5.1 核心概念

- **抽象元件（Component）**：定義所有樹狀結構中物件的共同介面。
- **樹葉節點（Leaf）**：不可再延伸的終端節點（例如檔案）。
- **複合節點（Composite）**：可包含子節點的節點（例如目錄）。

---

#### 5.2 复合模式三步驟設計流程

| 步驟 | 說明 |
| --- | --- |
| **萃取共通抽象** | 抽出File與Directory共通特性，形成抽象類別 Item（包含 `name`、`parent`、`Bytes()` 方法等）。 |
| **依賴反轉** | Comilite Interface與Directory不再依賴具體類別File，而是依賴抽象的Item。子目錄與子檔案統一存放於Item list。 |
| **簡化操作** | 對子物件的新增、查詢、大小計算均以Item為統一操作，消除原本File與Directory兩種子物件成對重複的程式碼。 |

---

#### 5.3 重構後類別設計

| 類別 | 說明 |
| --- | --- |
| **Item** | 抽象類別，包含`name`與`parent`，以及抽象方法`Bytes()`，所有具體檔案與目錄皆繼承自此。 |
| **File** | 繼承Item，實作Bytes回傳內容大小，負責檔案名稱合法性驗證。 |
| **Directory** | 繼承Item，包含一個`children`的List<Item>，統一管理子目錄與檔案，實作Bytes為所有children加總。 |
| **Comilite Interface** | 依賴Item抽象介面，透過Item物件取得大小與切換目錄，實現指令操作的簡化。 |

---

### 6. 复合模式帶來的主要改進與特性

| 改進點 | 說明 |
| --- | --- |
| **程式碼簡潔** | 消除File與Directory中重複的新增、查詢、大小計算方法，統一使用Item介面操作。 |
| **擴充性佳** | 新增檔案種類或節點類別時，只需實作Item介面，不用修改Directory與Comilite Interface，符合開放封閉原則（OCP）。 |
| **結構透明度（Transparency）** | Client無需知曉樹狀結構的內部細節，只透過抽象的Item接口操作，彷彿只看到一個統一介面，樹狀結構的複雜性對Client透明。 |

---

### 7. 透明度（Transparency）與agnostic概念

- **透明度**指Client對Component介面背後複雜結構或實作的無感知、不在乎。
- 由於「透明」用詞易混淆，部分學者建議用**agnostic（未知者）**描述：

    - **structure-agnostic**：Client不知也不需知道樹狀結構的存在。
    - **framework-agnostic**：Client不知也不在乎使用了何種技術框架。
---

### 8. 重要概念與關鍵字定義

> **复合模式（Composite Pattern）**  
> 一種結構型設計模式，用於處理包含樹狀結構的物件集合，通過抽象共同介面統一管理葉節點與複合節點，從而簡化客戶端操作並提升擴充性。

> **樹狀結構（Tree Structure）**  
> 具有遞迴關聯且嚴格階層關係的結構，每個節點最多只有一個父節點，結構可無限延伸。

> **開放封閉原則（Open Closed Principle, OCP）**  
> 軟體實體應對擴展開放，對修改封閉，意味著新增功能不應修改既有程式碼。

> **依賴反轉原則（Dependency Inversion Principle）**  
> 高層模組不應依賴低層模組，兩者應依賴抽象；抽象不應依賴細節，細節應依賴抽象。

---

### 9. 典型方法行為與範例

| 方法名稱 | 所屬類別 | 功能說明 |
| --- | --- | --- |
| `Bytes()` | Item（抽象） | 回傳物件佔用的記憶大小，File為內容長度，Directory為所有子項目Bytes總和。 |
| `AddItem()` | Directory | 新增任意Item類別的子節點（子目錄或檔案）。 |
| `GetItemByName()` | Directory | 根據名稱查找子節點，回傳Item物件。 |
| `Start()` | Comilite Interface | 啟動命令列程式，持續接收使用者輸入指令並執行。 |
| `PrintSize(name)` | Comilite Interface | 查詢當前目錄底下名稱為name的Item，並呼叫其Bytes方法印出大小。 |
| `CD(name)` | Comilite Interface | 切換當前目錄到指定名稱的子目錄，或處理`..`回到父目錄的特殊指令。 |

---

### 10. 复合模式帶來的設計效益比喻

- **比喻說明**：  
  就如同企業組織的階層結構，客戶（Client）只需下達需求，無需了解公司內部各層級的組織細節與運作方式。組織內部透過明確的階層分工與抽象介面，使得客戶的需求能被有效執行而不受內部結構複雜度影響。
---

### 11. 复合模式應用的主要架構圖示（文字版）
```javascript
           Comilite Interface (Client)
                     │
                     ▼
                   Item (抽象介面)
                  /             \
             File (葉節點)    Directory (複合節點)
                                │
                        ┌───────┴────────┐
                        Item (子節點列表)
```
- Client只與抽象介面Item互動，無需區分File或Directory。
- Directory統一管理所有子Item，遞迴處理樹狀結構。

---

### 12. 總結

复合模式透過抽象統一樹狀結構中不同節點的介面，將結構的複雜性封裝於Component背後，使客戶端不必關注樹的組成與變化，並且大幅提升擴充性與維護性。這種抽象與封裝方法有效地解決了遞迴結構複雜度與變動性帶來的挑戰，確保新增節點類型時不需修改客戶端程式，符合物件導向設計的核心原則。

## 🌳 复合模式（Composite Pattern）核心概念與應用

### 1. 何時使用復合模式

- **使用時機**：當希望對 **Client（使用者）隱藏樹狀結構的複雜度與變化**，只讓 Client 專注於「意圖」（操作要求）而不必理解整體結構。
- **效果**：使 Client 變得 **structure-agnostic（結構無感）** 或 **hierarchy-agnostic（階層無感）**，Client 不需知道物件是樹葉還是樹枝，完全由系統內部決定。

### 2. 復合模式的結構設計

- **抽象介面 Component**：是樹葉節點和複合節點共同遵守的介面。
- **樹葉節點（Leaf）**：代表終端節點，不會有子節點。
- **複合節點（Composite）**：代表包含子節點的節點，可以新增、刪除子節點。

這樣設計的目的是讓樹狀結構被包裝在 Component 介面背後，Client 只需透過 Component 介面進行操作。

---

## ⚖️ 透明度（Transparency）與操作安全性（Operational Safety）之衝突

| 需求面向 | 內容說明 | 可能問題 |
| --- | --- | --- |
| **透明度** | 把所有操作（如 addItem、removeItem）都萃取到 Component 介面中，讓 Client 不需知道目標物件是 Directory（目錄）還是 File（檔案） | File 物件無法擁有子節點，必須實作但會丟出例外，造成使用上的不直覺與不安全 |
| **操作安全性** | 確保執行操作時不會因誤用而中斷程式，避免 Client 執行不合理的操作（例如對檔案新增子項目） | 若操作都在 Component 介面，且 File 物件的 addItem 被誤呼叫時會拋出例外，導致程式崩潰 |

### 透明度與操作安全性的衝突解釋

- 若為了**提高透明度**，將所有操作都放在 Component 介面，File 類別必須實作這些操作，但因其不支援子節點操作，程式只能丟出例外。
- 這種設計雖使 Client 完全無感於目標物件的實際類別，但降低了操作安全性，因為例外可能造成程式崩潰。
- 若降低透明度，讓 Client 知道目標是 Directory 才執行新增子項目，則可避免例外，提升操作安全性，但 Client 必須認識底層結構。

---

## ⚙️ Trade-off（權衡）策略

- **兩道 Force（需求力量）**：透明度（Transparency）與操作安全性（Operational Safety）必然存在衝突，需要依具體需求做取捨。
- 以 **檔案系統案例** 為例：

    - Client（Comdlite Interface）一開始即必須指定目前目錄（Current Directory），因此 Client 已經知道目錄存在。
    - 透明度需求較低，操作安全性需求較高，故可選擇讓 Client 知道目錄結構以保障安全。- **結論**：根據需求重要性判斷優先解決哪個 Force，避免因過度追求透明度而犧牲安全。

---

## 🎯 復合模式的「Resulting Context」特性

- **最迷人的特性**：Client 變得 **hierarchy-agnostic**，不需知道物件是樹葉還是樹枝。
- **技術框架的典型應用**：在配置檔案系統中，常見樹狀結構，透過復合模式隱藏複雜結構，讓使用者操作更簡潔。
- **常見設計**：

    - 抽象 Component 介面同時表達樹葉與樹枝節點。
    - 客戶端操作透過 Component 介面完成，降低系統耦合。
---

## 🛠️ 復合模式與其他結構型設計模式的比較

| 模式名稱 | 主要用途 | 與復合模式的差異 |
| --- | --- | --- |
| **門面模式（Facade Pattern）** | 將複雜系統的介面簡化，提供統一入口 | 著重簡化使用介面，不一定處理樹狀結構 |
| **轉接器模式（Adapter Pattern）** | 將不兼容的介面轉換成可共用的介面 | 著重介面轉換，不涉及樹狀物件結構 |
| **代理人模式（Proxy Pattern）** | 控制對物件的存取，常用於延遲載入、權限控制 | 著重物件存取控制，非結構隱藏 |

復合模式**核心在介面背後隱藏一棵樹**，專門解決樹狀結構的複雜度。

---

## 💡 重要提醒與後續挑戰

- 復合模式是**結構型模式中最核心的設計模式**，在物件導向分析與設計中具備基礎且廣泛的應用價值。
- 技術框架中的配置彈性往往依賴復合模式以支援多層次的設定結構。
- 復合模式的二星挑戰題以「Logging Framework（日誌框架）」作示範，完整演示如何從需求分析、設計到實作運用復合模式。
- 復合模式還有**特殊形式**，學習後可完整掌握結構與行為擴充的核心基礎。

## 重要概念整理表

| 觀點 | 說明 | 影響 |
| --- | --- | --- |
| **Component 介面** | 抽象出樹葉與複合節點共同操作的介面 | 隱藏樹狀結構，統一操作 |
| **樹狀結構透明度（Transparency）** | Client 不需了解物件的階層與類型 | 提升使用便利，但可能降低操作安全 |
| **操作安全性（Operational Safety）** | 防止錯誤操作導致系統崩潰 | 需要 Client 知道部分結構，降低透明度 |
| **Trade-off（權衡）** | 透明度與安全性必須平衡取捨 | 根據需求優先解決影響最大的 Force |
| **Client 的結構無感（structure-agnostic）** | Client 完全不關心物件的內部階層與分類 | 降低耦合度，提高系統彈性 |

---

## 比喻說明

- 將復合模式比喻為一棵樹，**Component 介面像樹的主幹**，樹枝（Composite）與樹葉（Leaf）分別是不同類型的樹節點。
- Client 不用分辨每片葉子或枝條，只需透過主幹操作整棵樹。
- 但若主幹的某些操作對葉子無效，就像踩到隱藏的地雷（例外），會導致危險（程式崩潰），這就是透明度和操作安全性的衝突。

---

## 操作安全性問題的技術細節說明

- 若將 `addItem` 和 `removeItem` 操作放在 Component 介面，File 物件必須實作這兩個功能。
- 由於 File 是樹葉，不能有子項目，故實作通常是**直接拋出例外**。
- 這種設計導致 Client 若誤呼叫 File 的新增操作，程式執行會中斷，不安全。
- 因此，需要在設計時決定是：

    - 讓 Client 知道 Directory 與 File 的區別，避免誤操作，提升安全性。
    - 或追求最高透明度，承擔因例外導致程式崩潰的風險。
---

## 結論判斷

透明度與操作安全性兩者相互牽制，設計時必須根據實際使用情境和需求重點做出抉擇。若系統高度依賴安全性，則可接受 Client 對樹狀結構有一定認知；反之，若追求最高封裝與透明度，則必須準備處理因操作不當引發的例外狀況。這種權衡是復合模式設計中的核心挑戰。
