## 🧩 裝飾者模式（Decorator Pattern）概述

> **裝飾者模式**是一種結構型設計模式，用來靈活組合多變的行為，避免因為組合爆炸而造成維護困難，並且支援擴充新的行為組合。

---

## 需求背景與初版 Messenger 設計

- **系統目標**：開發一個「對話軟體（Messenger）」，讓每個使用者（User）能夠透過 Email 傳送訊息（Message）給其他使用者。
- **User 屬性**：Email、暱稱（Nickname）
- **Message 屬性**：內容（1至2000字）、建立時間（Create Time）、傳送者與接收者（多對多關聯）
- **訊息格式**：

    - 顯示格式為 `[傳送時間][作者暱稱]: 訊息內容`
    - 訊息最少一字，最多2000字- **初版 Messenger 特點**：

    - 有多種 Messenger 實作，且在送出訊息前會進行不同的訊息加工處理。
    - 三種主要的訊息加工處理方式：

          1. **電子郵件遮蔽（Email Hiding）**：隱藏訊息中所有 Email 的部分字元。
          2. **電子郵件格式化（Email Style Formatting）**：將訊息內容包裝成 Email 格式（加上問候語）。
          3. **訊息分段（Paragraphing）**：以空行分段，分成多則訊息依序傳送。  - 初版只支援兩種加工組合：

          - Email Hiding + Paragraphing Messenger
          - Email Formatting + Paragraphing Messenger
---

## 初版物件導向分析（Object Oriented Analysis）

| 類別 | 屬性 / 職責 |
| --- | --- |
| User | Email、Nickname，能發送訊息 |
| Message | Content（1~2000字）、Create Time，關聯 User（多對多） |
| Messenger | 傳送訊息的類別，提供 `Send Message` 方法 |

- Message 為 User 與 User 間的關聯類別（Association Class）
- Messenger 內部實作不同訊息加工流程，形成不同 Messenger 類別

---

## 初版 Messenger 實作特色

- **Email Hiding and Paragraphing Messenger**：

    1. 使用正規表達式遮蔽訊息內的 Email
    2. 以空行分段訊息
    3. 依序印出分段訊息- **Email Formatting and Paragraphing Messenger**：

    1. 先格式化訊息為 Email 樣式
    2. 以空行分段
    3. 依序印出分段訊息- 兩者行為流程類似，唯加工處理順序及內容不同

---

## 新需求與設計挑戰

- 未來可能引入更多不同的訊息加工處理方式，且需自由組合，避免限定於少數幾種 Messenger 類別。
- 訊息可發送到不同終端（Endpoint），例如：

    - Console 顯示
    - Email 信箱
    - 第三方平台（Discord、Slack）
---

## 三大設計力道（Forces）

| 力道名稱 | 說明 |
| --- | --- |
| 組合爆炸（Combinatorial Explosion） | 行為有 N+1 組合變化，N 種加工方法任意組合，加上 1 種終端，組合數量指數成長。   例如 N=3 時有 32 種組合，增加加工方式組合數爆炸。 |
| 良好組合性（Composability） | 設計必須允許客戶端彈性組合各種行為，避免為每種組合建立獨立類別，減低複雜度。 |
| 擴充性（Extensibility） | 新增加工方法或終端時，不修改既有程式碼，遵守開放封閉原則（OCP，Open-Closed Principle）。 |

---

## 問題定義（Problem）

> 如何讓客戶端在不修改既有程式碼的前提下，能彈性地組合和擴充多種訊息加工處理及終端行為？

---

## 裝飾者模式的推導步驟

### 1. 封裝變動（Encapsulate What Varies）

- 將所有加工行為（配菜）和訊息發送終端（主菜）各自封裝成獨立類別。
- 配菜類別封裝特定加工行為，定義 `Process` 操作處理訊息。
- 主菜類別封裝終端的訊息發送行為，定義 `Send` 操作。
- 配菜可能會串接下一個處理器（類似責任鏈），以遞回方式呼叫下一個處理器。
- 特殊注意：`Paragraphing` 會將訊息分段成多則訊息，需支援多訊息傳遞給下一個處理器。

### 2. 萃取共同行為（Abstract Common Behaviors）

- **主菜行為**抽象為介面 `Messenger`，定義送訊息的 `Send` 方法，接收多則訊息。
- **配菜行為**抽象為抽象類別 `MessageProcessor`，繼承自 `Messenger`，擁有下一個 `Messenger` 聚合關聯，並覆寫 `Process` 方法。
- 修改 `Process` 的輸入為多則訊息，以支援分段訊息的傳遞。
- `MessageProcessor` 呼叫其聚合的下一個 `Messenger` 物件的 `Send` 方法，完成行為委派。

### 3. 套用複合模式（Composite Pattern）

- `Messenger` 介面為 Component，`MessageProcessor` 為 Decorator（配菜），`Messenger` 具體類別（如 ConsoleMessenger、DiscordMessenger）為 Concrete Component（主菜）。
- `MessageProcessor` 聚合另一個 `Messenger`，形成裝飾鏈（串列），透過遞迴呼叫實現多層裝飾行為。
- 透過依賴注入方式建構出任意組合的裝飾鏈，達成彈性且可擴充的行為組合。

---

## 第二版系統類別架構與流程

| 類別名稱 | 角色 | 功能說明 |
| --- | --- | --- |
| Messenger（介面） | Component | 定義 `Send(messages: List<Message>)` 方法，作為所有訊息發送者的共同介面。 |
| MessageProcessor | Decorator（配菜） | 繼承 Messenger，封裝一個下一個 Messenger，實作特定訊息加工，並呼叫下一個 Messenger。 |
| EmailHidingProcessor | Concrete Decorator | 封裝 Email 遮蔽行為，呼叫下一個 Messenger。 |
| EmailFormattingProcessor | Concrete Decorator | 封裝 Email 格式化行為，呼叫下一個 Messenger。 |
| ParagraphingProcessor | Concrete Decorator | 封裝訊息分段行為，呼叫下一個 Messenger。 |
| ConsoleMessenger | Concrete Component | 將訊息輸出到 Console。 |
| DiscordMessenger | Concrete Component | 模擬將訊息發送到 Discord。 |

---

## 主要類別與方法說明

| 類別 | 主要方法 | 功能描述 |
| --- | --- | --- |
| Messenger | `Send(messages)` | 抽象方法，負責傳送多則訊息。 |
| MessageProcessor | `Process(messages)` / `Send(messages)` | 執行特定加工行為，呼叫下一個 Messenger 的 `Send`。 |
| EmailHidingProcessor | 覆寫 `Process` | 將 Email 部分字元遮蔽，呼叫下一個 Processor。 |
| EmailFormattingProcessor | 覆寫 `Process` | 將訊息格式化為 Email 樣式，呼叫下一個 Processor。 |
| ParagraphingProcessor | 覆寫 `Process` | 將訊息依空行分段，呼叫下一個 Processor。 |
| ConsoleMessenger | 覆寫 `Send` | 將訊息輸出到 Console。 |
| DiscordMessenger | 覆寫 `Send` | 模擬將訊息發送至 Discord。 |

---

## 行為組合示範

- 以 Email Formatting + Paragraphing + Discord Messenger 為例：
```plaintext
new EmailFormattingProcessor(
    new ParagraphingProcessor(
        new DiscordMessenger()
    )
)
```
- 以 Email Hiding + Paragraphing + Console Messenger 為例：
```plaintext
new EmailHidingProcessor(
    new ParagraphingProcessor(
        new ConsoleMessenger()
    )
)
```
行為流程：

1. 呼叫最外層 Processor 的 `Send` 方法。
2. 依序執行每個 Processor 的加工行為。
3. 最終由主菜 Messenger（Console 或 Discord）將訊息送出。

---

## 裝飾者鏈的運作機制

| 步驟 | 說明 |
| --- | --- |
| 1. 呼叫外層 | 呼叫最外層 `MessageProcessor` 物件的 `Send` 方法，開始加工流程。 |
| 2. 加工訊息 | 該 Processor 進行自己的加工（如遮蔽 Email 或格式化），完成後呼叫下一個 Processor。 |
| 3. 遞迴傳遞 | 下一個 Processor 接收經加工的訊息，繼續執行自己的加工，流程沿鏈條向終端遞迴。 |
| 4. 最終輸出 | 主菜 Messenger 收到最終訊息，執行實際送出動作（Console 印出或模擬發送 Discord）。 |

---

## N+1 行為組合變化與設計挑戰

- **N+1 組合變化**：

    - N 種配菜加工行為任意排列組合（$2^N$ 種）
    - +1 種主菜終端行為- 造成組合數量指數級爆炸，開發難度和維護成本劇增。

---

## 三大設計力道在裝飾者模式中的體現

| 力道 | 裝飾者模式解決方案 |
| --- | --- |
| 組合爆炸 | 裝飾者模式透過串接多個裝飾類別（Decorator），以組合方式實現多種行為，避免類別數指數爆炸。 |
| 良好組合性 | 客戶端可自由組合任意多層裝飾，彈性高且程式碼乾淨。 |
| 擴充性 (OCP 原則) | 新增配菜或主菜類別時，不須修改既有類別，符合開放封閉原則。 |

---

## 裝飾者模式與複合模式的關係

- 裝飾者模式是複合模式（Composite Pattern）的一種特殊形式。
- 兩者皆使用遞迴關聯（Recursive Composition）形成樹狀或串列結構。
- 裝飾者模式以裝飾鏈串聯多個行為，複合模式強調整體與部分的統一介面。

---

## 關鍵概念總結

| 概念 | 定義與說明 |
| --- | --- |
| 行為組合爆炸 | 行為組合數量隨加工行為數量指數成長，難以維護。 |
| 配菜（Decorator） | 可加在主菜前的多種加工行為，可串成鏈條。 |
| 主菜（Concrete Component） | 最終送出訊息的行為，如 ConsoleMessenger、DiscordMessenger。 |
| 裝飾者鏈 | 由多層裝飾器串連而成的結構，實現動態行為組合。 |
| OCP（開放封閉原則） | 擴充新行為不修改既有程式碼，增強系統彈性與維護性。 |
| 依賴注入（Dependency Injection） | 透過建構子傳入下一個組件實例，實現裝飾鏈的組合。 |

---

## 重要程式設計原則與模式關聯

| 原則 / 模式 | 作用說明 |
| --- | --- |
| 依賴反轉原則（Dependency Inversion Principle） | 抽象化介面，避免高層模組依賴低層實作，促進擴充性。 |
| 責任鏈模式（Chain of Responsibility） | 行為串接與委派，類似裝飾者鏈的遞迴呼叫結構。 |
| 複合模式（Composite Pattern） | 建立統一介面，處理樹狀結構，裝飾者模式為其特殊應用。 |

---

## 裝飾者模式實踐的效益

- **彈性組合**：允許系統依需求自由組合多種訊息加工與送出行為。
- **降低維護負擔**：避免類別數爆炸，易於理解與管理。
- **擴充簡易**：新增加工器或終端時，不需改動原有類別，提升系統彈性。
- **行為可重用**：單一職責的加工器類別可重複利用於不同組合。

---

裝飾者模式透過將多種可變行為封裝成獨立類別，並串成裝飾鏈，實現行為的動態組合與延伸，同時保持系統設計的清晰與彈性，能有效解決大量行為組合爆炸的問題，並且讓擴展新的加工行為與終端行為成為可能。

## 裝飾者模式（Decorator Pattern）🧩

> **裝飾者模式**是一種結構型設計模式，透過串接多個裝飾者（Decorator）物件，動態地為主體物件（Concrete Component）增加行為，達成行為的多層次組合與擴充。

---

### 1. 裝飾者模式的核心概念

| 名稱 | 說明 |
| --- | --- |
| **Component（組件）** | 抽象介面或抽象類別，定義主體物件與裝飾者共同的行為介面。 |
| **Concrete Component（具體組件）** | 實現 Component 介面的主體物件，裝飾者最終會包裝的核心物件。 |
| **Decorator（裝飾者）** | 繼承 Component，持有一個 Component 物件的參考，並在執行行為時先執行自己的裝飾邏輯，接著呼叫被包裝物件的行為。 |
| **Concrete Decorator（具體裝飾者）** | 實作具體的裝飾行為，先執行自身想要的行為，再呼叫下一個 Component（可能是另一個 Decorator 或 Concrete Component）。 |

---

### 2. 行為串接機制

- **裝飾者形成行為鏈條（Chain）**：每個 Concrete Decorator 先完成自己的裝飾行為，然後呼叫下一個 Component 的操作，直到最底層的 Concrete Component。
- 如同「接力賽跑」中每棒選手完成自己的任務後，將棒子傳給下一棒，裝飾者模式中行為在物件間逐層傳遞與疊加。

---

### 3. 裝飾者模式帶來的三大優點

| 優點 | 說明 |
| --- | --- |
| **良好的組合性與擴充性** (Composability and Extensibility) | Client 可以自由組合 n+1 種行為，若 n=4，則可組合出 $2^4=16$ 種行為，且新增裝飾者或 Concrete Component 時遵守開放封閉原則（Open-Closed Principle，OCP）。 |
| **結構透明性** (Transparency) | 將複雜的行為組合結構隱藏在 Component 介面背後，Client 僅依賴介面，無需了解背後具體的裝飾者串接細節，行為組合變動不影響 Client。 |
| **行為維護性與可測試性** (Maintainability and Testability) | 將不同子行為封裝成獨立的類別，方便單獨維護與測試，提高程式碼品質與可讀性。 |

---

### 4. 裝飾者模式的套用條件與實作步驟

| 問題導向 | 解決方案 |
| --- | --- |
| **何時套用？** | 當系統中有 n+1 種行為變化，造成行為組合爆炸，難以管理時。 |
| **如何套用？** | 主菜（Concrete Component）繼承 Component 抽象類別，配菜（Decorator）繼承 Decorator 抽象類別，並串成行為鏈即可。 |

---

### 5. 與其他結構型模式的比較與關聯

| 模式名稱 | 主要目的 | 與裝飾者模式關係 |
| --- | --- | --- |
| **門面模式（Facade Pattern）** | 隱藏複雜結構，降低 Client 認知負擔 | 隱藏結構以簡化介面，著重於方便使用 |
| **轉接器模式（Adapter Pattern）** | 轉換不相容介面，使 Client 可依自身介面操作 | 隱藏第三方介面差異，強調介面相容性 |
| **代理模式（Proxy Pattern）** | 控制對物件的存取，可能延遲載入或權限控管 | 介入 Client 與目標物件間的呼叫，增加額外控制與功能 |
| **複合模式（Composite Pattern）** | 組合物件成樹狀結構，讓 Client 對單一物件與組合物件無差異操作 | 強調透明性，讓 Client 不須關心物件階層結構 |
| **裝飾者模式（Decorator Pattern）** | 動態擴充物件行為，利用複合結構串接多層裝飾 | 複合模式的特殊形式，強化行為的動態組合與擴充 |

---

### 6. 控制反轉框架（Inversion of Control Framework, IoC）與設計模式

- **控制反轉（IoC）**為大型軟體架構或框架設計中重要概念，核心為將控制權由 Client 反轉給框架或容器。
- 裝飾者模式等結構型設計模式是構建 IoC 框架的基礎技術之一。
- 透過設計模式積木式的組合，構建出靈活且可維護的 IoC 框架。

---

### 7. 裝飾者模式與行為型與結構型模式的差異

| 模式類型 | 特色與重點 |
| --- | --- |
| **行為型模式（Behavioral Pattern）** | 著重行為的變化與互動，解決行為變化導致程式碼擴散的問題。 |
| **結構型模式（Structural Pattern）** | 著重物件結構的組合與隱藏，降低 Client 對複雜結構的認知負擔，並強調介面透明性。 |

- 副本 2、3 著重行為型模式，處理行為的多樣變化。
- 副本 4 著重結構型模式，強調結構的封裝與透明，讓 Client 不需深入了解結構細節。

---

### 裝飾者模式的行為流程示意
```text
ConcreteDecoratorA -> ConcreteDecoratorB -> ... -> ConcreteComponent
       ↑                    ↑                         ↑
    執行自身行為          呼叫下一個裝飾者          主體物件的基本行為
```
- 每個裝飾者先執行自己的行為，接著呼叫下一個 Component。
- 最終由 Concrete Component 完成核心行為。

---

裝飾者模式利用複合結構靈活串接多層裝飾，實現行為的自由組合與擴充，確保系統在面對多變行為時仍具備良好的結構透明性與維護性。這種設計理念與模式的組合，成為建立大型軟體架構、尤其是控制反轉框架的基礎。
