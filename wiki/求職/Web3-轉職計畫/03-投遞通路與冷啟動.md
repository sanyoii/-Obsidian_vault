## Application-first 決策

1. Primary QA／Product Quality 與 Secondary Technical Support 使用兩份 role-specific resume，不用一份混打。
2. Qualified role 先投，Day 21–25 portfolio evidence 並行補強；不等所有作品完成。
3. Fully Remote 是 hard gate；`Remote` 標籤本身不等於 Taiwan eligible。
4. 每次投遞只用當日 official job page；舊 inventory、聚合站與 company-level remote policy 只能做 discovery。
5. Saved job 不算 application；只有實際 submitted 才進 funnel。

## Submission gate

每一份送出前都要通過：

- [ ] Official job page 仍 active，checked date 為 submission day
- [ ] Taiwan／APAC／Global eligibility 明確；不明則記 `Unknown`，不得自行補成 Pass
- [ ] Fully Remote；hybrid／relocation-only 直接排除
- [ ] Role family 符合 Primary／Secondary／Stretch boundary
- [ ] Resume 是單語、單 role、針對 JD 選材，未改 chronology／employment title
- [ ] Unsupported tools、AML ownership、Web3 tenure 與 blocked metrics 掃描通過
- [ ] schedule、shift、weekend、on-call、travel／offsite 的 unknowns 已列為 screen questions
- [ ] Contact、Degree、LinkedIn、Portfolio、GitHub links 使用已核准版本
- [ ] User 完成人工 PDF／DOCX 檢查；任何 submit／message 都有當次明確授權

## Pipeline 規則

| 維度 | 規則 |
|---|---|
| Role track | QA／Product Quality、Technical Support 分開計算；Stretch Lead 另標 Conditional |
| Eligibility | Taiwan／APAC／Global role-level evidence 與 company-level remote policy 分開 |
| Stage | Submitted → Recruiter／TA → HM → Later stage／Closed；不得跳階推定 |

| Unknown | schedule／on-call／travel 等未公開欄位保持 `Unknown`，進 screen 再問 |

## Iteration thresholds

以下是 operating thresholds，不是市場 benchmark：

- 十份 qualified applications 或 7–10 business days，取較晚者，才做第一輪 review。
- 零 screen：檢查 targeting、remote eligibility、title、summary 與前三個 evidence points。
- 有 screen，但連續三次未進 HM：修正 transition narrative、role fit 與 STAR selection。
- 有 HM，但連續三次未前進：檢查 technical depth、examples、answer precision 與 mock evidence。
- 不因單一 rejection 新增 unsupported tools 或重寫完整 career history。

## Outreach 與冷啟動

優先順序：

1. 對 target company 的公開 repo 提出可重現 bug、test 或 documentation fix。
2. 以 CEX lab、test design 或 case study 對工程師提出具體技術問題。
3. 使用短、role-specific recruiter／referral message；不大量發送罐頭訊息。
4. 每次 message、application 或 live profile change 都需要當次明確授權。

### 追蹤表規則

career-ops 追蹤表**必須拆成兩個 pipeline，不可混在一起算轉換率**。

理由：兩軌的市場條件完全不同，混在一起算出來的數字沒有任何診斷價值——海外低轉換會被台灣的數字蓋掉，反之亦然。而 [[00-總覽與定位]] 的 M2 停損判斷（海外初面低於 4 場就停投改履歷）完全依賴這個數字乾不乾淨。

- [ ] 在 career-ops 建立兩個獨立 pipeline
- [ ] 每兩週各自計算：回覆率、初面轉換率

**M2「海外累積 40 份」的現實補充（2026-07-27 語料實證）**：單日快照裡真正可投的只有約 14 份（歐洲可投 7 ＋ Anywhere 遠端 7），其餘綁美國／新加坡／杜拜在地。40 份**不可能靠單次盤點達成**，必須靠職缺輪替累積——所以**每週重掃是固定節奏，不是可選項**。

- [ ] 把每週 JD 重掃排進行事曆（與 [[02-35天執行計畫]] Week 1 的重掃規則同步）

### 冷啟動策略

**前提**：無內部推薦管道，靠可被查證的工作品質開路。

以下按投報率排序，不是按容易度排序。

#### ① 對目標公司的開源專案送 PR / issue（最高投報率）

用 QA 的角度做三件事：

- [ ] 找 bug，附最小重現
- [ ] 補測試
- [ ] 修錯誤的文件範例

**為什麼這個排第一**：它直接把工作品質展示給團隊看，而且**不需要認識任何人**。一個附最小重現步驟的 issue，比任何自我介紹都有說服力。

名單來源：[[02-35天執行計畫]] Week 1 撈出的 8–10 個目標公司 repo。

#### ② 技術寫作

- [ ] 把 Week 3 作品的過程寫成 2–3 篇英文短文
  - 提幣狀態機怎麼拆
  - reorg 怎麼測
  - 內外帳不一致的排查路徑
- [ ] 發 X ＋ Mirror

**目的不是流量**，是讓人 Google 到他的名字時，看得到他在想什麼。

#### ③ 直接聯繫目標公司的工程師

注意：**是工程師，不是 recruiter**。問技術問題，不問職缺。

**話術範本**：

> ❌ 不要問：「請問貴公司有沒有職缺？」（回覆率極低）
>
> ✅ 改成問：「我在做一個交易所提幣流程的測試套件，想確認我對 XX 環節的理解對不對，能聊 20 分鐘嗎？」

差別在於：前者是索取，後者是請教，而且附帶展示了他正在做的東西。

- [ ] 每週主動聯繫 3 人（對應 [[02-35天執行計畫]] Week 5 的節奏）
